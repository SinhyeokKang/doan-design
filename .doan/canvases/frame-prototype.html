Same target (Play on the frame already in this window): bring the window forward and keep its input and size. Different frame (a main-window Play or a drawer pick): reuse this window, fit it to that frame within the screen, reset state and add a history entry. Back and Forward play the previous or next entry the same way without adding one, and skip entries whose frame or support mark is gone. Reload restarts the current frame from its initial state (inputs, open modal, scroll and animation), keeps the window size and adds no entry. Main-window navigation or hiding does not change the target; Quit ends both windows.

Content-only scope: inputs, buttons, modals, scrolling and motion. Document navigation, new windows, downloads and native form submit are blocked. Fetch keeps the existing canvas policy. These are required behaviors, not verified prototype capabilities.

Loading, recovery and target loss

Every state reuses the problem overlay (styles.css .problem-overlay and .problem-scene): over the content panel only, the panel colour at 60 % with an 8 px blur, the scene centred. The previous run stays visible under the blur and is inert; the first load shows an empty panel. With Reduce transparency the overlay is the opaque panel. No loading, failure or lost view counts as a successful prototype render.

Each title names its cause: loading, read failure, initialization failure, frame removal and support removal do not share a title. Back, Forward, Reload and the frame name stay usable above the overlay; Reload on a failure or lost state acts as Retry, and during a load it starts the load again.
