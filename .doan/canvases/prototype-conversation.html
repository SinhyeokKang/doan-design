A conversation beside the prototype

Scope: the prototype window’s header conversation button and its badges, the conversation panel that pushes in beside the frame column, the window’s widening to 640, the window fit when playing with the panel open, the playing frame chip, the panel’s states and the toast when the main window cannot act. /design-sync compares all nine frames: header-button, panel-open, panel-wide, small-screen, panel-play, panel-states, playing-chip, both-windows, reveal-toast; all nine are new.

  • New, not in code (marked on each frame): the header conversation button and its working badge, the panel layout in the window, the window fit for a Play with the panel open, the headless panel’s 16 px top inset, the playing frame chip, the list failure line and its composer reason, the dialog reason of “Couldn’t show”.

01

Header · conversation button New, not in code

The header holds Back, Forward and Reload prototype on the left, the frame name between the groups, and on the right the Fit and Responsive toggle, Export prototype and, last, the conversation button (16 from the window’s end, 4 after Export). With it the right group is 140 wide, so the name capsule stays in the first row from 444 wide windows (80 wide at 444) and moves to a second header row below that. Tab goes Back, Forward, Reload, the name, the toggle (one stop), Export, the conversation button, then the frame’s content and the conversation panel. The button is one element in every state: its label, icon, aria-expanded and badge change. It keeps the history buttons’ chrome look (32 px, radius 10). Badges show only while the panel is closed, one at a time: needs your answer > working > finished unread. The working badge is the sidebar’s working mark (a 14 px neutral spinner) on the unread bubble’s place and ring, so no new accent place is added. The board leaves out aria-controls because it holds many panels: in the app the button points it at the shipped CONVERSATION_PANEL_ID ("doan-conversation-panel", ConversationPanel.tsx) on the column’s aside in every state, as the main window’s Show and Hide conversation do.

02

Opening the panel from a narrow window New, not in code

Like Chrome DevTools docked to the side, the panel takes width from the frame column. A window narrower than 640 widens to exactly 640 and the panel opens at its 280 minimum, so the frame column keeps its 360 minimum. The content panel and the conversation column form one surface: the content panel keeps its start corners, the column its end corners, with the shipped 1 px start edge between them; both run from under the header to 8 above the window’s bottom.

03

Opening the panel in a window 640 or wider New, not in code

A window already 640 or wider keeps its size. The panel opens at the canvas panel’s default width, cut to the maximum, and the start-edge handle resizes it between 280 and min(50 %, window − 360). Closing the panel leaves the window as it is and gives the width back to the frame column.

04

A work area narrower than 640 New, not in code

The window stops at the work area’s width and stays inside it; the frame column gives way. The handle keeps its role but has no range here: its maximum min(50 %, 600 − 360) = 240 is under the 280 minimum, so the maximum is 280 too and the panel stays at 280.

05

Playing with the panel open New, not in code

A new Play while the panel is open (a Play from the main window, the drawer, Back/Forward, doan open --prototype) fits the window to the marked size plus the panel: width = marked width + 16 + panel width (at least 640), height = marked height + 64 (header 56 + bottom inset 8). When that is wider than the work area the panel gives way first, down to 280, then the frame column; the height stops at the work area’s height. Opening the panel in a narrow window (02) narrows the frame column instead, while a Play keeps the marked width; the two look different on purpose.

06

Panel without its head · states New, not in code

The canvas conversation panel without its head: no title menu, New conversation or Hide conversation (the header button hides it). It always shows the playing canvas’s current conversation, also while the main window shows an earlier one. The thread, choice cards, suggestions, composer, reason lines and docked buddy are the shipped ones; new here are the playing frame chip in the card (frame 07), the list failure line and its composer reason. Tiles are the conversation column of a 600 px high window (280 × 536).

07

Playing frame chip New, not in code

The playing frame always goes with a message from this window, as one frame chip at its start; a field that already starts with the same chip is not given a second one. The chip follows the playing frame, named by its own title (its id when it has none). It takes no focus, so like the shipped field chips it has only a native title, not the shared Tooltip; the composer field carries its meaning through aria-describedby. For the implementation: that description changes whenever the playing frame changes, and the field drops it while the composer is locked (canvas no longer listed, duplicate canvas ID).

08

One conversation in both windows New, not in code

Both windows show the same thread, cards, queue and turn line, and either can answer. The window whose answer arrives second folds its card without “Couldn’t send your answer. Choose again.” Drafts and attachment chips stay per window.

09

Main window busy · Couldn’t show New, not in code

Thread chips and the main-window-only buttons (Sign in, the Open buttons) bring the main window forward and act there. When it cannot act, it does not cancel what it holds and shows one toast with the reason. When it can, it acts as its own chips and buttons do (locate, open the canvas, “No longer in the canvas”, the canvas-not-found toast), so those are not drawn again.
