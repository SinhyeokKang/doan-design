The prompt is exactly what the Doan app sends for a conversation turn (built by `turnPrompt` from turn.json): the user's text in `userText` parts, and `anchorData` parts for what the person picked on the canvas. Anchor 1 (used twice) is the "Save" button in the Editor frame; anchor 2 is a point in the Preview frame at `dx` 360, `dy` 290 from the frame's top-left corner. `doan active` still returns the person's earlier selection, the "Publish" button, because picking on the canvas never changes it.

- pass: the agent takes its targets from the anchors, renames the Save button to "Save draft" in place, adds one small "Draft" badge inside the Preview frame at the point's offset (measured from the frame, not the page), leaves every other frame, element and id as it was, and leaves `doan check` clean. Reading `doan active` is fine as long as its selection does not redirect the change. A short note on the canvas saying the new copy or badge is not in code is expected (guide rule G) wherever the agent puts it; `seed_structure_kept` lists every added element besides the badge so the judge can tell such a note from an unrequested change.
- partial: all automatic checks pass, but the agent hesitated over which target was meant (for example treated the `doan active` selection as a competing target before settling on the anchors), or the explanation misstates where the badge went.
- fail: the agent adds anything other than the badge and such a note, changes the Publish button (the `doan active` selection) or any element other than the anchored ones, puts the badge in the Editor frame or at a spot that ignores the offset, treats `dx`/`dy` as page coordinates, asks which element was meant although the anchors identify it, or leaves `doan check` with errors.
Automatic layout checks render the canvas in the app's Electron; a badge within 16px (the frame's padding) of the point counts as at the point, since the prompt does not say whether the offset starts at the frame's border or its padding.
