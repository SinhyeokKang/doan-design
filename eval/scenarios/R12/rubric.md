The prompt is exactly what the Doan app sends for a Home conversation's turn (built by `turnPrompt` from turn.json with the Home and handoff lines): the user's text in `userText` parts, a context with the project root and no canvas, the Home line (the request has no canvas selection, so the agent finds its target from the request), and at the end the handoff line. The person asks for a mobile version of the existing `account` canvas as a new canvas, `account-mobile`: 390 px wide, with its Profile and Billing screens stacked in one column, `account` left alone. They add that the mobile version is where the work continues, and that the next step is tuning its tap targets. The handoff line asks the agent, for every new canvas the turn made in `.doan/canvases/`, to run `doan handoff <path> --message '<message>'` once for each canvas, consecutively as its last step, each as its own plain command (not joined with `&&` or `;`), with the message as a single quoted argument (no heredoc, pipe or redirection), with a message another agent can continue from alone, and to say the result in one line. It skips handoffs if the person asks not to hand off or to stay on this canvas or in this conversation. The fake app stands for the Home conversation, which has no source canvas: it knows the key in `DOAN_HANDOFF`, accepts the request and records it; the app's later steps (starting the new conversation when the turn ends, the toast) are not simulated.

- pass: the new canvas `account-mobile` exists with both screens stacked for a 390 px width and nothing else in the repo changed (`account` is untouched), `doan check` is clean, and the agent ran `doan handoff` for that canvas so that exactly one request was accepted, as its last step, after the canvas was complete. A refused attempt followed by one accepted request still passes the automatic checks (a refusal does not reserve the canvas path); the judge notes the refused attempt as a stall. The agent found `account` from the request, not from `doan active` (the Home line says not to). The message is written for a reader who has not seen the conversation: it carries the person's request (a mobile version of `account`, 390 px, screens stacked, `account` untouched), what was decided and made (the new canvas and what it contains) and what is left (tuning tap targets). The final answer says the result in one line, does not offer to open the canvas in Doan, prints no `doan://` link and runs no `doan open`. A `doan:` location link is allowed.
- partial: all automatic checks pass, but the message is thin (for example only "continue on the mobile canvas" or a path), omits what is left, or asks the next agent to redo work already done; or the final answer is long instead of one line; or the agent ends with an offer to open the canvas in Doan (the turn prompt overrides the guide's offer rule; classify it as guide unless the prompt line is missing from the transcript).
- fail: no accepted `doan handoff` or a second accepted one, one for another canvas (automatic checks `handoff_requested_once`, `handoff_path_is_new_canvas`), a handoff before the canvas is complete (`canvas_written_before_request`), an empty message, a new canvas that is not `account-mobile`-like or an extra new canvas, a change to `account` or any other file (`only_new_canvas_added`), a new canvas that is not 390 px wide (`new_canvas_390_wide`: `<meta name="doan:width" content="390">`, or a wider board whose CSS declares `width: 390px`, since `doan:width` is the board and the frame is the screen) or that lacks the copy of either screen of the seed (`new_canvas_has_both_screens`: the Profile email line and the Billing invoice line), `doan check` errors, or `doan open`. Treating the handoff as an instruction the agent must also carry out itself (doing the tap-target tuning in this turn) is also a fail: the person said that is the next step, in the new conversation.

Automatic checks read the app's own record of the v5 requests (`ctx.handoff()`), not the transcript, for the count, the path, the message and the order against the canvas content. Each check has one cause: `handoff_requested_once` counts accepted requests; `handoff_path_is_new_canvas`, `canvas_written_before_request` and `handoff_message_not_empty` judge every accepted request on its own, so a missing or extra request does not turn the per-request checks false. The message's first 300 characters are in the `handoff_message_not_empty` detail. Whether the screens are really stacked in one column is not measured automatically; the judge scores it from the canvas diff. Either one frame holding both cards or two frames counts as stacked. The Codex run sees the eval workspace's committed `.codex/rules/doan.rules`, which allows `doan`; whether a real Doan conversation asks for approval of `doan handoff` is not measured here.
