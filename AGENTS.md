# AGENTS.md

## Working principles

- **State assumptions**: if there are several interpretations, do not silently pick one — present the options. If unsure, ask.
- **Propose a simpler way if there is one**: do not add flexibility, configurability, or abstraction that was not requested. **Building ahead for extensibility is itself a defect.**
- **Surgical changes**: no adjacent improvements or refactors not directly related to the request. Follow the existing style. Remove only orphans your own change created.
- **Turn tasks into verifiable goals**: "fix the bug" → "reproduce, then confirm it passes". For multi-step work, first present a plan that includes a verification check for each step.
- **Do not report unverified things as passing.** Leave verification you lacked the tools for or could not run as unfinished, and report what you could not do.
- **Leave evidence for references**: for ideas taken from other tools (Claude Design · Orca · ego-browser · Storybook, etc.), write where they came from. Do not assert from memory; check what can be checked.

- **Keep rules separate from domain context**: AGENTS.md contains working principles and procedures. Keep product behavior, feature-specific constraints, and implementation decisions in PRODUCT.md, ARCHITECTURE.md, or the relevant feature documents; link to those sources instead of duplicating their content here.

> The source of the working rules for this repo. Claude Code and Codex both read this file — there is no mirror and no generator.

## Response style (takes precedence over every other rule in this document)

**Reply in Korean, concisely.** If a reply violates this, rewrite it. The items below are pass/fail criteria, not preferences.

- **Language policy**: Korean is used only for (a) conversation between the agent and the user (replies, reports) and (b) documents under `docs/features/<slug>/` (spec·design·tasks and audit reports). Everything else is English: AGENTS.md, skills (`.agents/skills`), `docs/` (PRODUCT.md, ARCHITECTURE.md, and future docs), README.md, code comments, commit messages, and PR title/body.
- **Plain register**: Korean replies and reports use the plain non-honorific style (`~했다`, `~이다`, `~할까?`), not 존댓말 (`~습니다`, `~해요`). This also covers AskUserQuestion text and interim updates.
- **The first sentence is the conclusion**: no preamble or announcement — do not open with phrases like "~해보겠습니다" ("I'll go ahead and…"), "좋은 질문입니다" ("Good question"), or "확인해보니 다음과 같습니다" ("Having checked, here is what I found"). Start with the answer or result.
- **No embellishment**: drop evaluative or agreeing phrases such as "완벽합니다" ("Perfect"), "훌륭한" ("great"), "핵심적인" ("key"), "말씀하신 대로" ("as you said") whenever removing them loses no information.
- **No restating**: do not re-explain in prose a diff, command output, or file content you just showed.
- **Length cap**: simple question or confirmation → 3 lines or fewer. Task-completion reports have no line cap — do not cut needed information just to make them short.
- **Unfinished work and failures first**: put what you could not do, failed verification, and skipped scope before the success summary.
- **No listing of options**: pick one recommendation and give one line of reasoning. The only exception is a point where the user must decide ("State assumptions" under Working principles).
- **Exception**: code, commit messages, and PR title/body are in English (see the language policy above).
- For Korean phrasing, also follow [Korean writing rules](#korean-writing-rules) below.

Enforcement has two layers: this section (shared by both runtimes), and the `UserPromptSubmit` hook in `.claude/settings.json`, which re-injects **a summary of this section** and of the decision-source rules into the context every turn (so the start of the document does not fade in long sessions).

## Korean writing rules

These apply to conversation replies and reports to the user, and to feature documents (`docs/features/<slug>/`). They target text that is newly written or revised within the scope of a request; they do not mean rewriting all existing text. **Meaning and the reader's understanding are the criteria.**

- **Preserve content first.** Do not change numbers, dates, proper nouns, quotes, negations, conditions, exceptions, causal relations, or who performs an action. Also keep possibility, inference, and obligation distinct. Do not insert an arbitrary subject into a passive sentence whose subject is unknown.
- **Make sentences read as if written in Korean from the start.** Undo unnecessary nominalization, double passives, and strings of abstract nouns, and use verbs to say who does what. Reduce `~에 대해` and `~를 통해` only when a more direct particle or verb conveys the same meaning.
- **Write concrete content instead of empty words.** Remove unsupported praise or exaggeration, introductions and conclusions that add no content, and coinages or metaphors whose meaning is hard to grasp. Do not invent facts or examples to make content more concrete.
- **Keep the relations between sentences.** Split long sentences along condition, action, and result, but keep needed connectives and commas. Do not mix registers to vary the rhythm.
- **Fix terms.** Do not swap a term for a synonym just to avoid repetition (for canvas, frame, chip, inspector, and so on, use the words in docs/PRODUCT.md and docs/ARCHITECTURE.md).
- **Finally, compare against the original.** Check that shortened or rewritten parts did not change information, conditions, or certainty. Leave sentences that already read naturally as they are.

|---|---|---|
| 변경 사항에 대한 검토를 수행합니다. | 변경 사항을 검토합니다. | 목적어와 동사를 바로 연결 |
| 설정 화면을 통해 언어의 변경이 가능합니다. | 설정 화면에서 언어를 바꿀 수 있습니다. | 명사화를 풀되 가능성은 보존 |
| 저장되어진 값 | 저장된 값 | 이중 피동만 제거 |

## Decision sources

⚠️ **The source of truth for planning decisions is [docs/PRODUCT.md](./docs/PRODUCT.md) (product judgment) and [docs/ARCHITECTURE.md](./docs/ARCHITECTURE.md) (structure, formats, conventions). Anything not in those two is undecided.** Both describe the product as it is now; history (dates, who decided, superseded rules, PoC observations) lives in git. Everything they state is decided, whoever decided it: changing it needs the user's approval.

- [README.md](./README.md) is the public introduction: what Doan is, its status, its features, how to install and build it, and a short background. It summarizes; **do not cite README content as a decision** — cite PRODUCT or ARCHITECTURE.
- Read ARCHITECTURE.md for the stack and implementation constraints. It holds only what the code cannot tell: conventions, boundaries and invariants, non-obvious constraints with their reason, and public-contract summaries. Shapes, channel lists, field lists and constants stay in code and schemas; the document points to the file. Keep it that way when promoting a feature. **Do not lay down** package manifests, directory structure, or build settings without a request.
- For product requests outside the scope defined in PRODUCT.md, ask back first, citing that scope, even when asked.
- When a decision is made, rewrite the relevant document (PRODUCT or ARCHITECTURE) so it states the current rule; delete what it replaces rather than marking it superseded. Do not add dates, decider tags or a log entry; the rationale goes in the commit message. Keep a reason in the text only when it is a non-obvious constraint someone would otherwise undo. AGENTS.md and the skills follow the same rule: they state the current procedure, without dates or history. Update AGENTS.md only when the way we work changes.

Real-app checks are separate short probes of the affected behavior.

- `node --test .agents/skills/verify/scripts/verify.test.mjs` — shared gate runner regression tests.

- App setup: `npm --prefix app ci`, then `node -e "require('electron')"` from `app/` once to download the Electron binary (Electron 45 has no postinstall).
- `npm --prefix app run build` — build the app into `app/out/` (`electron-vite build`).
- `npm --prefix app run package` — build the versioned arm64 Go CLI and an unsigned local `app/dist/mac-arm64/Doan.app` with electron-builder.
- Tester build: `/tester-build` builds the signed and notarized `Doan-tester-<date>-<sha>.dmg` from the latest remote develop; steps and tester install notes are in `.agents/skills/tester-build/SKILL.md`.

The sign job waits for the `release` environment approval: the maintainer approves tester builds and dry runs, and only `/release` approves its own release run, because invoking it covers every approval.

- `node app/scripts/verifySignedPackage.mjs <dmg> [<zip>]` — checks a signed, notarized and stapled package (with a zip, also the app inside it and the `latest-mac.yml` beside it); `node app/scripts/checkReleaseVersion.mjs <version>` — checks a release version against existing tags and releases. `codesign -dv <app>` shows whether a package is signed; the local `npm --prefix app run package` app shows `Signature=adhoc`.
- `app/dist/mac-arm64/Doan.app/Contents/MacOS/Doan --user-data-dir=<tmp>` — run the packaged app by hand (Playwright cannot launch it, because its inspector fuse is off: ARCHITECTURE §9 'Fuses'; Playwright probes launch the built `app/` with the `node_modules` Electron). It inherits the shell environment, and so does a copy started with `/usr/bin/open` from a shell (`open` hands the caller's environment to a newly launched app). The `app/dist` copy is outside the Applications folders, so it writes no agent setup. A copy launched directly in `/Applications` or `<HOME>/Applications` sets up agents on every launch: links, the Codex rule and Claude Code's allow rules under that HOME and, when the login shell's `PATH` lacks `~/.local/bin`, `/usr/local/bin/doan`, possibly through a macOS administrator dialog (targets: ARCHITECTURE §7 'Agent setup'). Run such a copy only as `<tmp HOME>/Applications/Doan.app` with `HOME`/`SHELL`/`CLAUDE_CONFIG_DIR`/`CODEX_HOME` isolated as for dev runs and a fake `SHELL` whose `PATH` includes `<tmp HOME>/.local/bin`, so no administrator dialog opens; with the real `HOME`, ask the user first.
- `node --test 'app/runtime/*.test.ts'` — Node tests for reusable runtime isolation, cleanup, native-window and state-preservation support; included in the shared static gate and excluded from app Vitest.
- `node eval/run.ts [--scenarios W1,R2] [--agents claude,codex] [--repeat N] [--round <name>] [--no-judge]` — a real agent-eval round, used by `/agent-eval`. It runs real Claude Code and Codex against the packaged CLI (run `npm --prefix app run package` first), each in a temp repo under `/tmp`, and writes results to `.scratch/agent-eval/<round>/`. It touches real agent state and needs `python3.12`.
- `node eval/run.ts --self-test [--scenarios <ids>]` — runs every scenario's pass and fail fixtures through the runner with a fake agent and judge, no model calls; builds its own CLI with `go build`. Require `self-test PASS` and exit 0.
- `node --test 'eval/**/*.test.ts'` — runner unit tests (quote the glob; `node --test eval/` does not accept a directory).
- `DOAN_CLI=<abs path to doan> npm --prefix app run dev -- -- --user-data-dir=<tmp>` — run the app by hand without touching the real `~/Library/Application Support/doan/`. Also use a temporary `HOME`, a fake `SHELL` that emits controlled probe output, and unset or override `CLAUDE_CONFIG_DIR` / `CODEX_HOME`; userData isolation alone does not protect machine setup targets.
- `go build -o <tmp>/doan ./cli/cmd/doan` — build the CLI for `DOAN_CLI`.
- `DOAN_RUNTIME=<absolute temp userData>/runtime.json <absolute CLI> active --json --repo <absolute temp repo>` — inspect a dev/e2e app without touching the real runtime.

## Workflow (skill lineup)

The source for development skills is `.agents/skills/<name>/SKILL.md` (pipeline adapted from malmoi `.claude/commands/`, without its deploy, DB, and translation stages).

**Verification policy:** until the app is complete, use static/unit/build checks and short real-app probes scoped to the change; there are no screen-specific e2e scripts and no full-suite gate. Keep only reusable runtime isolation/cleanup/state-protection support in `app/runtime/`; put temporary screen probes in `.scratch/`. Do not add a new full-flow suite during feature work. Once the app stabilizes, design new end-to-end scenarios against that app. A later change invalidates only affected evidence; do not restart unrelated runtime checks automatically.

**Real agent sign-ins:** the agent accounts signed in under the developer's real HOME (Claude Code, Codex and the other providers Doan runs) are accounts kept for developing Doan. Any session — lead, conductor or worker — may use them at any time for real-agent checks (real CLI and app-server runs, model turns) without asking, through a copy: clone the sign-in into a temporary, isolated agent home (the provider's credential file, such as Codex's `auth.json`; for a provider that keeps it in the macOS Keychain, a temporary item for that temporary home), run there, and delete the copy, any temporary Keychain item and the temporary home when the check ends, even when it fails. Never run in the real agent home and never change the real agent configuration or Doan's real setup. A clone that refreshes its token can rotate the real session's refresh token and sign it out, so keep such runs short, and tell the user if a real sign-in stops working afterwards. Launching the Doan app itself with the real HOME still follows 'Commands'.

**Recommended flow**: `/feature` → (`/feature-review`) → `/tdd` → `/implement` → (`/runtime-test`) → `/code-review` → `/refactor` → (`/postmortem`) → `/verify` → push. A small change goes all the way to push with `/deliver` alone; a large batch to split across several workers runs through `/orchestrate`.

- **Terms**: a **feature** is a logical division of the MVP feature list (PRODUCT §5). One feature = one `/feature` run = one `docs/features/<slug>/`. A **batch** is a bundle of work that `/orchestrate` hands to a worker when implementing one feature. One feature can be implemented by several workers and several batches. A **parent feature** is a hub `docs/features/<slug>/` that defines child features, holds their shared decisions and research, and lists them in its `tasks.md`; each child is an ordinary feature with its own `/feature` run and directory. A parent is never run through `/deliver` or `/orchestrate`, its edits are harness/docs changes made in conversation, and only its last task deletes it, after every child has merged.
- **Plans go in feature documents; the harness documents follow implementation.** A planned change is written only in its `docs/features/<slug>/`. PRODUCT, ARCHITECTURE and DESIGN describe what exists, and are updated to the new current state once the change is implemented — that is the default last step of every feature. An idea with no feature yet goes in `docs/BACKLOG.md`, not in a plan.
- `/feature` is the starting point of a feature. Its output goes in `docs/features/<slug>/` (spec·design·tasks); when the feature is done, promote the conclusions to PRODUCT.md (product judgment) and ARCHITECTURE.md (structure, formats, conventions) and delete that directory.
- `/code-review` refers to this repo's skill. It is different from Claude Code's built-in `code-review`.
- `/audit` reviews the whole codebase against decisions, contracts, boundaries, lifecycles and postmortem prevention rules. Reports findings and coverage only; `/code-review` remains the changed-code review.
- `/audit-loop [rounds]`, invoked by the user in the lead session, repeats `/audit` and fixes what it finds without asking the user: findings whose fix changes no decided policy and no usability go to `/deliver` and `/orchestrate` conductors and merge into develop, the rest go to BACKLOG or stay in the report. The skill holds the decision boundary and round steps.
- `/sec-audit` audits the whole codebase for security along Doan's trust boundaries (SECURITY.md 'Scope'), refuting every candidate before it reports it. The repository is public, so its report stays local in `.scratch/sec-audit/`, and public text about a fix (PRs, commits, comments, postmortem) names the defect class and the fix, never an exploit path. `/sec-audit-loop [rounds]` repeats it and fixes findings like `/audit-loop`, keeping user decisions in the local report instead of BACKLOG.
- `/doc-check` checks docs against code and code against docs, and corrects verified factual documentation drift. Decision conflicts require a decision; POSTMORTEM and USABILITY-EVAL history is preserved.
- `/ux-audit` compares wording, states, actions, recovery and tokens across implemented screens. Reports only; `/design-sync` remains the first-implementation measurement workflow.
- `/audit`, `/sec-audit`, `/ux-audit` and `/doc-check` use specialist subagents and a lead that verifies evidence and completes coverage before reporting; partial coverage is a checkpoint, not a finished audit. Each skill holds its concurrency, model-family and edit-ownership rules.
- `/audit` and `/ux-audit` write Korean consolidated reports to `docs/features/audit-YYMMDD/report.md` and `docs/features/ux-audit-YYMMDD/report.md` (e.g. `audit-261025`). Record the full execution date inside the report. These directories hold audit results, not `/feature` plans; do not create placeholder planning files or apply automatic feature-completion deletion. Raw evidence stays in `.scratch/`.
- `/verify` runs the shared static/unit/build command above; include `--eval` for eval runner changes. Docs-only changes use targeted checks.
- `/runtime-test` launches the isolated real app, with `app/runtime/` support, for a short probe of the changed behavior only. Run it when app behavior changes, before `/code-review`. Reuse unaffected evidence and coordinate GUI probes across workers.
- **Design presets in development skills**: design work in this repo's skills (`/feature` UI flows, `/design-draft`, `/design-sync` fixes, `/ux-audit` reviews) checks Doan's own presets with the installed `doan design-skill --json` and reads only the ones the task needs (`doan design-skill <id> --json`), without waiting for the user to name them. The skill's own rules and the feature documents win over a preset; the report names the presets read.
- `/design-draft` draws a feature's UI draft canvas in `.doan/canvases/` from its feature documents and checks it with `doan check` / `doan ls`. Run it after `/feature-review` and before `/tdd`, on whichever branch is checked out; either runtime may draw, and the user confirms the draft in the app before implementation. Exception: a redesign feature (a child of a parent feature, or a standalone follow-up, whose `design.md` asks for a new look of a screen already on develop) may draw a new draft file for that screen; it never edits the existing draft.
- `/design-sync` compares an app screen's first implementation with its draft canvas in `.doan/canvases/` by computed style in the real app. Run it inside a `/deliver` or `/orchestrate` branch; the draft is the source of truth only until that screen's first implementation is integrated on develop. Exception: a redesign feature's new draft is the source of truth for that screen until the feature's branch is merged.
- `/agent-eval` runs the fixed scenarios in `eval/` with real Claude Code and Codex and records rounds in `docs/usability-eval/rounds-<YYYY-MM>.md` and usability issues in `docs/USABILITY-EVAL.md`. Run it when a PR changes the guide, CLI output or messages, `doan check` rules or the skill stub, before a feature's last integration, and after an agent version change. Fixes go through `/deliver` or `/feature`.
- If you fixed a regression or bug, run `/postmortem`. `/feature`, `/feature-review`, `/tdd`, `/implement`, `/refactor` and `/code-review` grep the month files under `docs/postmortem/` before starting.
- **Lead and conductors**: the user invokes `/deliver`, `/orchestrate` and `/chain` in a session on the develop checkout, the **lead**, so that many conductors can run and open PRs in parallel while one session orders their merges and resolves their contention. The lead does not run the work itself: it creates the `<type>/<slug>` branch from the latest `origin/develop` ('Commit conventions') in a new Orca worktree, starts a **conductor** session there with a brief, and waits. The conductor runs the skill on that branch and ends with a push + a PR against develop; it never merges. The lead reviews the PR, merges it into develop with a merge commit, and removes the conductor's worktree (the branch stays). Once all its conductors' PRs have merged, the lead itself verifies, in the develop checkout, every item their PRs left unverified. The procedure is `/deliver` 'Lead' (`.agents/skills/deliver/lead.md`). The lead still makes harness and docs changes itself, committed and pushed on develop ('Commit conventions'). A small extra change the user gives a conductor directly goes on that conductor's branch and into its PR. Exception: `/deliver` on a `hotfix/<slug>` branch runs in that checkout, keeps the branch and opens its PR against main, for `/release` to merge.
- `/release <version>` (or `/release hotfix <slug>`) is invoked only by the user, never by the model, another skill, a chain or a worker. Together with `/publish` it is the only way `main` changes. The invocation is the user's approval for every step of `.agents/skills/release/SKILL.md`: the version bump, the PR that merges develop (or the hotfix branch) into main, the `v<version>` tag, approving its own release run, and publishing the draft Release.
- `/publish <slug> [<commit>...]` is invoked only by the user. It brings chosen public-facing documentation commits (`README.md`, `docs/` except `docs/features/`, issue and PR templates, `web/`) from develop to main through a PR, without a version, tag or release (steps: `.agents/skills/publish/SKILL.md`). App, CLI, workflow and build changes reach main only through `/release`.
- **Chains**: `/chain` links several features into `/orchestrate` runs, in series unless the files they change (code, tests, schemas and fixtures, skills, drafts) do not overlap (shared docs do not count), in which case those links run in parallel. Each link is an `/orchestrate` conductor that the lead starts from the latest develop and whose PR it reviews and merges in link order, as above; the chain skill §3 holds the rules for both. The chain file `docs/features/chain-<YYMMDD>-<n>/chain.md` is the source for order and standing permissions; only the lead writes it, and it is deleted after the last merge.

## Commit conventions

- **Branches**: `main` (the release record), `develop` (integration), `<type>/<slug>` and `hotfix/<slug>`. GitHub's default branch stays `main`, so always name `develop` as the base (`gh pr create --base develop`, `--base-branch` in Orca).
  - **Releases**: `main` changes only when the user invokes `/release` or `/publish`; no other commit, merge or push goes to `main`, and they are the only skills that merge into it. `/publish` carries only public-facing documentation and the landing page. A `hotfix/<slug>` branch comes from the last stable release tag, takes only its fix, and reaches `main` and then `develop` through `/release`.
  - **Code changes** are requested by the user via `/deliver`, `/orchestrate` or `/chain` in the lead session ('Workflow' Lead and conductors). The lead creates the `<type>/<slug>` branch from develop for a conductor, the conductor ends with a push of that branch + a PR against develop, and the lead merges it with a merge commit; `/deliver` on a `hotfix/<slug>` branch opens its PR against main instead, for `/release` to merge. Even a docs-only change takes the same path if it goes through these skills.
  - **Branch names**: `<type>` is the Conventional Commit type of the change's main commit (`feat`, `fix`, `docs`, `chore`, `refactor`), so a bug fix is `fix/<slug>` and a docs-only change `docs/<slug>`. `/orchestrate` integration branches are always `feat/<slug>`.
  - **Harness and docs changes** (AGENTS.md · skills · hooks · PRODUCT.md, etc.) are fixed directly during the conversation. Commit them on whichever branch is checked out — do not switch branches just for a harness change, except from `main`: never commit on `main`; switch to develop first. On develop, push straight to develop; on a `<type>/<slug>` branch, they reach develop with its PR; on a `hotfix/<slug>` branch, commit only that fix.
- **Commit messages are in English**, Conventional Commits (`feat:` `fix:` `docs:` `docs(scope):` `chore:`).
- Split commits per document.
- **Comments (code and CSS): English, short, and only what the code cannot say** (outside contributors must be able to read them; every agent that opens the file pays for them).
  - Write one only for a non-obvious constraint, invariant or pitfall someone would otherwise break: why this value or order, what depends on this name, which platform quirk it works around. One or two lines; a longer reason goes in ARCHITECTURE, and the comment points to that section.
  - Never: the "what" the code already says; history or narrative (drafts, frames, rounds, measurements, who chose what, what it used to do); `docs/features/` documents (their sections, decision or task ids, or slugs — they are deleted once promoted); a description of the screen.
  - When you change code, shorten or remove stale and over-long comments in the lines you touch.
- Put one-off experiment files in `.scratch/` (gitignored).
- Remove a local worktree as soon as its work is merged, handed off or abandoned; check `git status` in it first and ask before discarding uncommitted work.
- **Keep implementation branches.** A branch used for implementation (a PR branch or a worker's batch branch) stays, local and remote, after its merge until the user says to delete it. Never pass `--delete-branch` to `orca worktree rm`; an older Orca host may still delete a merged checked-out branch, so note the branch tip before removing the worktree and recreate it (`git branch <name> <sha>`) if it is gone.
- PoC experiment code also goes in `.scratch/`. `.scratch/` is not committed, so write what the PoC established as current facts in PRODUCT or ARCHITECTURE, and the observations (pass/fail, measurements, date) in the commit message or the feature documents.
- Commits made in a Codex session end with `Co-Authored-By: Codex <noreply@openai.com>` as the last line. This is to tell from the history which runtime made a commit (the same rule as malmoi `.agents/PREAMBLE.md`).

## Runtime differences

- **⚠️ Do not create `CLAUDE.md` at the root.** Claude Code (v2.1.277+) reads `AGENTS.md` only when there is no `CLAUDE.md` in the working directory or anywhere above it. If a `CLAUDE.md` appears, this file is ignored without warning. If Claude Code-only rules are truly needed, add a `CLAUDE.md` whose first line is `@AGENTS.md`.
- **Bedrock · Vertex · Foundry sessions do not read `AGENTS.md`.** If you need to work through those paths, use the `@AGENTS.md` import above.
- **The response-style re-injection hook is Claude Code only** (`.claude/settings.json`). Codex sessions keep only the response style at the top of this file, so maintain it even in long sessions.
- **Worker model boundary** — if the session calling workers or subagents is Codex, call only Codex models; if it is Claude Code, call only Claude models. Crossing model families is allowed only with the user's explicit permission. Standing exception: `/agent-eval` always runs both Claude Code and Codex and has the other family judge each run.
- **Skill locations differ** — Claude Code looks in `.claude/`, Codex in `.agents/skills/`. The skills used to develop this repo have their source in `.agents/skills/<name>/SKILL.md`, and `.claude/skills/<name>` is a symlink pointing to that directory. When you create a new skill, create the link too. These are different from the doan skill that the product installs into the user's agent (ARCHITECTURE §6 'Skills': `SKILL.md` stub + `doan skill`).
