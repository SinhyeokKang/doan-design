### 2026-11-01 — A frame drawer list closed by a disabled trigger reopened by itself

- **Area**: `app/src/renderer/CanvasHeader.tsx` (`FrameDrawer`, `ZoomControl`, `useMenuFocus`), `app/src/renderer/canvasFocus.ts` (`menuCloseNow`).
- **Symptom**: with the frame drawer's list open, the canvas lost its board width (the drawer turned disabled, "Frames") and the list disappeared. When the width came back on the same canvas, the list popped open again with nobody touching it. Seen in the buzz-canvas BR1 runtime probe before merge, not on main.
- **Root cause**: the menus were shown as `open && view.enabled`, a derived value, while the person's `open` state stayed `true` underneath. Hiding a popup by masking its state with an availability flag keeps the stale intent, so the popup returns as soon as the flag does. Static markup tests render the closed trigger only and never run an open → disabled → enabled sequence.
- **Net**: caught by the BR1 `/code-review` reading the open-state logic, then pinned by a runtime probe step (width removed and restored with the list open): red on the pre-fix build (`.scratch/runtime-test/buzz-canvas/BR1/run6-red.log`, list `open: true` after recovery), green after `77b66249` (`run7.log`). Missed by the implementation's unit and markup tests.
- **Prevention**: a popup whose trigger becomes disabled closes its own state (`menuCloseNow` returns `close` for an open, disabled menu; `canvasFocus.test.ts`), and focus goes to the canvas region. Do not express "unavailable" as `open && enabled` alone. Keep the probe's restore step. Grep: `grep -rnE 'open=\{[a-zA-Z.]+ && |const shown = open && ' app/src/renderer --include='*.tsx'` (on 2026-11-01 it finds only the two canvas header menus, both now closing through `menuCloseNow`).

### 2026-11-01 — A failed Antigravity sign-in left no evidence of why

- **Area**: `app/src/main/agentAuth/manager.ts` (`acpSignIn`, `acpStatus`, `acpExec`, `ServerError`, `serverEvent`).
- **Symptom**: in a dev app's first-run Agent step, Antigravity sign-in failed twice in a row ("Sign-in to Antigravity keeps failing") while four other providers signed in. The profile afterwards held `settings.json` (written only after a successful `authenticate`) but no `acp_token.json`, no vault image and no metadata entry; the dev log held no `doan:` line about it. Two later real sign-ins with the same Google account, in copies of that profile through the window API and through the same UI, and a retry in the original profile all succeeded, so the cause was not found.
- **Root cause**: diagnosis was impossible, not the failure itself: a failed ACP sign-in or status check kept its reason only in the in-memory `Failure` detail, which never reaches a window or the log, and `acpExec` discarded the server's stderr. The file evidence also misled: on its identity/onboarding rejection path (a `ValueError` from `get_access_token`, handled by `_sign_out_after_identity_failure`: onboarding failure, its 300 s login timeout, denied consent) the 1.3.0 server deletes `acp_token.json` itself and keeps `settings.json`, so a missing token does not show that Doan lost it. Hypothesis, not reproduced: its loopback listener answers exactly one request, so a second visit to the link (a second tab, "Open again") could end the flow.
- **Net**: reported by the user; the profile's file times were the only evidence, and they fit no single Doan code path.
- **Prevention**: a failed ACP sign-in, a status check that ends without a login, and a failed server logout now log in Doan's own categories only: how the exchange ended and the recognized auth-path server events, reworded; the RPC error text, payloads and every other server line are withheld (tests in `manager.test.ts` 'ACP sign-in diagnostics'; a first version that printed filtered server text leaked RPC `data.message` and structured stderr, review RBG). A status check stopped by its time limit says so. Never log a provider's message text, even filtered: provider errors embed whole replies. When a provider login fails, read that log before reading profile files, and read the provider's own source for what deletes its credentials before blaming Doan's scrub. Other providers' login failures still keep their output only in `Failure` detail. Grep: `grep -n 'console.error' app/src/main/agentAuth/manager.ts`.
- **Follow-up (2026-11-01, cause found)**: the user's machine was under heavy load (load average ~117 on 8 cores). Reproduced in a copy of the profile at a load of ~120-190: the server took about 30 s to answer `initialize`, the approved sign-in's `authenticate` returned `{}`, and the status check that follows it counted the server's start in its 20 s limit, was stopped before the server printed anything (`status check failed: the server was stopped after 20000 ms without an answer`), and the failed sign-in scrubbed the new token, leaving the reported file state. At ~270 a first attempt failed earlier, in `initialize`'s own 60 s limit. Fix: `acpExec` sends and checks `initialize` itself, bounded by `ACP_OPEN_MS` (60 s, as for sign-in and conversation runs), and starts the caller's limit at its answer; under a load of ~227 a status server then lived 36 s and the sign-in succeeded. Prevention: a time limit around a provider process must not include the process's start unless the start is what it bounds; measure a provider's start under load (`uptime` plus spawn-to-first-answer) before choosing a limit. Grep: `grep -n 'Timeout\|_MS = ' app/src/main/agentAuth/manager.ts app/src/main/conversation/acpRunner.ts`.

### 2026-10-31 — A linked default directory served its unconfigured target

- **Area**: `cli/internal/repo/scope.go` (`Scope`, `defaultServeDirs`), `cli/internal/repo/files.go` (`Canvases`), `cli/internal/repo/layout_test.go`.
- **Symptom**: with an empty `serve` config, a symlink `.doan/canvases`, `.doan/ds` or `.doan/assets` pointing at an internal directory such as `src` (or a symlinked `.doan`) put the link's real target in the `doan ls` scope, so the app served that whole subtree, source files included, without any config entry. Listing skipped the same link, so no canvas appeared and nothing looked wrong.
- **Root cause**: listing and scope applied different symlink policies to the same default directories. `Canvases` lstat-checks `.doan` and each default directory and skips links; `Scope` sent defaults through the same `Resolve` path as explicit `serve` entries, which follows links on purpose. The metadata filter only rejects the repo root, `.doan` metadata and their ancestors, so an ordinary internal target passed. The relocated-metadata layout test even pinned the linked-`.doan` default as served.
- **Net**: caught by the independent review of the design-system-canvases T2 batch (R-BC), from the batch handoff's note that a linked `.doan/ds` still served `elsewhere`. Missed by the T2 tests, which asserted only the empty canvas list for a linked `.doan/ds` and never the scope, and by earlier batches, where `.doan/canvases` and `.doan/assets` already had the defect.
- **Prevention**: default directories are served only when neither `.doan` nor the directory itself is a symlink; explicit `serve` entries keep following links. Any test of a linked default directory asserts `scope` as well as `canvases` (`TestScopeSkipsLinkedDefaultDirectory`, `TestScopeSkipsDefaultsUnderLinkedMetadata`). When adding a default directory, add it to the lstat-checked lists in both `files.go` and `scope.go`. Grep: `grep -rnE '"\.doan/(canvases|ds|assets)"' cli/internal/repo app/src/main`.

### 2026-10-30 — Packaged-app probes failed for reasons of their own: keychain, signature identity and focus

- **Area**: `.scratch/runtime-test/buzz-settings/human*.mjs`, `r2.mjs`; `app/runtime/environment.ts` (`isolatedEnv`); electron-builder output `app/dist/mac-arm64/Doan.app`.
- **Symptom**: with a real account and real notifications in the packaged app, (1) Codex finished OAuth in the browser but said "credentials could not be saved locally"; (2) the test notification failed at once ("Doan isn't allowed…") though System Settings showed a 'doan' row allowed, and no permission prompt appeared; (3) Playwright-driven pages never received window focus or blur, so focus re-reads looked broken; (4) a banner click launched other registered copies of the app without isolation: first the P1 PoC (which created the real `~/Library/Application Support/doan-notify-poc`), then, once that was unregistered, an old build in another checkout, which created the real `~/Library/Application Support/doan` (both deleted after the run; nothing else changed). A probe also reported a notification PASS from "the window came back" alone.
- **Root cause**: (1) an isolated `HOME` has no `~/Library/Keychains`, so `codex` (keyring store) and Electron `safeStorage` find no default keychain. (2) The allowed record belonged to the P1 PoC copy, an ad-hoc build re-signed as `design.doan.app`; electron-builder with `identity: null` leaves Electron's ad-hoc signature (identifier `Electron`, another cdhash), which macOS refuses silently. Many LaunchServices registrations of `design.doan.app` (old worktree builds) also let a click open another copy. (3) Playwright enables focus emulation on the pages it drives. (4) The PASS checked a side effect, not the event.
- **Net**: caught because the user watched the browser and the banner; missed by the probe's own assertions, which looked only at window state.
- **Prevention**: for a real sign-in, link `<temp HOME>/Library/Keychains` to the real folder (approved real-state change; delete the provider's keyring item and `<App> Safe Storage` afterwards and verify). For notifications, launch through LaunchServices (`open -n … --args --remote-debugging-port --inspect`) a temp copy re-signed with `codesign --force --deep --sign -` (identifier from Info.plist), count `Notification` events in main over the inspector, and `lsregister -u` the copy at the end. Before a notification probe, `lsregister -dump` every registration of `design.doan.app` and `lsregister -u` the existing copies that are not the build under test (a banner click opens whichever copy LaunchServices picks, with the real HOME), and keep every `~/Library/Application Support/doan*` in the real-state check (`.scratch/design-sync/buzz-settings/lib.mjs` `REAL_USERDATA`). Turn focus emulation off (`Emulation.setFocusEmulationEnabled {enabled:false}`) and focus Doan before a Finder round trip. Pass only on the event itself (`show`, `click`), never on window visibility. Grep: `grep -rn 'isolatedEnv\|_electron.launch' .scratch/runtime-test` for probes that need these.

### 2026-10-30 — A renderer import of a main module left the built app's window blank

- **Area**: `app/src/renderer/SettingsAbout.tsx`, `app/src/main/about.ts` (split into `aboutView.ts`), `app/src/main/conversation/sessions.ts` (`MINIMUM_VERSIONS` moved to `minimumVersions.ts`), `app/src/formats/validate.ts`.
- **Symptom**: the production build opened an empty window: `#root` stayed empty, the console showed "Error compiling schema … Evaluating a string as JavaScript violates the following Content Security Policy directive". Every page, not only Settings, was unusable.
- **Root cause**: Settings > About imported `aboutView` by value from `main/about.ts`. That module also held main's readers and imported `designSkills.ts` and `conversation/sessions.ts`, which import `formats/validate.ts`; ajv compiles its schemas with `new Function` when that module loads. The renderer's CSP has no `'unsafe-eval'`, so the bundle threw before React mounted. Nothing marks a main module as renderer-safe: a value import of a type file and of a reader look the same, and one helper added to a "pure" main module can pull the validators in later.
- **Net**: caught by the first real-app launch of the integrated branch (BS `/runtime-test`). Missed by four batches and their reviews: Vitest runs in jsdom without the CSP, `tsc` and `electron-vite build` accept the bundle, and no batch launched the built app.
- **Prevention**: `app/src/renderer/rendererImports.test.ts` walks the value-import closure of every renderer module entry (`index.html`'s module script) and fails if it reaches `src/formats/validate.ts`, `ajv` or a Node module, printing the import chain. A renderer value import of a main module must come from a module that imports only types or other such modules (`aboutView.ts`, `agentAuth/types.ts`). Grep: `grep -rn 'from "\.\./main/' app/src/renderer | grep -v '\.test\.' | grep -v 'import type'` lists the value imports to keep that way; launch the built app once after a batch that adds one.

### 2026-10-30 — Timing tests failed under machine load because their waits matched or beat the test limit

- **Area**: `app/vitest.config.ts`, `app/src/main/shell.test.ts`, `watch.test.ts`, `agentAuth/manager.test.ts`, `app/src/renderer/quickOpen.test.ts`, `app/runtime/harness.test.ts`.
- **Symptom**: at load averages of 11–30 (browser, design tool and Orca running), the shared verify gate failed in two to five tests per run, a different set each time, on main as well as on branches. The same tests passed alone.
- **Root cause**: main-process tests wait up to 5 s with `vi.waitFor` for spawned CLI reads and file watchers, and Vitest's default test limit is also 5 s, so any slowdown ended the test before its own wait. Seven workers on eight cores each spawned children and starved each other. A sign-in test set a 40 ms link timeout below the 100 ms link poll; the harness fixture's 3 s outer kill guard was shorter than starting node and loading `harness.ts` under load; the Quick Open budget judged a single wall-clock run.
- **Net**: alternating full-suite runs: 11 failures in 4 runs before, 5 after the limit and worker changes (at higher load); the remaining Quick Open failure is judged by the fastest of three runs.
- **Prevention**: keep a test's limit well above every wait inside it; keep component timeouts above the poll that feeds them; judge wall-clock budgets by the fastest of several runs; treat outer kill timers as hang guards with generous values. When the gate fails only under load, compare against main before blaming the change.
- **Follow-up (watch.test.ts)**: "a served directory at the root that is replaced" once missed `reread` at load 3.6. 300+ isolated probes (with CPU load, re-arming watchers mid-burst, and a concurrent canvas edit) never lost the root event; the likely cause is fseventsd splitting one burst into batches more than the 300 ms quiet window apart during the full suite. The product's refresher still runs again for the late event. `expectChange` now waits for the expected flags before settling; a mutation that drops the root `reread` still fails it.

### 2026-10-30 — Renaming the bundle to Doan left "About/Hide/Quit doan" in the menu, and the window title was never Doan Design

- **Area**: `app/src/main/index.ts` (app menu, main `BrowserWindow`), `app/src/renderer/index.html` (`<title>`), `app/package.json` (`productName`).
- **Symptom**: with `productName` `Doan` and `app.setName("doan")` kept for userData, an Electron 45 probe listed the app menu roles as "About doan", "Hide doan", "Quit doan". ### 2026-10-29 — A cancelled replacement sign-in lost a working connection, and Codex's credential with it

- **Area**: `app/src/main/agentAuth/manager.ts` (`signIn`, `signInFlow`, `discard`, `retire`, `profileOf`), `state.ts` (`settled`, failed `signedIn`), `storage.ts` (`seal`, `storeSealed`, `profileDir`), `providers.ts` (`loginClears`).
- **Symptom**: in the packaged app with all five providers connected, `doan onboarding sign-in --provider <p>` followed by `onboarding cancel` left each provider `unverified`; Copilot then stayed "not checked" until a paid Retry. Codex's next check reported `reauthRequired` ("connection expired") and its Keychain item `Codex Auth|cli|…` was gone (batch V, 2026-10-29).
- **Root cause**: three layers. (1) The state machine unverified every connection whose replacement was cancelled or failed, on the assumption that the replacement "may have overwritten the previous login", without asking whether it did. (2) For vault providers the new login was sealed into the vault before the last cancellation point, so a cancel during encryption really did leave the new credential under the old connection. (3) Codex 0.164.0 `codex login` calls `clear_existing_auth_before_login` → `logout_with_revoke` (`codex-rs/cli/src/login.rs`, `login/src/auth/manager.rs`) before its login server starts: any replacement in the stored connection's `CODEX_HOME` revoked and deleted the working login the moment it spawned, whatever the user did next. Claude 2.1.312 `auth login` stores only after the token exchange and restores on a refused login, so it never had this problem.
- **Net**: unit tests drove fake processes that never touch the profile on start, and the replacement tests pinned "unverified" as the intended outcome, so neither the demotion nor Codex's pre-login logout was visible until a real-provider probe cancelled replacements on connected accounts.
- **Fix**: each sign-in tracks whether it may have changed the stored connection's login (`touch.live`); `settled` and failed `signedIn` carry `kept` and keep the connection's verified state when it is true. Vault providers seal the new login in memory and remove the working copy before the commit, then store the vault with the metadata, restoring the previous vault if the metadata write fails; nothing that can fail runs after that commit. A provider whose login clears the profile first (`loginClears`, Codex) signs a replacement in to a fresh `profiles/<provider>-<id>/`; on success the connection moves there and the old profile is logged out and removed, on cancel or failure only the staging profile is (D22, 2026-10-29). A staged or replaced profile is recorded in `cleanup.json` before it exists or stops being live, is removed only after its logout exits 0, and a later start retries what is left, never the stored connection's profile.
- **Review round (2026-10-29)**: the first fix still scrubbed the working copy after the commit, so a failed scrub returned the old verified connection over the new vault and metadata; and the staging cleanup removed the profile even when its logout failed, with no record to retry after a crash. A commit boundary only holds when every fallible step is on one side of it, and a credential directory may only go once the provider confirms its logout. A second review found that the startup retry treated a signed-out provider's own profile name as live and skipped it forever, and that a failed record write still created and logged out an unrecorded staging profile: "live" must mean referenced by stored metadata, and a profile that could not be recorded must not be created.
- **Prevention**: before trusting a provider login in a profile that already holds a connection, read what the login does before it prints its link (logout, revoke, store reset) at the pinned version, and add the finding to `providers.ts`. Run `rg -n 'loginClears: true' app/src/main/agentAuth/providers.ts` when a provider minimum rises (performed 2026-10-29: Codex only). In `signInFlow`, keep every fallible step before the metadata write; check with `rg -n 'writeMetadata' app/src/main/agentAuth/manager.ts` that only non-throwing record cleanup follows it (performed 2026-10-29). Real-provider probes of sign-in must include cancelling a replacement on a connected, verified account and checking the stored credential afterwards.

### 2026-10-28 — A send right after turn.done was refused as busy until the previous process group was gone

- **Area**: `app/src/main/conversation/service.ts` (`send`, `previousExit`), `ownership.ts`.
- **Symptom**: in the packaged app, a send issued on `turn.done` returned `busy`: Claude for 2.1-5.0 s, Copilot for about 0.5 s, Cursor and Antigravity only for the first millisecond (D1, 2026-10-28). The dev run missed it because its next send came 6 s later.
- **Root cause**: a per-turn process keeps the conversation's reservation until `process_exited` (group gone), by design, so that two processes never share a session; but `send` treated a held reservation after a finished turn the same as a running turn. Fixing it by waiting exposed a second trap: if the wait timed out and `send` went on to replace the live entry before `reserve` threw, the old process's exit callback (`this.live.get(id) === live`) no longer matched and its reservation was never released.
- **Net**: caught by the D1 busy-window probe (`busyjs.txt`: send on `turn.done`, retry every 50 ms). Unit tests had always released the reservation by calling the exit callback before the next send. ### 2026-10-21 — Filesystem APIs did not match "missing" and "same file" as the product means them

- **Area**: `cli/internal/repo/resolve.go`, `find.go`; `cli/internal/cli/init.go`
- **Symptom**: a canvas href such as `tokens.css/x.css` or `%00` made `doan check` exit 1 (`internal_error`) instead of reporting `local_css_not_found`; an ancestor `.doan` regular file stopped repo discovery; `DESIGN/A.CSS` and `design/a.css` became two keys on macOS (false `css_not_served`, duplicate findings); `doan init` followed a dangling `.doan/config.json` symlink and created a file outside the repo.
- **Root cause**: `os.IsNotExist` covers only `ENOENT`, while `ENOTDIR`, `EINVAL`, `ENAMETOOLONG` and Go's unwrapped "EvalSymlinks: too many links" also mean "no such file" for content-derived paths; `filepath.EvalSymlinks` resolves links but keeps the caller's letter case on case-insensitive filesystems; "missing" is safe for reading but not for writing, because `os.WriteFile` follows a dangling symlink.
- **Net**: caught by the independent reviews of batches A and D with concrete inputs, and by D's self-review for the write path. Missed by the planned case lists, which only had `ENOENT`-shaped inputs and one spelling per file.
- **Prevention**: for every path that comes from canvas or config content, test `ENOTDIR`, a NUL byte, an over-long name, a symlink loop, a different letter case, and a dangling symlink at each write target. Grep: `grep -rnE 'IsNotExist|EvalSymlinks|os\.WriteFile' cli app/src`.
- **Recurrence (2026-10-21, app-shell)**: `doan ls` `result.root` kept the caller's letter case from `--repo` or `$PWD` (`repo.Find` used `EvalSymlinks` alone), so one repo could be stored twice by the app and every served path would miss `relInside`. Caught by the batch B1 independent review; fixed by passing the root through `diskSpelling`. `doan init`'s `result.repo` (`init.go`) still keeps the caller's spelling.
- **Recurrence (2026-10-24, onboard)**: in app main, JS `realpathSync` kept the caller's letter case on this macOS volume while `realpathSync.native` returns the on-disk spelling, so a same-file link written with another case was not recognized as ours. Caught by the G review; fixed by using native realpath for setup identities, with a case-alias regression (an `ELOOP` link stays foreign). Grep: `rg -n 'realpathSync\(' app/src/main --glob '!*.test.ts'` should find no caller (2026-10-24: only `realpathSync.native` is used).

- **Recurrence (2026-10-28, unified project layout)**: moving canvases below `.doan/` introduced a new symlink ancestor. Checking only `canvases/` with lstat let discovery traverse a linked `.doan/` into another directory. A red regression now covers that ancestor; discovery and fixed watchers reject it. Scope filtering also resolves the metadata directory before excluding it and its ancestors, so an internal metadata alias cannot serve settings or comments. A relocated-metadata scope test failed before that filter. Searched `rg -n 'Lstat|lstatSync' cli/internal/repo/files.go app/src/main/watch.ts`; both new traversal paths check the metadata ancestor.

### 2026-10-21 — An HTML parser fed from memory can still fail, and dropping the error looks like a missing meta

- **Area**: `cli/internal/canvas/canvas.go` (`Parse`)
- **Symptom**: a canvas nested deeper than 512 elements parsed to an empty model, which would have produced `missing_canvas_id` and `missing_width` for a canvas that has both.
- **Root cause**: `golang.org/x/net/html` returns an error when the open-element stack exceeds 512 nodes, even with an infallible `bytes.Reader`; the planned signature had no error because input from memory "cannot fail".
- **Net**: caught by batch B's self-review; no planned case covered parser resource limits. Fixed by returning `(Canvas, error)` and reporting `unparsable_canvas` instead of failing the command.
- **Prevention**: when wrapping a third-party parser, read its error paths before choosing a signature without `error`, and add a resource-limit case (deep nesting, huge input). Grep: `grep -rnE 'html\.Parse|_ = .*Parse' cli`.

### 2026-10-21 — A character device is not necessarily a terminal

- **Area**: `cli/internal/cli/run.go`, `terminal_*.go` (`doan init` prompt)
- **Symptom**: `doan init < /dev/null` asked the token CSS question even though no human can answer.
- **Root cause**: `os.ModeCharDevice` marks any character device, `/dev/null` included, not an interactive terminal; tests injected `Context.Terminal` and a `strings.Reader`, so a real non-terminal device never reached the check.
- **Net**: caught by batch D's self-review, then pinned with a `cli.Run` test on `/dev/null`; the batch D reviewer confirmed the real-terminal path with a pty.
- **Prevention**: decide "interactive" with a terminal ioctl (termios), and test with `/dev/null` and a pipe besides the injected prompt. Grep: `grep -rn 'ModeCharDevice' cli app/src`.

### 2026-10-21 — Sorting file names does not sort the ids derived from them

- **Area**: `cli/internal/cli/read.go` (`doan comments`)
- **Symptom**: comments for canvas `foo-bar` came before `foo`, against the documented sort by canvas id.
- **Root cause**: results were emitted in `os.ReadDir` order of `<id>.jsonl`; `-` (0x2D) sorts before `.` (0x2E), so `foo-bar.jsonl` < `foo.jsonl` while `foo` < `foo-bar`. Every planned test used one id, or ids that sort the same either way.
- **Net**: caught by the batch D independent review running the binary on `foo` and `foo-bar`; missed by single-id tests.
- **Prevention**: sort explicitly on the logical key after deriving it from a file name, and include an id that is a prefix of another (`foo`, `foo-bar`) in ordering tests. Grep: `grep -rn 'ReadDir\|CommentFiles' cli/internal/cli`.

### 2026-10-21 — Local server guarantees lived in comments and echoed constants, not in behavior

- **Area**: `app/src/main/serve/server.ts`, `server.test.ts`
- **Symptom**: the "listens on 127.0.0.1 only" test stayed green with `listen(0, "0.0.0.0")`; a directory swapped for a symlink between the realpath check and `open` served a file outside the repo with 200 (reproduced with a delay); a file growing mid-transfer sent more bytes than `Content-Length` on a keep-alive socket. The code comment claimed the swap could not happen.
- **Root cause**: the server returned its `HOST` constant, so the test compared the constant with itself; `open(realPath)` re-walks the path, so resolving first and opening by name is not atomic; `createReadStream()` reads to EOF, not to the `fstat` size sent in the header.
- **Net**: caught by the batch B3 independent review, which mutated the bind address, widened the race window with a delay, and grew a file during a transfer. Missed by the batch's own 39 server tests, which only exercised static trees.
- **Prevention**: assert observed state (`server.address().address`), and prove each security test with a mutation that must turn it red. Open resolved paths with `O_NOFOLLOW_ANY` (macOS) and cap streamed bodies at the `fstat` size. Grep: `grep -rnE 'host: HOST|open\([^)]*"r"\)|createReadStream\(\)' app/src`.
