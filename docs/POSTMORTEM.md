### 2026-11-11 — The auto-registration restart test read the folder list before it was saved

- **Area**: `app/src/main/shell.test.ts`, "the auto flag survives a restart".
- **Symptom**: release run 42941499765 attempt 1 failed with only the parent in the restarted shell, while the test expected the parent and the auto-registered child; previous local and PR gates passed.
- **Root cause**: `adopted()` waited for `auto-folders.json`, the first write in the serialized save, but the restart also needs the following `folders.json` write. `Shell.dispose()` closes watchers and the server; it does not await that save. Restart could read the old list. Ignoring an orphan mark after an interrupted save is the existing ARCHITECTURE §7 contract, not evidence that loading lost a persisted child.
- **Net**: CI caught the timing window. A controlled filesystem probe held adoption's folder-list rename until the restart read had captured the old list and reproduced the same missing child three times. With the same held rename released when the persistence check reads the list, the corrected test passed. The final test keeps the exact initial loading entries and the loaded auto flag assertions, adding a bounded wait for the exact saved parent-and-child list before disposal; ordinary repeated runs alone did not establish the cause. No production behavior changed.
- **Prevention**: wait for every persisted prerequisite a restart consumes, not the first file in an ordered save or an unrelated disposal promise. Search: `rg -n 'autoSaved\(|survives a restart|shell.dispose\(' app/src/main/shell.test.ts`. The shared `adopted()` helper also serves live-state tests, so keep the additional list barrier in the restart case; the neighboring adoption test already checks the saved list separately. Keep diagnostic probes under `.scratch/`, not in the production persistence API.

### 2026-11-10 — A quick second trackpad swipe on the buddy row did nothing: momentum kept the first gesture open

- **Area**: `app/src/renderer/coverFlow.ts` (wheel input, now `scrollPosition`, `snapTarget`, `WHEEL_QUIET`), `BuddyFlow` in the Buddy step; the rule came from the draft's handler in `.doan/canvases/buddy-choice.html`.
- **Symptom**: on a real trackpad, two swipes in a row moved the row one card; the second swipe registered only after the person moved the cursor first. Unit tests and the synthetic-wheel probe passed.
- **Root cause**: the rule "one card per gesture, a gesture ends after 160 ms without wheel events" assumed a gesture's events stop when the fingers lift. macOS keeps sending momentum wheel events for 1.3–1.7 s after a swipe, and a second swipe started 40–60 ms into that stream, so the quiet gap never came and both swipes were one gesture. Synthetic `mouse.wheel` probes send no momentum, so nothing but a real trackpad could show it.
- **Net**: caught by the person on a real trackpad, then confirmed with a raw wheel log (deltaX and timestamps per event). Missed by unit tests and the Playwright probe, which modelled a gesture as a short burst followed by silence.
- **Prevention**: horizontal scroll that moves discrete items follows the deltas continuously and snaps to the nearest item once events stop, instead of counting gestures; the quiet timer only decides when to snap. Any wheel handler that infers gestures from timing gets a raw-event log from a real trackpad (two quick swipes, a long flick) before it is accepted, and its tests include a recorded momentum tail. Search run: `rg -n "addEventListener\(\"wheel\"|onWheel" app/src -g '!*.test.*'` (2026-11-10: `CanvasController.ts` page-zoom guard and margin wheel, which scroll continuously and count no gestures, and `BuddyPicker.tsx` (the Buddy row, follows deltas and snaps)).

### 2026-11-09 — An agent planted provider settings in its own profile that a later run would execute outside any sandbox

- **Area**: `app/src/main/agentAuth/fence.ts` (`CLAUDE_SETTINGS`, `CODEX_SETTINGS`, `claudeSettingsDirs`, `codexSettingsFiles`, `codexSettingsDirs`, `claudeFenceSettings`, `codexProfileArgs`); tests `fence.test.ts`.
- **Symptom**: the first fence closed userData but left the run's own profile writable. A fenced Claude or Codex agent could then write its profile's `settings.json`, `config.toml`, `hooks.json`, `rules/`, or a skill, subagent, command or plugin there. The next run reads those files, and the next Claude run (with its sandbox on) or Codex run (outside Full access) has no outer fence: hooks, MCP servers and Codex `notify` named there run outside every sandbox. In a probe a Codex `config.toml` MCP server and `notify` read other profiles and `conversations/` even under Doan's permission profile.
- **Root cause**: "the agent's own profile is the provider's own data" treated the profile as data only. It also holds the provider's configuration, and a provider runs its hooks, MCP servers and plugins as separate processes that its command sandbox does not cover. Each review round found one more surface (settings files, then `skills/`, `agents/`, `plugins/`, then Claude `commands/`, the older skill format that takes the same frontmatter).
- **Net**: caught by independent review rounds of the fence; the runtime probes only tested reads and writes of other profiles, so they never tried writing the run's own settings.
- **Prevention**: the fence closes every profile path the provider reads as configuration to writes (outer fence rules, Claude `denyWrite` and `Edit(...)`, Codex `deny` for settings files and `read` for `skills/`, `plugins/`), and keeps them readable where the agent opens skills itself. When a provider gains a configuration file or directory that can name hooks, MCP servers, plugins or commands, add it to `claudeSettingsDirs`, `codexSettingsFiles` or `codexSettingsDirs` with a `fence.test.ts` case, and probe a write to it from a sandboxed command and from the file tool. Search run: `rg -n "claudeSettingsDirs|codexSettingsFiles|codexSettingsDirs" app/src/main -g '!*.test.ts'` (2026-11-09: only `fence.ts`, used by the outer policy, the Claude flag settings and the Codex profile).

### 2026-11-09 — A deny on userData silently beat the allows that reopened the run's own paths

- **Area**: `app/src/main/agentAuth/fence.ts` (`fenceDenied`, `claudeFenceSettings`, `codexProfileArgs`); tests `fence.test.ts` (no `denyWrite` path is the profile or its ancestor; no Codex `deny` on userData or an allowed path's ancestor).
- **Symptom**: with Claude's sandbox on, `denyWrite=<userData>` beat `allowWrite=<profile>`, so Bash could not write its own profile, and a `permissions.deny` `Read(//<userData>/**)` hid the profile and this turn's pasted image from the Read tool. In Codex Ask first an approved escalated `doan handoff` failed with "Cannot read the Doan runtime file": Codex applies a permission profile's `deny` entries to an approved escalated command but not the narrower `read` and `write` entries under them.
- **Root cause**: the outer Seatbelt policy works as "deny the parent, reopen children" because its last matching rule wins. Claude's settings and Codex's permission profiles do not follow that rule: a deny beats every allow, and an escalated Codex command keeps only the deny entries. Carrying the Seatbelt shape over to them looked equivalent and failed without an error.
- **Net**: caught by the real-app check (the sandbox-on Claude turn and the Codex handoff). Missed by the PoC, which checked that decoys were blocked but not that every reopened path was still reachable on every path (sandboxed command, file tool, approved escalation).
- **Prevention**: in provider settings, deny by listed name only: the entries off the way to an allowed path (`fenceDenied`), never userData or an allowed path's ancestor. Any probe of a deny rule checks both directions on each execution path: the decoy is blocked, and the run's own profile, `runtime.json` and attachments are reachable, including through an approved escalation. Search run: `rg -n "denyWrite|denyRead|\"deny\"" app/src/main -g '!*.test.ts'` (2026-11-09: only `fence.ts` builds filesystem denies; the other hits are permission-option kinds).

### 2026-11-09 — A second Seatbelt policy inside Doan's fence failed every command (exit 71)

- **Area**: `app/src/main/agentAuth/fence.ts` (header comment, `codexMechanism`), `app/src/main/conversation/runners.ts` (`openClaude`, `openCodex`), `prepare.ts` (`claudeSandboxEnabled` sources), `service.ts` (`switchCodexServer`).
- **Symptom**: inside `sandbox-exec -p '(version 1)(allow default)'`, an inner `sandbox-exec` with any rule, `codex sandbox -- /usr/bin/true` and every Bash command of Claude Code with its sandbox on exited 71 with `sandbox_apply: Operation not permitted`. One outer fence for every provider would have broken Codex's Ask first, Accept edits and Plan and every Claude turn whose person turned its sandbox on.
- **Root cause**: macOS refuses to apply a second Seatbelt profile with rules to a process that already runs under one. The common nesting check (`sandbox-exec ... sandbox-exec -p '(version 1)(allow default)' /usr/bin/true`) passes because the inner policy has no rule, so it proves nothing.
- **Net**: caught by the nesting PoC before implementation, using an inner policy with one deny rule and each provider's own sandbox command.
- **Prevention**: a provider that sandboxes its own commands never runs inside the outer fence in that mode; it gets Doan's limits as its own settings (Claude's flag-tier settings, Codex permission profiles), and the choice is made per Claude turn and per Codex server mechanism. A misjudged Claude sandbox shows as Bash exit 71, never as an unfenced run. A nesting check always uses an inner policy with at least one rule. Search run: `rg -n "fencedCommand\(" app/src -g '!*.test.ts'` (2026-11-09: `acpRunner.ts`, every mode; `runners.ts` Codex only in Full access and Claude only with its sandbox judged off).

### 2026-11-09 — The canvas panel's agent notice drew at 11px because it carried the inspector's loading-line class

- **Area**: `app/src/renderer/CanvasConversationPanel.tsx` (the drawing and promoted notices), `app/src/renderer/styles.css` (`.canvas-notice`, `.shell-worktree > span`), `app/src/renderer/ProjectOverview.tsx` (worktree menu); tests `CanvasConversationPanel.test.tsx`, `ProjectOverview.test.tsx`.
- **Symptom**: the panel's "A project conversation is drawing this canvas" and "Open the current conversation" notices rendered at 11px with 7/12 padding (86px tall) instead of the shared notice's 14/20 with 12/16 padding (128px). Moving the Overview worktree menu to the toned status chip then stretched the chip to 115px; Home's same menu already stretched it.

### 2026-11-09 — Export inlined the wrong file after a nested self-closing `<template/>`

- **Area**: `cli/internal/export/base.go` (`templateTag`, `firstBaseHref`), `rewrite.go` (`rewriteMarkup`, also walked by `collectUses` in `customurl.go`), `inline.go` (`documentIDs`); tests `template_test.go`, `base_test.go` 'self-closing template opens'.
- **Symptom**: in `<template><template/></template><style>.inert{mask:var(--icon)}</style>…</template>`, the export took the inert `<style>` as a user of `--icon`, so an active `style="--icon:url(icon.svg)"` resolved from the canvas folder and inlined `.doan/canvases/icon.svg` instead of refusing the missing `.doan/assets/icon.svg`. The new `<base href>` check had the same hole one level up: a `<base>` inside `<template/>…</template>` hid the real, folder-moving base, and the export included files the app would not load.
- **Root cause**: the tokenizer walkers each counted `<template>` depth on their own. The HTML parser ignores the self-closing flag on `<template>` and opens one at any depth, but `rewriteMarkup` counted `<template/>` only at top level, `documentIDs` only start tags, and the first `firstBaseHref` only start tags. A walker that leaves a template too early reads inert content as document content, and `collectUses` feeds that into how active `url()`s resolve.
- **Net**: caught by the independent cross-family review of the base batch and its re-review, each with a reproduced canvas. Missed because every template test used `<template>…</template>`, never the self-closing spelling, and the walkers' depth rules were never compared with each other.
- **Prevention**: every tokenizer walker that skips `<template>` content counts depth through `templateTag` (start or self-closing tag opens at any depth, end tag closes when depth > 0). Search run: `rg -n 'NewTokenizer' cli --glob '!*_test.go'` (2026-11-09: `base.go`, `inline.go` and `rewrite.go` use `templateTag`; `assemble.go` `measureOffset` stops at the head and never enters a template; `canvas.go` uses `html.Parse`, which follows the parser). A new walker's tests include `<template/>` at top level and nested.

### 2026-11-09 — `open -g` to a running Doan brought its window over the app in use

- **Area**: `app/src/main/index.ts` (`activate` handler), `app/runtime/windows.ts` (`showMain`); tests `index.test.ts` 'an activate while another app is in front …'.
- **Symptom**: `doan onboarding start` while the app was running but not answering its socket yet sent `open -g`, and the window came forward over the person's app, against PRODUCT §5 item 0 (start keeps the current app in front).
- **Root cause**: Electron emits `activate` for every reopen, including one `open -g` sends without activating the app, and the handler treated `activate` as a Dock click and showed the window. `BrowserWindow.show()` activates the app, so the background launch became a foreground one.
- **Net**: found while building the background reveal and parked in BACKLOG; the unit tests emitted `activate` with `isActive()` mocked true, so they never separated a reopen from a Dock click. A native probe (`open -g` with Finder in front, then eight real HID Dock clicks) showed `activate` with `isActive()` false for `open -g`, and true for every Dock click even when `did-become-active` came after `activate`. The runtime helper `showMain` relied on the old behaviour (it emits `activate` right after `app.show()`), and `app.focus({ steal: true })` does not activate Doan while another app is in front.
- **Prevention**: run `rg -n 'emit\("activate"\)|on\("activate"' app/src app/runtime` (performed 2026-11-09: only the handler in `index.ts`; tests emit it with `isActive` set explicitly). A handler for an OS "bring forward" event must check `app.isActive()` before showing a window; a test or probe that emits `activate` must set the activation state it means, and a probe that has to show the window while another app is in front uses `second-instance` (`showMain`).

### 2026-11-09 — A quietly opened update popover closed when Agent usage moved focus between two places outside it

- **Area**: `app/src/renderer/UpdateHeaderButton.tsx` (`onFocusOutside`); test `UpdateHeaderButton.interaction.test.tsx` "only focus leaving the popover closes it".

- **Prevention**: when wrapping a third-party parser, read its error paths before choosing a signature without `error`, and add a resource-limit case (deep nesting, huge input). Grep: `grep -rnE 'html\.Parse|_ = .*Parse' cli`.

### 2026-10-21 — A character device is not necessarily a terminal

- **Area**: `cli/internal/cli/run.go`, `terminal_*.go` (`doan init` prompt)
- **Symptom**: `doan init < /dev/null` asked the token CSS question even though no human can answer.
- **Root cause**: `os.ModeCharDevice` marks any character device, `/dev/null` included, not an interactive terminal; tests injected `Context.Terminal` and a `strings.Reader`, so a real non-terminal device never reached the check.
- **Net**: caught by batch D's self-review, then pinned with a `cli.Run` test on `/dev/null`; the batch D reviewer confirmed the real-terminal path with a pty.
- **Prevention**: decide "interactive" with a terminal ioctl (termios), and test with `/dev/null` and a pipe besides the injected prompt. Grep: `grep -rn 'ModeCharDevice' cli app/src`.

### 2026-10-21 — Sorting file names does not sort the ids derived from them

- **Area**: `cli/internal/cli/read.go` (`doan comments`)
- **Symptom**: comments for canvas `foo-bar` came before `foo`, against the documented sort by canvas id.
- **Root cause**: results were emitted in `os.ReadDir` order of `<id>.jsonl`; `-` (0x2D) sorts before `.` (0x2E), so `foo-bar.jsonl` < `foo.jsonl` while `foo` < `foo-bar`. Every planned test used one id, or ids that sort the same either way.
- **Net**: caught by the batch D independent review running the binary on `foo` and `foo-bar`; missed by single-id tests.
- **Prevention**: sort explicitly on the logical key after deriving it from a file name, and include an id that is a prefix of another (`foo`, `foo-bar`) in ordering tests. Grep: `grep -rn 'ReadDir\|CommentFiles' cli/internal/cli`.

### 2026-10-21 — Local server guarantees lived in comments and echoed constants, not in behavior

- **Area**: `app/src/main/serve/server.ts`, `server.test.ts`
- **Symptom**: the "listens on 127.0.0.1 only" test stayed green with `listen(0, "0.0.0.0")`; a directory swapped for a symlink between the realpath check and `open` served a file outside the repo with 200 (reproduced with a delay); a file growing mid-transfer sent more bytes than `Content-Length` on a keep-alive socket. The code comment claimed the swap could not happen.
- **Root cause**: the server returned its `HOST` constant, so the test compared the constant with itself; `open(realPath)` re-walks the path, so resolving first and opening by name is not atomic; `createReadStream()` reads to EOF, not to the `fstat` size sent in the header.
- **Net**: caught by the batch B3 independent review, which mutated the bind address, widened the race window with a delay, and grew a file during a transfer. Missed by the batch's own 39 server tests, which only exercised static trees.
- **Prevention**: assert observed state (`server.address().address`), and prove each security test with a mutation that must turn it red. Open resolved paths with `O_NOFOLLOW_ANY` (macOS) and cap streamed bodies at the `fstat` size. Grep: `grep -rnE 'host: HOST|open\([^)]*"r"\)|createReadStream\(\)' app/src`.
