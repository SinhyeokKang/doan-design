# doan-design-skills — spec

작성일: 2026-10-27. 2026-10-29 feature-review 반영. 이번 feature는 백엔드만 구현한다. UI는 `buzz-restyle`의 `buzz-home`(C3)에서 구현한다.

## 1. 목적과 확정 범위

도안으로 디자인하는 에이전트가 디자인 프리셋을 발견하고, 사용자 요청에 맞는 지침을 읽어 작업하도록 돕는다. 도안은 feature별 디자인과 문서 작업을 지원한다. 디자인을 자동으로 종합 평가하거나 해결책을 주도하지 않는다.

2026-10-27 사용자 결정:

- feature 이름은 `doan-design-skills`이다. Impeccable 전체 스킬 셋을 참고하되 도안에 맞는 것만 공개 프리셋으로 제공한다. 중복 별칭은 합치고 원본 전용 실행 기능은 제외한다(2026-10-27 리뷰 결정).
- 최소 기능은 프리셋 제공과 자연어 요청에 적절한 프리셋이 있을 때의 매핑이다.
- 별도 모델로 프롬프트를 재작성하거나 분류하지 않는다. 기존 디자인 에이전트가 짧은 목록에서 고르고 필요한 본문만 읽는다. 적합한 항목이 없으면 일반 요청으로 진행한다.
- 사용자 요청 원문을 보존한다. 자동 검토·추천 시스템이나 대안 비교 UI를 추가하지 않는다.
- 앱 사용자와 외부 에이전트는 같은 지침을 에이전트에게 전달하는 두 진입점이다.
- 이번 구현은 백엔드이다. 앱에서 목록을 발견하고 선택·전송하는 UI와 그 조작 방식은 `buzz-restyle`의 `buzz-home`(C3)이 맡는다(2026-10-29 사용자 결정). 앞서 제안한 선택 후 Send 방식은 확정 결정이 아니다.
- Impeccable 본문을 각색해 CLI에 넣어 배포한다. 원본 LICENSE·NOTICE와 파생 출처 고지를 함께 넣고 변경 사실을 표시한다(2026-10-29 사용자 결정).

범위 게이트: [PRODUCT §1](../../PRODUCT.md#1-problem-2026-10-21)의 문제 3 'Tie to code'에 연결된다. `context`·`document`·`extract`는 실제 토큰·컴포넌트를 근거로 디자인 시스템을 정리하고, 이후 프리셋은 그 시스템을 참조해 작업한다. [§3](../../PRODUCT.md#3-scope)의 Deliver·Conversation과 §5 Skills를 확장한다. 사람의 요청으로 기존 에이전트가 작업하며 직접 그리기, 자동 에이전트 기동, 계정 관리, 호스팅을 추가하지 않으므로 Out of scope와 충돌하지 않는다.

## 3. 프리셋과 매핑

- 기존 `doan` 스킬을 진입점으로 유지한다. 별도의 전역 스킬 24개나 설치기를 만들지 않는다.
- 앱과 함께 배포하는 CLI에 목록과 정적 Markdown을 포함한다. Impeccable 설치나 네트워크 연결 없이 조회한다.
- 전체 스킬 셋을 조사하되, 원본의 명령·런타임·강제 절차를 그대로 복제하지 않는다. 원본 항목별 도안 대응은 design의 표로 추적한다.
- 목록에는 안정적인 ID, 표시 이름, 짧은 사용 조건과 적용 범위를 제공한다. 본문은 선택한 항목과 필요한 공통 지침만 반환한다.
- 사용자가 프리셋을 명시하면 우선한다. 자연어 요청은 기존 에이전트가 의미·부정·대상을 고려해 매핑한다. 단어 포함 여부로 강제하지 않는다.
- 간단한 요청은 하나의 적합한 프리셋만 읽는다. 요청을 수행하는 데 다른 프리셋이 필요하면 현재 에이전트가 해당 지침을 추가로 읽고 이어서 작업한다. 필요한 의존 작업의 연계는 허용하되, 요청과 무관한 전체 프리셋 연쇄 실행은 하지 않는다.
- 검토를 요청하면 검토만 한다. 조회 성공을 디자인 작업 완료로 표현하지 않는다. 프리셋은 사용자 요청보다 우선하지 않는다.
- 외부 에이전트와 앱 대화 모두 도안 가이드에서 같은 목록과 매핑 규칙을 발견한다. 앱 전송 경로에는 가이드를 읽도록 하는 짧은 안내만 두며 전체 프리셋 본문을 삽입하지 않는다.
- 조회에 실패했을 때 연결 복구 안내는 사용자가 프리셋을 명시한 경우에만 한다. 에이전트가 스스로 고른 프리셋의 조회가 실패하면 한 줄만 언급하고 원래 요청을 계속한다.

### 3.1 공개 스킬 선정 — 2026-10-28

사용자와 논의한 공개 목록은 아래 20개이다. Task 1의 선정 결과이며 구현 시 다시 검토한다. 디자인 시작 프리셋의 ID는 `context`이다(2026-10-29 사용자 결정). 원본 이름 `init`은 쓰기 도구인 CLI `doan init`·MCP `init`과 겹쳐 에이전트가 `.doan`을 만드는 도구를 부를 위험이 있다. 디자인 시스템 정리 역할은 기존 `document`를 확장해 맡기는 안으로 기록하고, 표시 이름은 구현 전 재검토한다.

| ID | 역할과 사용 조건 |
|---|---|
| context | 프로젝트의 제품·사용자·기존 디자인·제약을 파악하고 디자인 작업을 시작한다. 필요한 디자인 시스템 정리 프리셋으로 연결한다(원본 `init`) |
| shape | 개별 기능·화면의 목적, 흐름, 상태, 범위를 정리한다. 설계 결과를 내며 구현을 자동으로 시작하지 않는다 |
| document | 프로젝트 디자인 시스템을 정리한다. 에이전트가 참조할 규칙 문서와 사용자가 직접 확인할 색상·타이포·컴포넌트 캔버스를 만든다. 규칙 문서는 기존 디자인 문서가 있으면 그 문서를 갱신하고, 없으면 사용자에게 위치를 묻는다. 답이 없으면 루트 `DESIGN.md`를 제안한다(2026-10-29 사용자 결정) |
| extract | 기존 디자인의 재사용할 토큰·반복 패턴을 정리한다. 실제 앱 코드 리팩터링은 별도 요청 범위 안에서만 한다 |
| critique | 요청한 디자인의 UX·시각적 위계·전달력을 검토한다 |
| audit | 접근성·반응형 등 확인 가능한 문제를 점검하고 확인하지 못한 항목을 구별한다 |
| polish | 기존 정체성과 기능을 유지하면서 마무리한다 |
| distill | 불필요한 정보·요소·복잡성을 줄인다 |
| bolder | 요청한 대상의 시각적 강조를 강화한다 |
| quieter | 과도한 시각적 강조와 자극을 완화한다 |
| layout | 배치·간격·그룹 관계와 읽는 순서를 개선한다 |
| typeset | 글꼴·타이포그래피 위계와 가독성을 개선한다 |
| colorize | 브랜드와 의미를 유지하면서 색의 역할과 대비를 개선한다 |
| clarify | 의미와 제품 용어를 보존하면서 문구·행동·오류 안내를 명확하게 한다 |
| harden | 오류·누락·긴 문구·극단값 등 현실적인 상태를 보강한다 |
| onboard | 첫 사용·빈 상태와 다음 행동을 설계한다 |
| adapt | 요청한 화면 크기·기기·사용 환경에 맞게 조정한다 |
| animate | 상태·관계·피드백을 설명하는 모션을 설계한다 |
| delight | 기능을 방해하지 않으면서 제품에 맞는 표현과 상호작용을 개선한다 |
| generate | 사용자가 요청한 대상의 디자인 대안을 만든다. 비교·채택 전용 UI는 만들지 않는다 |

독립 공개 항목에서 제외하는 원본은 `craft`, `live`, `overdrive`, `optimize`이다. `craft`는 일반 생성 지침과 `shape`, `live`는 `polish`·`generate`, `overdrive`의 표현 지침은 `animate`·`delight` 등에 통합한다. `optimize`의 관련 성능 주의사항은 공통 지침에 반영하되 실서비스의 번들·네트워크·API 최적화를 별도 디자인 프리셋으로 제공하지 않는다. 원본 엔진 절차와 강제 점수화·서브에이전트 실행은 가져오지 않는다.

### 3.2 초기 진입과 스킬 연계 — 2026-10-28

- CLI `doan init`은 도안 프로젝트 셋업이다. `context` 프리셋은 디자인 작업을 위한 프로젝트 맥락 정리이다. 서로 다른 역할이다.
- `doan init`과 MCP `init`의 성공 결과 `nextSteps`에 `context` 프리셋과 조회 명령을 안내한다(2026-10-29 사용자 결정). CLI 자체가 모델이나 프리셋을 실행하지 않는다. 앱의 Set Up은 CLI `nextSteps`를 표시하지 않으므로 이 안내는 에이전트 경로에만 보인다.
- 프리셋 간 연계는 현재 에이전트가 필요한 다른 프리셋의 지침을 읽고 이어서 수행하는 방식이다. 별도 실행 엔진이나 모델 분류기를 만들지 않는다.
- 예: 초기 셋업 요청 → `context` 프리셋 발견·프로젝트 맥락 확인 → 필요한 CLI 셋업 → 디자인 시스템 정리가 필요하면 `document` 참조 → 규칙 문서와 확인용 캔버스 작성 → 이후 생성·수정 프리셋이 같은 디자인 시스템 참조. CLI 셋업을 이미 마쳤다면 반복하지 않는다.
- 기존 토큰·컴포넌트·디자인 문서는 기준으로 재사용하고, 없는 설명을 보완한다. 없는 규칙을 확정 사실로 만들지 않고 사용자와 정한다. 문서·캔버스는 실제 토큰과 컴포넌트의 참조 관계를 남긴다.
- 기존 디자인 시스템이 충분하면 재사용하며 매번 다시 생성하지 않는다. 사용자가 요청한 작업에 필요한 범위에서만 연결하고, 단순 CLI 셋업 요청을 디자인 시스템 작성 승인으로 간주하지 않는다.
- 디자인 시스템 캔버스는 사용자의 프로젝트에 프리셋이 만드는 산출물이다. 이번 feature에서 도안 앱의 별도 디자인 시스템 관리 화면이나 renderer UI를 구현한다는 뜻은 아니다. 2026-10-28 사용자 결정: 파일 경로는 `.doan/canvases/design-system.html`, 캔버스명은 확장자 `.html`을 뺀 `design-system`이다. 별도 표시 이름 `Design System`은 두지 않는다. 기존 프로젝트 구성을 존중한다. 갱신할 때 요청 밖 프레임·ID를 보존하고, 색·타이포는 값을 복사하지 않고 프로젝트 Token CSS 변수를 참조한다(2026-10-29 사용자 결정).

## 4. 백엔드 완료 조건

1. Settings > Connections로 새로 연결한 Claude Code와 Codex가 기존 `doan` 스킬을 통해 목록과 본문을 찾는다. 이전 stub(`c994913`의 bytes)도 가이드 조회로 새 기능을 발견한다. 앱 대화의 다섯 공급자도 profile stub과 bundled CLI로 같은 목록과 본문을 찾는다.
2. CLI·MCP·앱 main/preload 조회가 동일한 버전의 카탈로그와 본문을 반환한다. 임의 파일 경로나 알 수 없는 ID는 거부한다.
3. 앱이 꺼져 있고 프로젝트가 초기화되지 않은 디렉터리에서도 CLI/MCP로 지침을 읽는다. 선택 대상이 필요한 실제 작업은 기존 `active` 또는 명시 대상 해석을 사용한다.
4. 외부 에이전트 Claude Code·Codex가 명시 프리셋, 자연어 일치, 부정 표현, 적합한 프리셋 없음, 복합 요청, 검토만 요청의 필수 사례를 통과한다. 사례별 허용 선택·필수 조회·미일치 시 본문 미조회·금지 수정을 rubric과 checks로 판정한다. 가이드 인용은 실제 조회로 인정하지 않는다. 자동 검사 실패 또는 judge partial/fail이 남으면 해당 완료 조건은 미완료이다.
5. 전체 본문이 기본 가이드·목록·앱의 매 전송에 들어가지 않는다. 요청 원문과 기존 앵커 경계는 보존한다. 측정 없이 토큰 절감률이나 매핑 정확도를 주장하지 않는다.
6. 대표 수정 작업에서 대상 밖의 프레임과 ID가 유지되고 `doan check`가 통과한다. 생성 작업은 캔버스가 없는 프로젝트에서도 동작한다.
7. 원본 커밋, 파일별 출처, 도안의 변경 내용을 보존한다. CLI에 Impeccable `LICENSE`(Apache-2.0)·`NOTICE.md`와 iOS/Android 지침의 ehmo MIT 고지를 포함한다. 원본 전용 엔진 명령을 호출하라는 미해결 지침이 없다.
8. 외부 에이전트는 shell 전용과 MCP 전용 경로에서 발견·본문 조회를 각각 검증한다. 둘 다 사용할 수 없으면 프리셋 미적용과 연결 방법을 알리고 자동 설치·권한 변경·재시도를 하지 않는다. 앱 대화는 bundled CLI shell만 사용하며, 조회에 실패하면 미적용 사실과 원인만 알리고 Settings > Connections나 MCP를 안내하지 않는다.
9. `doan init`·MCP `init` 성공 결과의 `nextSteps`에서 `context` 프리셋을 발견하고, 필요한 디자인 시스템 프리셋(`document`)으로 연결하며, 기존 시스템이 충분하면 재사용하는 사례를 검증한다. 문서와 확인용 캔버스의 근거가 일치하고 요청 밖 변경이 없어야 한다.
10. 앱용 읽기 API를 실제 격리 Electron에서 짧게 검증하고, `buzz-home`에 계약·실패 상태·예제를 전달한다. renderer 화면은 변경하지 않는다.
11. 앱 대화의 다섯 공급자 각각이 실제 격리 앱에서 가이드 안내로 프리셋을 발견하고 본문을 조회한다.

## 5. 비목표

- 프리셋 선택기·검색·칩·추천 카드·전송 UI 및 도안 앱 UI의 디자인 초안. 사용자 프로젝트의 디자인 시스템 캔버스 작성 지침은 범위에 포함한다.
- 별도 모델 분류 호출, 임베딩 검색, 규칙 기반 자연어 분류기, 사용자 프롬프트 자동 재작성.
- 디자인 자동 진단·점수·자동 해결책 추천, 상시 검사 훅, 평가 결과 저장소.
- Impeccable 엔진·브라우저 확장·live 서버·검사기·이미지 생성 서비스 이식.
- 대안 비교·채택 상태 관리, 자동 대안 생성, 새 디자인 문서 관리 체계.
- 사용자 제작 프리셋, 플러그인 마켓, 원격 카탈로그, 자동 upstream 동기화.
- 외부 에이전트 통합(Settings > Connections) 대상 확대. 외부 경로는 Claude Code·Codex만 검증한다. 앱 대화의 다섯 공급자는 기존 도안 연결을 그대로 사용한다.

## 6. 완료 경계와 선행 조건

현재 설치·CLI/MCP·대화 백엔드를 사용하므로 `buzz-conversation` UI 완료를 기다릴 필요가 없다. UI 최소 목표는 후속 `buzz-home`(C3)에서 완성한다. 그때에도 같은 백엔드를 사용하며 카탈로그를 renderer에 복제하지 않는다.

추가 PoC는 선행 조건으로 두지 않는다. 기존 실험(`.scratch/design-tools-poc/`, 2026-10-27)은 정적 지침 전달의 가능성을 보였다. 이 결과는 커밋되지 않으므로 tasks A0에서 PRODUCT §6에 기록한다. 실제 발견·매핑·설치·대화 연결은 구현 테스트와 agent-eval에서 검증한다.
