# multi-handoff — spec

## 사용자

- **사람**: 캔버스 대화에 "새 캔버스 n개를 만들어 줘"라고 요청한 사람. 턴이 끝나면 새 캔버스마다 새 대화가 시작되어 있고, 각 대화의 첫 메시지는 이전 에이전트가 쓴 핸드오프다. 소스 대화의 스레드에서 캔버스마다 핸드오프가 됐는지 안 됐는지 보고, 줄의 Open으로 그 캔버스를 연다.
- **에이전트**: 앱 대화의 턴 프롬프트에서 "이번 턴에 만든 새 캔버스마다 `doan handoff`를 한 번씩 실행하라"는 안내를 받는다. 같은 턴에서 서로 다른 새 캔버스에 대한 두 번째 요청도 받아들여진다.

## 문제

- 지금 Doan은 턴마다 핸드오프를 하나만 받는다(PRODUCT §5 item 2 'Handoff': "Doan accepts one per turn"). 두 번째 `doan handoff`는 `already_requested`로 거절된다(`app/src/main/conversation/handoff.ts` `handoffEligibility`).
- 턴 프롬프트의 `HANDOFF_GUIDANCE`(`app/src/main/conversation/prompt.ts`)는 "작업이 이어질 새 캔버스"가 하나라고 전제한다. 그래서 새 캔버스를 여러 개 만든 턴에서는 에이전트가 이어갈 캔버스를 고르지 못해 핸드오프를 아예 하지 않을 수 있다. 실제로 그런 일이 있었다(사용자 관찰).
- 에이전트가 핸드오프를 하지 않으면 사람에게는 아무 표시도 보이지 않는다. 새 캔버스에 대화가 없다는 사실을 사람이 직접 찾아야 한다.

## 완료 조건

1. **요청 수락**: 핸드오프할 수 있는 턴(Doan 연결, 캔버스 대화, Plan 아님, 핸드오프로 시작된 턴 아님)에서, 서로 다른 캔버스 경로에 대한 `doan handoff` 요청을 개수 제한 없이 받는다. 같은 턴에서 같은 경로를 다시 요청하면 `already_requested`로, 소스 자신의 캔버스를 지정하면 지금처럼 `same_canvas`로 거절한다. 경로는 CLI가 정규화한 repo 상대 경로(`.doan/canvases/<file>.html`)로 비교한다.
2. **판정과 시작**: 턴이 done으로 끝나면 요청마다 따로 판정한다(목록에 하나뿐인 캔버스인지, 턴 시작 때 없던 캔버스인지, 현재 대화가 없는지). 모든 요청이 판정을 마친 뒤(폴더 새로고침 또는 마감), 시작 조건을 통과한 요청을 요청 순서대로 하나씩 시작한다. 새 대화는 요청이 몇 개든 소스의 provider, model, effort, Fast, 현재 권한 모드를 쓰고 Last used를 바꾸지 않는다. 한 요청이 거절되어도 다른 요청에는 영향이 없다.
3. **취소**: 턴이 failed·stopped·interrupted로 끝나거나, 판정·시작 사이에 소스가 보관되거나, 그 공급자의 Stop·sign-out이 오거나, 앱이 종료되거나 재시작되면 아직 시작하지 않은 요청은 모두 cancelled가 된다. 이미 시작된 대화는 그대로 둔다.
4. **소스 스레드의 줄**: 요청마다 줄 하나를 요청한 자리에 보여 준다(“Hands off to <file> when this turn ends” → “Handed off to <file>” / “Didn’t hand off to <file>. …”). 기존 단일 핸드오프의 문구와 동작은 그대로다. 줄의 Open 버튼은 접근 이름에 파일 이름을 담는다(“Open <file>”).
5. **기록 형식**: `handoff.resolved` 이벤트는 어느 요청의 결과인지 캔버스 경로로 밝힌다. 경로가 없는 기존 기록은 그 턴의 유일한 요청에 대한 결과로 읽는다.
6. **안내**: `HANDOFF_GUIDANCE`는 "이번 턴에 `.doan/canvases/`에 만든 새 캔버스마다, 마지막 단계에서 연달아 `doan handoff`를 한 번씩 실행하라. 사람이 핸드오프하지 말라고 하거나 이 캔버스에 머물라고 하면 하지 마라"고 안내한다. Send now로 끼어든 메시지의 프롬프트도, 그 턴에 이미 요청이 있었더라도 이 안내를 유지한다.
7. **누락 줄**: 턴을 보낼 때 `HANDOFF_GUIDANCE`를 받은 턴이 done으로 끝났을 때, 다음을 모두 만족하는 캔버스마다 소스 스레드에 줄을 하나씩 보여 준다. 문구는 “Didn’t hand off to <file>. The agent didn’t ask to.”이고 Open이 있다(그 캔버스를 Quick Open처럼 연다). Doan은 이 캔버스에 대화를 시작하지 않는다.
   - 그 턴의 활동 기록에 edit 경로로 보고됐다.
   - 턴 시작 때 없던 캔버스이고, 판정 때 목록에 하나뿐이다.
   - 소스 캔버스가 아니고, 그 턴에 핸드오프 요청이 없었고, 판정 때 현재 대화가 없다.
   - 한계: 셸 명령으로 만든 파일(Claude Code·Codex의 command 활동)과 edit 경로를 보고하지 않는 공급자에서는 줄이 나오지 않는다.
   - 누락 줄은 그 턴의 마지막 핸드오프 줄 뒤에, 핸드오프 줄이 없으면 그 턴의 끝에 붙는다. 판정을 기다리는 동안 큐와 working 상태는 붙잡지 않는다.
8. **큐**: 핸드오프를 기다리는 동안 소스에 쌓인 메시지는 모든 요청이 해결된 뒤 한 번만 처리한다. 요청이 하나면 지금처럼 동작한다(시작 → 새 대화로 이동, 거절 → 소스, 취소 → 초안). 요청이 둘 이상이면, 취소된 요청이 하나라도 있으면 초안으로 돌려주고, 아니면 소스로 보낸다.
9. **화면**: 시작된 핸드오프가 하나면 지금처럼 이동하거나 토스트를 띄운다. 둘 이상이면 화면을 옮기지 않는다. 사람이 소스 캔버스 페이지에 있으면 줄 n개와 Open으로 충분하므로 아무것도 띄우지 않는다. 다른 곳에 있으면 토스트를 하나만 띄운다(“<source file> handed off to <n> canvases”). Open은 소스 캔버스와 그 대화로 간다.
10. **상한**: 턴 하나가 시작하는 핸드오프 대화 수에 상한이 없다. 새 대화 n개의 첫 턴은 같은 계정에서 동시에 돌고, 한도에 걸리면 각 대화가 자기 실패를 보여 준다.
11. **문서**: PRODUCT §3 Out of scope 4와 §3 In scope 6 'Conversation', §5 item 1의 승격 규칙(해결 안 된 핸드오프가 있는 턴의 캔버스), §5 item 2 'Handoff', ARCHITECTURE §4·§7·§14의 핸드오프 서술이 "새 캔버스마다 하나"로 바뀐다.
12. **eval**: `/agent-eval`에 새 캔버스 두 개를 만드는 핸드오프 시나리오 R11이 추가되고, Claude Code와 Codex 실행 결과가 `docs/USABILITY-EVAL.md`에 기록된다.

## 비목표

- Doan이 핸드오프 메시지를 대신 쓰거나, 요청이 없는 캔버스에 대화를 시작하는 것. Doan이 스스로 에이전트를 깨우는 셈이라 Out of scope 4에 걸린다.
- 핸드오프로 시작된 턴의 연쇄 핸드오프. 지금처럼 `handoff_turn`으로 거절하고, 그 턴에는 누락 줄도 없다.
- 프로젝트 대화(캔버스 없는 대화)의 다중 승격. 프로젝트 대화는 지금처럼 승격으로만 캔버스에 붙고, 누락 줄도 없다.
- 레거시 외부 대화와 터미널 에이전트. `doan handoff`는 여전히 Doan 앱 대화에서만 동작한다.
- 셸로 만든 파일과 ACP 공급자의 누락 줄. edit 경로 보고가 없으면 표시하지 않는다.
- 앱 소켓 v5 형식 변경. 요청과 응답 모양은 그대로다.
- 핸드오프 줄 묶기. 줄이 많아지는 턴이 흔한지는 R11과 실제 사용으로 본 뒤 다시 판단한다.
