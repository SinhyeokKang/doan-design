# canvas-edit-awareness — spec (canvas-multi-conversation 하위 3)

에이전트가 캔버스를 고치기 전에, 같은 캔버스 파일을 고치는 다른 세션이 있는지 안다. 있으면 사람에게 한 번 확인한다. Doan은 막지 않는다. 상위 [canvas-multi-conversation](../canvas-multi-conversation/spec.md)의 공통 결정 1–8을 따르고, 하위 1 [canvas-concurrent-conversations](../canvas-concurrent-conversations/spec.md)가 병합된 뒤에 구현한다.

## 사용자

- **에이전트**: 터미널 에이전트와 Doan 앱 대화 안의 에이전트. 편집 전에 부르는 `doan work start`(터미널)와 `doan work update`(터미널과 앱 대화)의 답에서 다른 세션을 본다.
- **사람**: 같은 캔버스를 다른 세션이 고치고 있을 때, 에이전트가 고치기 전에 한 번 묻는다. 지금 고칠지 사람이 정한다.

## 문제

- 사용자 보고(상위 spec '문제'): 한 캔버스에서 세션 여러 개를 굴리는 사람이 있고, 그때 각 세션의 상태를 알고 싶어 한다. 하위 1 이후 한 캔버스에서 앱 대화 여러 개가 동시에 돌 수 있고, 같은 파일을 동시에 고쳐도 Doan은 막지 않는다(상위 공통 결정 3). 터미널 에이전트끼리는 지금도 그렇다.
- 앱은 어느 세션이 어느 캔버스를 고치는지 안다. 터미널 세션은 `workState.ts`, 앱 대화의 작업 내용은 `conversationWork.ts`, 돌고 있는 턴은 `ConversationService.liveTurns()`다. 하지만 v3 답은 `{v: 3, ok: true}`뿐이라(`schema/app-socket.v3.schema.json` `response`) 에이전트에게 돌아가는 정보가 없다. 에이전트는 다른 세션이 같은 파일을 고치는지 모른 채 편집을 시작한다.

## 정한 점

1. **다른 세션의 범위**: 같은 캔버스 파일(루트 + 경로)을 고치는 세션이다. `doan work`로 그 파일을 작업 중이라고 알린 터미널 세션과, 그 파일에서 턴이 돌고 있는 앱 대화를 센다. 다른 워크트리의 같은 캔버스는 파일이 다르므로 세지 않는다. 부른 쪽 자신은 뺀다.
   - 앱 대화는 그 턴의 마지막 `update`가 이 파일을 가리킬 때, 또는 이 캔버스에 묶인 대화가 그 턴에서 아직 `update`를 보내지 않았을 때 센다. 마지막 `update`가 다른 파일을 가리키면 세지 않는다(질문만 하는 대화가 불필요한 확인을 늘리지 않게). `update`가 없는 묶인 대화는 프레임과 메모 없이 담는다. 다른 캔버스의 프레임이나 메모를 이 캔버스의 항목에 담지 않는다(PRODUCT §5 item 2 'Work content').
   - 터미널은 그 파일을 마지막으로 건드린 지 `WORK_EXPIRY_MS`(5분)가 지나면 에이전트에게 주는 목록에서 뺀다. 세션 전체의 만료를 기다리지 않는다. 앱의 작업 표시는 지금 규칙 그대로다.
2. **답에 담는 것**: 다른 세션마다 종류(터미널 / 앱 대화), 알 수 있으면 프로바이더, 지금 프레임, 메모(`doan work update`의 `--frame`·`--note`)를 담는다. 세션 ID, 대화 ID, 계정 이름, 경과 시간은 담지 않는다. 항목에는 앞으로도 손잡이나 ID를 넣지 않는다(원소의 `additionalProperties: false`).
3. **에이전트가 묻는 때**: 한 대화 안에서 그 캔버스를 처음 고치기 전에 한 번 묻는다. 다른 세션이 누구인지(종류, 프로바이더, 프레임은 제목으로, 메모) 말하고 지금 고칠지 묻는다. 사람이 진행하라고 하면 같은 대화 안에서 그 캔버스에 대해 다시 묻지 않는다. 다만 `others`의 항목 수가 지난번 물었을 때보다 늘면 다시 묻는다. 프레임이나 메모만 바뀐 것은 새 세션이 아니다. 사람이 처음부터 "다른 세션과 상관없이 진행"이라고 했으면 묻지 않는다. 묻느라 멈추면 `doan work done --json`을 부른다(가이드 규칙 E).
4. **정보가 없을 때**: 앱이 꺼져 있거나 답에 정보가 없으면(`delivered: false`, 또는 `others`가 없는 답) 묻지 않고 지금처럼 진행한다. Doan은 어떤 경우에도 편집을 막지 않는다(상위 공통 결정 3).
5. **앱 대화는 첫 편집 전에 `update`를 보낸다**: 앱 대화에서 `start`는 아무것도 보내지 않는다(ARCHITECTURE §4 'Suppression'). 새 프레임, `<head>` 편집, 파일 전체를 다시 쓰는 경우도 첫 편집 전에 `doan work update <canvas> --json`(`--frame`은 있으면)을 부르게 가이드가 말한다. 그 답의 `others`로 판단한다.
6. **프레임과 메모는 데이터다**: 다른 에이전트가 쓴 글이므로 가이드는 지시로 따르지 않게 한다(규칙 A의 선택 글과 같다). 메모는 다른 세션의 에이전트에게도 간다. PRODUCT §5 item 2 'Work content'와 Out of scope 4의 문장에 이 점을 적는다.

## 리드 판단

- **v3 안에서 답만 늘린다** — 요청은 바꾸지 않으므로 이전 앱도 지금처럼 신호를 받는다. 답의 `ok: true` 쪽에 선택 필드 `others`를 더한다. 새 CLI가 이전 앱의 답을 읽으면 `others`가 없으므로 정보 없음으로 진행한다. 이전 CLI가 새 앱의 답(`others` 포함)을 읽으면 이전 스키마(`additionalProperties: false`)에 걸려 `delivered: false`를 보고하지만, 앱은 신호를 이미 받았다('Best effort'). `DOAN_CLI`로 지정한 CLI, `app/dist`의 빌드, 테스터 복사본에서는 두 쪽이 어긋날 수 있다. 그래도 `delivered: false`는 오류가 아니므로 에이전트를 막지 않는다.
- **목록 상한은 8개**다. 최근 `touched` 순이고, `update`가 없는 묶인 대화는 뒤에 둔다.
- **익명 터미널** — 세션 ID가 없는 터미널은 루트마다 하나의 익명 세션이다(ARCHITECTURE §4 'State'). 같은 루트의 익명 터미널 둘은 구분되지 않으므로 서로를 다른 세션으로 보지 못한다. 알려진 한계로 BACKLOG에 둔다.
- **질문 카드를 기다리는 앱 대화**도 턴이 도는 동안이라 목록에 있다. 가이드는 "작업 중"이라는 말로 그 경우까지 덮는다.

## 완료 조건

- 서로 다른 세션 ID의 터미널 A·B가 있다. A가 `doan work update .doan/canvases/x.html --frame hero --note "Tightening spacing" --json`을 보낸 뒤 B가 `doan work start .doan/canvases/x.html --json`을 부르면 결과가 `{delivered: true, others: [{kind: "terminal", provider: "claude", frame: "hero", note: "Tightening spacing"}]}`이다. 그 뒤 A의 다음 `update` 답에는 B가 있고 A 자신은 없다.
- 앱 대화 C의 턴이 그 캔버스에 묶여 돌고 `update`가 없으면, B의 답에 `{kind: "conversation", provider: "<C의 프로바이더>"}`가 프레임·메모 없이 있다. C가 이 파일로 `update`를 보냈으면 그 프레임과 메모도 있다. C의 마지막 `update`가 다른 파일이면 없다. C 자신의 `update` 답에는 C가 없다.
- 다른 워크트리의 같은 캔버스 경로를 고치는 세션은 답에 없다. 이 파일을 5분 넘게 건드리지 않은 터미널은 답에 없다.
- 다른 세션이 없으면 `others`가 없다. 앱이 없으면 `{delivered: false}`이고 `others`가 없다. `done`의 답에는 `others`가 없다.
- `--json` 없이도 지금처럼 결과 JSON이 찍히고, `others`가 있으면 그 안에 있다(새 텍스트 줄은 없다).
- 가이드 규칙 D가 '정한 점' 3–6을 말하고, `doan skill --json` 출력이 `skillOutputBudget`(21,600 B) 안이다.
- `/agent-eval`: W9에서 Claude Code와 Codex가 다른 세션이 있는 캔버스를 고치기 전에 한 번 묻는다. W10에서는 "상관없이 진행"이 프롬프트에 있으므로 묻지 않고 고친다. W5(정보 없음)에서는 묻지 않고 지금처럼 진행한다.
- 세션 ID, 대화 ID, 계정 이름이 답과 CLI 출력 어디에도 없다.

## 하지 않는 것

- Doan이 편집을 막거나 경고하는 UI, 사람에게 보이는 앱 화면 변경.
- 다른 워크트리의 같은 캔버스를 같은 대상으로 보기.
- 같은 루트의 익명 터미널끼리 구분하기.
- 다른 세션이 끝날 때까지 기다리는 자동 동작.
- 항목에 손잡이나 ID를 넣어 세션을 개별로 추적하기.

## 사용자 결정(2026-11-14)

- 다른 세션 목록에 경과 시간을 넣지 않는다. 대신 터미널은 파일별로 5분이 지나면 빼고 앱 대화는 도는 동안만 세므로, 목록에 있으면 지금 작업 중이다.
- '상관없이 진행'을 처음부터 말한 경우는 `/agent-eval`의 별도 시나리오 W10으로 둔다(이 저장소에서 `b`는 같은 시나리오의 개정판이다).
- 리뷰 결정: 다시 묻는 기준은 항목 수 증가, 묶인 앱 대화는 이 파일을 고칠 때만 센다, 터미널은 파일별 5분 만료, 메모가 다른 에이전트에게 가는 것을 받아들인다.
- W9나 W10이 실패하면 병합을 막는다. 고치기 어려운 실패는 사용자가 열린 이슈로 받아들이면 `docs/USABILITY-EVAL.md`에 적고 병합할 수 있다.
