# 작업 표시 렌더링 부하 줄이기

## 사용자

앱에서 에이전트가 캔버스를 작업하는 동안 보드와 대화 패널을 보는 사람이다. 에이전트(CLI·스킬)가 받는 것은 없다.

## 문제

2026-11-11 실제 앱(0.1.5)에서 녹화한 영상(사용자 Desktop `화면 기록 2026-11-11 16.28.50.mov`, 8초, 60fps)에서 다음을 확인했다. 그때 머신은 load average 16–18(8코어)이었다.

- 작업 중 1–4프레임마다 한 프레임씩 작업 프레임 테두리, 대화 패널의 큐 행, 입력창 테두리·제출 버튼·모델 행, 스레드 끝부분이 함께 사라졌다. 입력창 placeholder만 테두리 없이 남았다.
- 작업 표시가 끝나자 깜빡임도 멈췄다. 사용자도 에이전트 작업이 시작될 때 깜빡임이 시작된다고 확인했다.

원인은 두 가지로 나눈다.

- **확인된 원인**: 재로드마다 작업 마커가 숨겨졌다가 다시 나타나며 애니메이션이 처음부터 시작된다. 이 수정은 chain-261111 링크 1(`frame-first-selection`)에 넘겼다(chain.md 인계 기록). 이 기능은 그 수정이 develop에 들어간 뒤 시작한다.
- **확정되지 않은 원인**: 서로 다른 DOM(캔버스 overlay와 대화 패널)의 요소가 같은 프레임에 함께 빠진다. 렌더러가 고부하에서 프레임 예산을 넘겨 레이어를 늦게 그리는 것으로 보지만 측정하지 않았다.

작업 표시는 작업 중 매 프레임 메인 스레드에서 다시 그리는 요소를 여럿 가진다(코드에서 확인).

- 작업 마커: `box-shadow` 키프레임(`doan-work-glow`)과 `background-position` 키프레임(`doan-work-travel`).
- 점 필드: 보드 전체 2D 캔버스를 `requestAnimationFrame`마다 지우고, 가까운 점 약 2천 개를 점마다 `fill`해 다시 그린다.
- 알림 pill의 `backdrop-filter: blur`가 계속 바뀌는 보드 위에 있다.
- 대화 패널은 스트리밍 delta마다 스레드를 다시 렌더한다.
- 그 밖에 100ms 프레임의 타이핑 GIF, 스피너, 캐럿 깜빡임이 있다.

## 접근

가능한 모든 수단을 쓴다. 원인이 확정되지 않거나 고부하 깜빡임이 재현되지 않아도, 매 프레임 메인 스레드나 넓은 다시 그리기를 일으키는 요소는 모두 바꾼다. PoC는 진행 여부를 가르는 관문이 아니라 바꾸기 전 기준선과 우선순위를 남기는 단계다.

가드레일은 하나다. **시각적 drift는 허용하지 않는다.** 바꾸기 전과 픽셀 비교에서 기준을 넘는 변경은 사용자 확인이 있어도 넣지 않고, 같은 화면을 내는 다른 수단을 찾거나 그 요소를 그대로 둔다.

## 완료 조건

1. PoC가 격리 앱에서 부하 없음과 고부하(코어 수의 2배만큼 `yes`) 두 조건으로 요소별 비용과 바꾸기 전 기준선을 측정했다. 조건·변형마다 3회 이상 반복하고 중앙값과 범위를 tasks.md에 남겼다.
2. 작업 마커 글로우, 작업 마커 그라디언트, 점 필드(메인 스레드 묶기와 Worker), 보드 글로우, 대화 패널 스트리밍 반영, 다시 그리기 격리(`contain`)를 바꿨다. 바꾼 요소는 화면이 멈춘 상태(슬라이드·확대·이동 중이 아닐 때)에서 첫 프레임 뒤 매 프레임 메인 스레드 paint를 일으키지 않는다. 점 필드는 프레임당 `fill` 호출이 알파 단계 수 이하다. 스트리밍은 delta 반영이 프레임당 한 번 이하다. 어떤 수단이 drift를 내면 그 수단은 넣지 않고, 그 사실과 픽셀 비교를 tasks.md에 남긴다.
3. 같은 조건에서 바꾸기 전보다 메인 스레드 시간의 중앙값이 줄었다. 줄지 않은 요소는 원인과 측정을 적고 사용자에게 돌아온다.
4. 화면은 바꾸기 전과 같다. 같은 애니메이션 시점에 멈춘 화면을 픽셀로 비교해 채널 차가 2 이하이다. 비교하는 상태는 working, still(대기), reduced motion, reduced transparency, forced colours, 라이트·다크, 마커 슬라이드 중, 큰 확대, 스트리밍 중인 스레드다. reduced transparency, forced colours, 다크는 Chromium 에뮬레이션으로 확인하고 그 사실을 남긴다. 기준을 넘는 변경은 넣지 않는다.
5. 고부하 10초 녹화(60fps)에서 대화 패널(입력창 테두리, 큐 행)과 작업 마커 테두리의 고정 영역이 배경색으로 떨어진 프레임을 스크립트로 세어, 바꾸기 전과 후의 수를 남긴다. 바꾼 뒤 0이 아니면 남은 원인 후보와 측정을 적고 사용자에게 돌아온다.

## 비목표

- 작업 표시와 대화 패널의 동작, 문구, 등장 조건, 마커 위치 규칙, 색·크기·주기는 바꾸지 않는다.
- 알림 pill의 블러를 없애거나 약하게 하는 것처럼 화면이 달라지는 수단은 쓰지 않는다. 블러는 같은 화면을 유지하는 수단(다시 그리기 격리 등)만 쓴다.
- 근거 없는 FPS 목표, GPU 플래그·하드웨어 가속 끄기, 큰 캔버스 iframe 렌더링(`canvas-rendering-stability`)은 다루지 않는다.
- 전체 e2e나 상시 성능 회귀 스위트를 추가하지 않는다.
