# 대형 캔버스 렌더링 안정화

## 순서와 사용자

다섯 기능 중 3번이다. 앞은 `frame-first-selection`, 뒤는 `frame-prototype`이다. 큰 캔버스를 보고 확대·축소·이동하는 사람이 대상이다.

## 문제와 현재 증거

사용자가 큰 캔버스의 그래픽 깨짐을 보고했다. 원본 캔버스와 Export HTML을 PoC 진행 시점에 제공하기로 했다. 아직 해당 자료를 받거나 현상을 재현하지 않았다. 잘림·빈 영역·깜빡임 중 무엇인지, 발생 동작, GPU·합성·레이아웃 중 어느 경로가 원인인지 확정하지 않는다.

## 완료 조건

1. 제공받은 원본과 Export HTML이 같은 시점의 내용인지 확인한 뒤 앱·브라우저에서 같은 크기·배율·동작으로 재현 여부를 기록한다. 한쪽에서 재현되지 않는 결과도 보존한다.
2. 원본·의존 파일·Export의 지문과 Export 생성 버전, 앱 커밋·Electron/브라우저 버전, 폰트·자산 로드 상태, 화면 크기·디스플레이 배율·캔버스 크기·프레임 수·확대율·재현 순서와 전후 증거가 있다. 확대·이동 중 깨짐은 해당 동작 구간의 화면 기록을 포함한다.
3. PoC 후 사용자와 합의한 개선 기준을 충족하고 남은 현상은 사용자에게 확인받는다. 자료 확보·측정만으로 완료 처리하지 않는다. 자료 미확보·재현 실패·원인 미확정은 조사 상태이며 추측 구현을 시작하지 않는다. 허용할 잔여 현상과 성능 기준은 PoC 결과를 보고 사용자에게 확인한다.
4. 일반 크기 캔버스의 선택 위치·프레임 점프·Capture area·재로드·스크롤·모션이 유지된다. 다른 현상을 숨기기 위해 상호작용을 끄지 않는다.
5. **범위 갱신(사용자, 2026-11-11 lead 전달)**: 그래픽 깨짐과 렌더링 버그를 고치는 데서 그치지 않고 앱 자체를 최적화한다. 큰 캔버스의 최초 렌더링, 빠른 확대·축소, 마구 하는 이동에서 렌더링 비용을 재고 줄인다. 대상은 메인 스레드의 script·style·layout·paint, 합성·래스터, GPU 메모리, 레이어 수, iframe·overlay 무효화다. 시각적 drift가 없는 변경만 넣는다(수정 전과 같은 픽셀). drift가 생기는 변경은 넣지 않는다. 기준선은 P2의 부하 비교와 최적화 측정이고, 수정 전후 수치를 PR 본문에 남긴다. 목표 수치는 측정에서 정한다(근거 없는 FPS 목표는 여전히 비목표다). ARCHITECTURE §3 구조(sandbox iframe, iframe 밖의 보드, src마다 새 iframe)를 바꿔야 하는 최적화는 먼저 사용자에게 묻는다.

## 비목표

원인 확인 전 가상화·타일 렌더링·GPU 옵션을 확정하지 않는다. 캔버스 포맷 개편, 근거 없는 FPS 목표, 전체 e2e 도입은 하지 않는다. Export HTML은 비교 자료이며 export 코드 수정 범위는 원인을 확인한 뒤 결정한다.
