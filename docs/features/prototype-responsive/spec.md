# prototype-responsive — spec

출처: 사용자 요청("프로토타입 모드. 지금 fit 밖에 없어? 반응형 느낌을 어케 본다니", "prototype-responsive 따위로 fit 모드 반응형 모드 토글을 추가해야될 것 같음"), 진행 중 지시("흠 스펙 변경. 툴바 따로 안둔다. 모두 헤더로. 너비 부족할 때 프레임명 캡슐 먼저 미노출. 모드는 오른쪽 그룹으로.", "모드는 두 아이콘 버튼을 한번더 감싸서 토글 처럼 만들어도 됨. 새로운 프리미티브", "이러면 디바이더는 필요없어. 한번 더 감싸진게 영역 구분이 될 듯")와 그 뒤 질문의 답(Reload는 왼쪽 Back·Forward 옆, 이름 캡슐은 두 무리 사이의 가운데), 이어진 지시("프레임 캡슐이 아이콘 버튼으로 변하는 임계 지점에 캡슐을 2행으로 보내면 어때? 헤더가 좀 두꺼워지더라고. 대신 임계는 지금보다 낮출 수 있을 때까지 더 낮추고"), `/feature-review` 결과. 아래 동작은 모두 사용자가 정했다('결정'). 남은 미확인은 design.md 'PoC 의존'뿐이다.

용어: **Fit 모드**와 **Responsive 모드**는 프레임 viewport의 크기 규칙이고, **창 맞춤**은 Play가 창 크기를 표시 크기에 맞추는 일(`fitPrototypeWindow`)이다.

## 사용자

- **사람**: 프로토타입 창에서 프레임을 표시된 크기로 고정해 보거나(Fit 모드), 창 크기를 따라 바뀌는 모습을 본다(Responsive 모드). 모드는 헤더 오른쪽의 토글로 고른다.
- **에이전트**: 바뀌는 것이 없다. 표시 `data-doan-prototype="<w>x<h>"`의 형식과 뜻(ARCHITECTURE §1 convention 14), PRODUCT의 "at the size the agent marked", guide, CLI, `doan check`는 그대로다. 그래서 이 feature에는 `/agent-eval`이 필요 없다.

## 문제 (코드에서 확인한 지금 동작)

- Play, 드로어 선택, Back/Forward는 창 맞춤을 한다(`fitPrototypeWindow`: 콘텐츠 폭 = 표시 폭 + 16, 최소 360, 작업 영역 안; 높이 = 표시 높이 + 64, 작업 영역 높이까지). Reload와 같은 프레임의 Play는 창 크기를 유지한다.
- 그 뒤 run iframe은 콘텐츠 패널을 따른다. 높이는 늘 패널 높이이고, 폭은 패널 폭이다. 표시 폭이 344(`PROTOTYPE_NARROW_BELOW`)보다 좁을 때만 그 폭을 지키고 가운데에 놓인다(`prototypeIframeBox`). 사람이 창을 끌어 크기를 바꾸면 `ResizeObserver`가 iframe 크기를 바꾸고, `innerWidth`·`innerHeight`·media query가 따라 바뀐다.
- 그래서 반응형 동작은 지금도 창 가장자리를 끌면 보인다. 하지만 다음이 없다.
  - 모드를 고르는 컨트롤. 창은 처음에 표시 크기와 같으므로 사람은 "fit만 있다"고 읽는다.
  - 창 크기와 상관없이 표시 크기를 지키는 방법. 창을 줄이면 프레임 viewport도 줄고, 작업 영역보다 큰 표시(예: 1440×900을 작은 노트북에서)는 처음부터 표시 크기로 보이지 않는다(높이가 작업 영역에서 잘리고 `innerHeight`가 표시 높이보다 작다).

## 동작

### 두 모드

- **Fit 모드**(기본, 결정 3): 프레임 viewport가 표시 크기(`<w>×<h>` CSS px)로 고정된다. 창 크기를 바꿔도 `innerWidth`·`innerHeight`·media query는 표시 크기 그대로다. 프레임은 콘텐츠 패널 가운데에 놓인다. 패널이 표시 크기보다 작으면 프레임 전체가 보이도록 비율을 지켜 줄인다(결정 1). 키우지는 않는다. 줄여도 viewport 크기와 media query는 바뀌지 않는다. 표시 폭이 344보다 좁은 프레임도 자기 크기로 가운데에 놓인다.
- **Responsive 모드**: 사람이 고를 때만 쓴다. 프레임 viewport가 콘텐츠 패널 전체를 채우고 창을 따른다. 창을 끌거나 형제 feature `prototype-conversation`의 대화 패널이 폭을 가져가면 `innerWidth`·`innerHeight`·media query·container query가 따라 바뀌고 문서가 `resize`를 받는다. 표시 폭이 344보다 좁은 프레임도 패널을 채운다(결정 5).
- 표시 크기를 아직 모를 때(run이 없거나, 첫 Play가 읽기 실패로 끝나 표시 폭이 0일 때)는 두 모드 모두 패널을 채운다.
- 두 모드 모두 Play·드로어·Back/Forward는 창 맞춤을 한다. 창 맞춤 폭은 지금 그대로다(표시 폭 + 16, 최소 360). 높이는 표시 높이 + 헤더 56 + 아래 여백 8이고, 맞춘 폭에서 이름이 헤더 둘째 줄로 가면 그 줄 44를 더한다('헤더').

### 예 (작업 영역이 충분히 클 때)

- 390×844 표시를 Play하면 창 콘텐츠 폭은 406이다. 헤더 오른쪽 무리가 104나 140이면 406에서 이름이 둘째 줄로 가서 창 콘텐츠는 406 × 952(844 + 헤더 100 + 8)이고, 토글만 있으면(68) 406 × 908이다. 어느 쪽이든 콘텐츠 패널은 390 × 844다. 두 모드가 같아 보인다.
- 그 창을 Fit 모드에서 폭 360으로 줄이면 이름이 둘째 줄이라 패널은 R 104·140에서 344 × 844(창이 이미 두 줄), R 68에서 344 × 800(줄이며 둘째 줄로 감)이다. 프레임 문서의 `innerWidth`는 390, `innerHeight`는 844이고, 보이는 프레임은 344 × 744로 줄어 패널 가운데에 놓인다(y 50, R 68에서는 y 28).
- 같은 창을 Responsive 모드에서 폭 360으로 줄이면 `innerWidth`는 344, `innerHeight`는 844다(R 68에서는 800).
- 작업 영역 높이가 창 맞춤 높이보다 작으면 창 맞춤 높이가 작업 영역에서 잘린다. Fit 모드에서는 프레임이 줄어 `innerHeight`가 844로 남고, Responsive 모드에서는 `innerHeight`가 패널 높이가 된다.

### 모드 전환

- 모드를 바꿔도 run을 다시 시작하지 않는다. 입력, 열린 모달, 스크롤, 애니메이션 상태가 남고, iframe 크기만 바뀐다(문서는 `resize`를 받는다). 창 크기도 바꾸지 않는다. 로딩 중에 바꿔도 gen과 10초 시간 제한은 그대로다.
- 보이는 이전 run과 숨은 로딩 run의 iframe은 곧바로 새 모드의 상자로 바뀐다. 각 iframe은 자기 run의 표시 크기를 쓴다. 정지 이미지만 찍힌 자리와 크기를 지킨다.
- Reload와 Retry는 모드를 유지한다. 새 Play(main 창의 Play, 드로어, Back/Forward, 형제 feature의 `doan open --prototype`)도 모드를 유지하고 창 맞춤만 한다.
- 로딩·실패·lost 화면에서도 모드를 바꿀 수 있다.
- 고른 모드는 앱이 도는 동안 main 메모리에 남고, 프로토타입 창을 닫았다 열어도 유지되며, 앱을 다시 시작하면 Fit 모드로 돌아간다(결정 4). 기기에 저장하지 않는다.

### 헤더

- 툴바 줄은 따로 두지 않는다. 모드 선택을 포함해 창의 컨트롤은 모두 헤더에 있다(결정 2). 콘텐츠 패널과 그 아래 8 여백은 지금 그대로다.
- 헤더는 세 무리다(결정 12): 왼쪽 [Back, Forward, Reload prototype], 가운데 프레임 이름, 오른쪽 [Fit·Responsive 토글, Export prototype, 대화 버튼]. Export는 형제 feature `prototype-cli-export`가, 대화 버튼은 `prototype-conversation`이 더하고, 이 feature는 그 자리를 둔다.
- 왼쪽 무리는 지금 헤더 그대로다: Back x88, Forward x124, Reload x160(32 버튼, 간격 4), 끝 x192.
- 오른쪽 무리는 창 오른쪽 끝에서 16 안쪽에 붙고, 항목 사이는 4다. 무리 폭(R)은 토글만 있을 때 68, Export까지 104, 대화 버튼까지 140이다.
- 프레임 이름 캡슐은 두 무리 사이를 양옆 8씩 남기고 채운다: x200부터 창 폭 − 24 − R까지, 폭은 창 폭 − 224 − R이다. 이름은 그 공간의 가운데에 놓인다(창 가운데가 아니다). 잘린 이름은 지금처럼 말줄임하고 tooltip에 전체 이름을 보인다.
- 너비가 모자라면 이름이 먼저 물러난다(결정 9). 캡슐의 가장 좁은 폭은 80이다: 지금 캡슐의 padding 10 × 2, 간격 8, chevron 16을 빼고 글자 자리 36이 남아, 보통 이름의 세 글자와 말줄임표가 들어간다(body-sm Geist에서 "Che…" 33.7, "Mob…" 36.4). 두 무리 사이가 80보다 좁으면(창 폭 < R + 304) 캡슐이 헤더 둘째 줄로 간다. 둘째 줄은 높이 44(캡슐 36 + 아래 8)이고, 캡슐은 x16부터 창 폭 − 16까지 채우며(이름은 가운데) y56에 놓인다. traffic light와 두 무리는 첫째 줄에 남고, 헤더는 100, 콘텐츠 패널은 y100에서 시작한다. 이름은 언제나 보이고 프레임 메뉴는 언제나 열 수 있다.
  - 첫째 줄에 남는 창 폭: R 140(세 항목 모두) 444부터, R 104(대화 버튼 전) 408부터, R 68(토글만) 372부터. 그보다 좁으면 둘째 줄이다.
  - 창 폭은 사람이 끌 때만 경계를 지난다. 그때 같은 캡슐이 줄을 옮기고, 콘텐츠 패널이 애니메이션 없이 44만큼 내려가거나 올라간다(다른 창 크기 변경과 같다, Fit 모드는 다시 줄이고, Responsive 모드는 문서가 `resize`를 받는다). 포커스와 열린 프레임 메뉴는 캡슐에 남고 메뉴는 캡슐을 따라간다. 줄 수는 창 폭으로만 정하므로 첫 view 전에도 둘째 줄 자리가 있다.
  - DOM 순서가 그대로라 Tab 순서도 줄과 상관없이 같다.
  - 예(R 140): 640 창 첫째 줄 캡슐 276, 520 창 156, 444 창 80, 443·406·360 창은 둘째 줄(411, 374, 328).

#### Reload prototype

- 지금 헤더의 자리(x160)와 동작 그대로다: 프레임을 다시 시작하고(입력, 열린 모달, 스크롤, 애니메이션이 처음으로 돌아간다), 창 크기와 모드를 유지하고, 기록에 남지 않고, 단축키가 없고, 실패 화면에서는 Retry와 같은 일을 하고, 첫 view가 오기 전에는 `disabled`다. 이름과 tooltip "Reload prototype", 아이콘 `RotateCw`도 그대로다.

#### Fit, Responsive 토글

- Fit과 Responsive는 두 아이콘 버튼을 한 트랙으로 감싼 토글이다(결정 11). 트랙이 두 버튼을 Export·대화 버튼과 나누므로 구분선은 없다. 모습과 치수는 design.md '모드 토글'.
- 버튼은 "Fit"과 "Responsive"이고 하나만 눌린다(`aria-pressed`). 접근 이름은 각각 "Fit", "Responsive"이고, 토글 묶음은 `role="group"`에 이름 "Viewport"다. 눌린 버튼을 다시 눌러도 그대로다.
- Fit의 tooltip은 "Fit 390 × 844 to the window"처럼 재생 중인 프레임의 표시 크기와 맞추는 대상(창)을 말하고(일반형 "Fit <w> × <h> to the window", 표시 크기를 모르면 "Fit to the window"), Responsive의 tooltip은 "Responsive"다(결정 6).
- view가 오기 전에는 두 버튼 모두 `disabled`이고 눌린 버튼이 없다. Reload의 `disabled`와 같다.

#### Export prototype

- 오른쪽 무리에서 토글 다음 자리만 둔다. 헤더의 다른 아이콘 버튼과 같은 32 버튼이고 Tab 정지를 따로 갖는다. 이름, 쓸 수 없는 이유, 저장 패널, 토스트, 저장 패널 뒤 포커스 복귀 같은 상태와 동작은 `prototype-cli-export`가 정한다.

#### 키보드, 포인터, Esc

- Tab 순서는 헤더의 왼쪽부터다: Back, Forward, Reload, 프레임 이름(첫째 줄이나 둘째 줄), 토글, Export, 대화 버튼, 그다음 프레임 콘텐츠, (대화 패널). 상태 overlay가 덮은 동안에는 헤더 → 장면 버튼(Retry, Close, Details)이다.
- 토글은 Tab 정지 하나이고, 눌린 버튼이 갖는다. ←/→는 두 버튼 사이로 포커스만 옮기고(누르지 않는다, 끝에서 돌아가지 않는다), Enter/Space가 누른다. view가 오기 전에는 두 버튼이 `disabled`라서 토글에 Tab 정지가 없다.
- 포인터로 Reload, Fit, Responsive, Export를 눌러도 포커스는 옮겨 가지 않는다(결정 10). 모드를 바꿀 때는 프레임 안 입력의 포커스와 blur로 닫히는 메뉴가 그대로 남고, 그 뒤의 키는 계속 프레임으로 간다. Reload를 누르면 run이 새 iframe으로 바뀐다. 누르기 전 포커스가 프레임 안이나 페이지에 있었고, 새 run의 프레임이 ready가 될 때도 포커스가 페이지에 있으면 포커스가 새 iframe으로 간다. 그래서 그 뒤의 키도 프레임으로 간다. 누르기 전이나 ready 때 포커스가 다른 곳(대화 composer, 헤더, 키보드로 온 컨트롤 등)에 있으면 그 자리에 둔다(결정 13). 새 run이 실패 장면을 띄우면 지금 규칙대로 포커스가 장면 제목으로 간다. 헤더 컨트롤에는 키보드(Tab)로 왔을 때만 포커스가 있다.
- 글자 단축키는 없다. 프로토타입 창의 키는 프레임 콘텐츠로 가기 때문이다(PRODUCT §5 item 2).
- Esc: 헤더 tooltip이 열린 채 Esc를 누르면 tooltip이 닫힌다. 그때 프레임 메뉴도 열려 있으면 메뉴도 닫히고 포커스는 프레임 이름으로 간다(메뉴가 열린 채 Esc를 누를 때의 지금 규칙과 같다). 그 밖의 Esc는 지금과 같다.

#### 상태

- 로딩·실패·lost 화면의 overlay는 콘텐츠 패널만 덮으므로 헤더는 그대로 쓸 수 있다.

## 완료 조건

- 툴바 줄이 없고, 헤더가 위 '헤더'의 배치다: Back x88, Forward x124, Reload x160, 오른쪽 무리는 끝에서 16 안쪽에 간격 4, 토글은 68 × 36(트랙 `--affordance-backdrop-hover`, 안쪽 2, 32 버튼, 눌린 버튼 `--surface-panel`과 `--shadow-panel`이고 누르는 동안에도 같음, 누르는 동안의 눌리지 않은 버튼 `--affordance-backdrop-pressed`). 이름 캡슐은 첫째 줄에서 x200부터 창 폭 − 24 − R까지이고, 그 폭이 80보다 작으면 둘째 줄(x16부터 창 폭 − 16까지, y56, 헤더 100)에 있다(640·520·406·360 창과 R 140·104·68의 경계 양옆, `/design-sync` 측정과 단위 테스트).
- 헤더의 Reload가 지금처럼 동작한다: 다시 시작, 창 크기와 모드 유지, 기록 없음, 실패 화면에서 Retry와 같음, 첫 view 전 `disabled`(단위 테스트와 실제 앱 확인).
- 390×844를 Play하면 창 콘텐츠가 R 68에서 406 × 908, R 104·140에서 406 × 952다(작업 영역이 충분할 때, 단위 테스트와 실제 앱 확인).
- 처음 연 프로토타입 창은 Fit 모드다. 위 '예'대로 Fit 모드에서 창 폭을 360으로 줄이면 `innerWidth` 390, `innerHeight` 844이고 보이는 프레임이 344 × 744로 가운데에 놓인다. 줄인 상태에서 프레임의 버튼을 누르면 그 버튼이 눌린다(단위 테스트와 실제 앱 확인).
- Responsive 모드에서 창을 640에서 480으로 줄이면 프레임 문서의 `innerWidth`가 624에서 464가 된다. 표시 폭 240 프레임도 패널 폭을 채운다(단위 테스트와 실제 앱 확인).
- 모드를 바꿔도 run의 gen이 바뀌지 않고, 프레임 안의 입력 값과 열린 모달이 남는다. 프레임 입력에 포커스가 있을 때 포인터로 모드를 바꾸면 포커스가 그 입력에 남는다. 포인터로 Reload를 눌러도 포커스가 Reload로 가지 않고, 프레임 입력에 포커스가 있었고 ready 때까지 다른 곳으로 옮겨 가지 않았으면 새 프레임이 ready일 때 포커스가 새 iframe에 있다. 그사이 포커스가 다른 곳으로 갔으면 그 자리에 남는다(단위 테스트와 실제 앱 확인).
- Reload, Back/Forward, 드로어 선택 뒤에도 모드가 같고, 창을 닫았다 다시 Play해도 같다. 앱을 다시 시작하면 Fit 모드다(단위 테스트).
- 실패·lost 상태로 바뀌며 찍힌 정지 이미지가 Fit 모드에서는 줄인 프레임 자리와 크기 그대로 보이고, 그 뒤 모드를 바꿔도 그 자리에 남는다(main이 찍은 상자를 정지 이미지와 함께 보낸다, 단위 테스트와 실제 앱 확인).
- 토글은 Tab 한 번으로 눌린 버튼에 오고, ←/→로 다른 버튼에 가며, Enter/Space로 누른다. 포커스가 있는 버튼의 눌림이 바뀌어도, view가 처음 와서 버튼이 쓸 수 있게 바뀌어도 같은 요소로 남는다(POSTMORTEM 2026-11-13). 창 폭이 경계를 지나 이름이 다른 줄로 가도 같은 캡슐 요소라서 포커스와 열린 프레임 메뉴가 남는다. tooltip이 열린 채 Esc를 누르면 tooltip이 닫히고, 프레임 메뉴도 열려 있었으면 메뉴가 닫히고 포커스가 이름에 간다(단위 테스트와 실제 앱 확인).
- PRODUCT §5 item 2 'Prototype window'(특히 'Header'), ARCHITECTURE §3 'Prototype window'('One window', 'Rendering in place', 'Timeout and kill'의 캡처, 'Fit')와 §7 'Prototype window IPC', DESIGN.md 'Frame prototype', BACKLOG.md의 해당 항목이 새 동작을 현재 규칙으로 적는다.

## 결정 (사용자 확인)

1. **Fit 모드에서 패널이 표시 크기보다 작을 때**: 비율을 지켜 줄인다(확대 없음). 구현 전에 PoC로 확인한다.
2. **컨트롤 자리**: 툴바 줄을 따로 두지 않고 모두 헤더에 둔다. 창 맞춤과 콘텐츠 패널은 지금 그대로다.
3. **기본 모드**: Fit 모드. 표시 크기 약속(convention 14, PRODUCT)은 그대로이고, Responsive 모드는 고를 때만 창을 따른다.
4. **모드 기억**: 앱이 도는 동안 main 메모리. 창을 닫았다 열어도 유지되고, 앱을 다시 시작하면 기본값이다.
5. **Responsive 모드에서 표시 폭이 344보다 좁은 프레임**: 패널을 채운다. 형제 feature `prototype-conversation`의 같은 문장은 맞춰야 한다(design.md '결정 영향').
6. **이름**: "Fit"과 "Responsive". Fit의 tooltip은 "Fit 390 × 844 to the window"(일반형 "Fit <w> × <h> to the window", 표시 크기를 모르면 "Fit to the window"), Responsive의 tooltip은 "Responsive". 크기는 프레임의 것이고 맞추는 대상이 창이라는 점이 드러나게 한다(크기 뒤에 바로 "to"가 오면 창을 그 크기로 바꾼다고 읽힌다).
7. **크기 표시**: 없다.
8. **폭 프리셋과 드래그 손잡이**: 이번에는 없다.
9. **좁은 헤더**: 너비가 모자라면 프레임 이름 캡슐이 헤더 둘째 줄로 내려가고 헤더가 그만큼 두꺼워진다. 첫째 줄에 남는 경계는 캡슐이 읽히는 가장 좁은 폭(80)까지 낮춘다. 이름은 창 가운데가 아니라 두 무리 사이의 가운데에 놓인다.
10. **포인터 누름과 포커스**: 헤더의 Reload, Fit, Responsive, Export를 포인터로 눌러도 포커스를 옮기지 않는다. PoC에서 확인한다.
11. **모드 토글**: Fit과 Responsive 두 아이콘 버튼을 한 트랙으로 감싼 토글이다(새 프리미티브). 감싼 트랙이 영역을 나누므로 구분선은 없다.
12. **헤더 내용**: 왼쪽 [Back, Forward, Reload prototype], 가운데 프레임 이름, 오른쪽 [Fit·Responsive 토글, Export prototype, 대화 버튼]. Reload는 지금 자리와 동작 그대로다. Export의 상태와 동작은 `prototype-cli-export`가, 대화 버튼은 `prototype-conversation`이 정하고, 이 feature는 자리를 둔다.
13. **포인터 Reload 뒤 포커스**: 헤더 Reload를 포인터로 누르기 전 포커스가 프레임 안이나 페이지(body)에 있었고, 새 run의 프레임이 ready일 때도 포커스가 페이지에 있으면 포커스를 새 iframe으로 옮긴다. 누르기 전이나 ready 때 포커스가 다른 곳(대화 composer, 헤더, 키보드로 온 컨트롤 등)에 있으면 그대로 둔다. 창의 키가 프레임 콘텐츠로 간다는 규칙(PRODUCT §5 item 2)을 지키고, 실패 장면에서 포커스가 장면 제목으로 가는 규칙과 짝을 이룬다. 형제 feature `prototype-conversation`의 결정 17(reload는 composer의 포커스를 빼앗지 않는다)도 지켜진다.
