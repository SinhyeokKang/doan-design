# formats — spec

MVP 피처 1번(PRODUCT §5 피처 분할). 앱(TypeScript)과 CLI(Go)가 함께 읽고 쓰는 형식 세 가지를 JSON Schema로 정하고, 같은 픽스처로 두 구현을 묶는다.

## 사용자

- **에이전트**(CLI·MCP를 쓰는 쪽): `doan comments`가 돌려주는 코멘트 상태, `--json` 봉투, 종료 코드가 런타임과 버전에 상관없이 같다. 그래서 기계적으로 읽을 수 있다.
- **사람**(앱에서 보고 코멘트하는 쪽): 앱에서 남긴 코멘트를 CLI가 똑같이 읽는다. 다른 머신에서 pull해도 상태가 같게 접힌다.
- **doan 개발자**: TS와 Go 구현이 어긋나면 테스트가 잡는다.

## 문제

- 형식의 원본이 아직 없다. ARCHITECTURE §11 'Shared formats'는 "JSON Schema가 원본, TS·Go가 같은 픽스처로 테스트"라고 정했지만, 스키마 파일도 픽스처도 없다.
- 코멘트 이벤트·config·CLI 응답의 필드가 문장으로만 정해져 있다(PRODUCT §5 · ARCHITECTURE). 이대로 TS와 Go가 각자 구현하면 필드 이름·접기 규칙이 갈라진다.

## 완료 조건

1. 스키마 세 개가 있다: 코멘트 이벤트, `.doan/config.json`, CLI 응답 봉투. 셋 다 형식 버전 `v`를 가진다.
2. 유효·무효 픽스처가 있고, TS와 Go 검증기가 둘 다 같은 판정(유효/무효)을 낸다.
3. 접기 픽스처(이벤트 JSONL → 기대 상태 JSON)가 있고, TS와 Go 접기 함수가 둘 다 기대 상태와 바이트 단위로 같은 JSON을 낸다(정렬된 키, 정해진 순서).
4. 접기가 다음을 만족한다(각각 픽스처로 덮는다):
   - 줄 순서와 무관하다. 같은 이벤트 집합을 섞어도 결과가 같다.
   - 같은 이벤트 `id`가 두 번 있어도 한 번으로 친다(union 머지로 생기는 중복).
   - 삭제된 코멘트는 결과에 없고, 삭제 뒤 이벤트는 무시한다.
   - 에이전트가 낸 수정·삭제·다시 open은 무시하고 경고로 보고한다(PRODUCT §5: 수정·삭제는 사람만, 에이전트는 resolve만).
   - 모르는 `v`를 만나면 그 이벤트를 무시하고 "더 새 버전의 Doan이 쓴 기록" 경고를 낸다.
5. PRODUCT §6 PoC 5(`merge=union`)가 통과했다.

## 비목표

- CLI 명령 자체(`doan comments` 등)와 명령별 `result` 모양 — 2번 `cli-core`.
- 앵커를 실제 DOM에서 다시 찾는 로직(재앵커링) — 7번 `comments-ui`.
- `doan active` 응답 모양 — 6번 `select-inspect`.
- JSONL 압축(PRODUCT §8: MVP에서 하지 않는다).
- 스키마로 TS·Go 타입을 생성하는 코드 생성기. 필요가 보이면 그때 정한다.
