# Doan Design — Product plan

> Source of truth for product judgment: problem, users, scope, core loop and MVP. It describes the product as it is now; history lives in git.
> Structure, formats and conventions live in [ARCHITECTURE.md](./ARCHITECTURE.md); measured UI values live in [DESIGN.md](./DESIGN.md). [README.md](../README.md) is the public introduction and is not a decision source.

## 1. Problem

The design drafts that coding agents make live outside the code, in external design services. This causes five problems; the arrow after each names the §3 'In scope' item that addresses it.

1. **Conversations split.** Design-draft and implementation conversations pile up separately in two tools, and some runtimes cannot reach the draft at all (Codex could not use Claude Design or DesignSync). → Deliver
2. **Agents cannot read design drafts properly.** Large files get truncated (DesignSync `get_file` caps at 256 KiB), and the agent does not know where the human pointed. → Show · Let humans point
3. **Design drafts do not know the code.** They do not know the real tokens or implementation, so they drift from it. → Tie to code · Check
4. **Records are locked into an external service.** When the service shuts down, the drafts and their feedback disappear: standalone Claude Design shuts down on 2026-12-14 without migrating chats and comments (support.claude.com/en/articles/17440474). → Show (the canvas is a file in the repo) · Conversation (kept on this device)
5. **A draft cannot be shown to someone outside the repo.** A canvas reads the repo's token CSS, shared CSS and assets by relative paths, so sending the HTML file alone does not open it, and a reviewer without the repo or Doan cannot see it. → Export

Source: the Malmoi case in the README background.

## 2. Users

The primary users are external users in general; installation, onboarding and documentation are in product scope.

Doan's own agent connections cover five providers — Claude Code, Codex, Cursor, Antigravity and GitHub Copilot — with one account each (§3 In scope 7); first run signs in to them and selects a project. Opening the packaged app from Applications also sets up the `doan` command and skill, with no setup screen, for the same five agents' sessions outside Doan (§5 item 0 'Agent setup'). A user who has only the app can ask their own agent to run first run, or to set up a repository for Doan, through `doan onboarding` (§5 item 0).

A canvas can also reach people who use neither Doan nor the repo, such as a reviewer or a stakeholder: they receive an exported file and open it in a browser (§3 In scope 8).

## 3. Scope

### In scope

1. **Show.** The app shows the canvas the agent wrote into the repo, with zoom and frame jumps. The canvas page has no inspector screen; a selection's styles and tokens are still collected for its planned new place (§5 item 4).
2. **Let humans point.** The human selects an element or frame, and puts frames, elements and spots inside frames into a message as chips (§5 item 6). The agent points back the same way: a frame or element its reply names in the app shows as a chip that moves to it. Comments in repo files have no app screen; the CLI still reads and resolves them (§5 item 5).
3. **Deliver.** The agent receives the person's message with its anchors, or reads the selection (`active`) and existing comments through the CLI and skills, applies them and resolves the comments it applied. The app sets up the CLI and skill for the five providers' own sessions.
4. **Check.** `doan check` statically checks the canvas's conventions, tokens and external resources.
5. **Tie to code.** The canvas uses the repo's real token CSS, and frames point to implementation files (`data-doan-implements`).
6. **Conversation.** A human message starts a live conversation with the installed, logged-in Claude Code or Codex, either resuming the drawing session without forking or explicitly starting a new one. Each canvas has one current conversation; starting another archives the previous one. A project also holds conversations bound to no canvas (project conversations); promotion, restore, queueing and the anchor limit are §5 items 1 and 6. A queued message is still the person's message, not Doan waking the agent (Out of scope 4). Session associations and conversation events stay on this device, outside the repo. A person can delete a conversation from this device; the agent's own session files stay.
7. **Agent authentication.** Users sign in from Doan and keep a Doan-specific connection, independent of Orca's or a terminal's login, with at most one account per platform. All five providers use their official login in a Doan-owned profile, keep credentials on this device, sign out locally and run new and canvas conversations on the connected account ([ARCHITECTURE §7 'Agent authentication'](./ARCHITECTURE.md#agent-authentication)).
   - Sign-in, check and sign-out happen in first run (agent sign-in → local folder or GitHub repository URL → Home) and, since first run cannot be reopened, afterwards in Settings > Agents (§5 item 0). Home's agent picker sends the person there (§5 item 1); conversations offer no sign-in.
   - A replacement sign-in that does not finish keeps the stored connection and its verified state.
   - Independent credentials do not establish external-session portability.
8. **Export.** The person saves a canvas as one HTML file that opens in a browser without Doan, the repository or a network, and sends it themselves. The app offers it from the sidebar's canvas row menu and the CLI as `doan export` (§5 item 1 'Canvas row menu', item 3 'Export and viewer', item 12).

Doan handles installation and onboarding for these capabilities. Where conversations show is §5 items 0–3.

### Out of scope

1. **Drawing.** The agent draws the design draft. Doan is not a vector tool (Figma) where humans draw shapes.
2. **Enforcing a canvas format.** The agent decides sections, notes and layout. Doan's conventions are only the minimal attributes Doan reads (canvas, frame and element ids, frame title, implementation path, board width).
3. **Multiple accounts per agent platform.** Account pools and multiple-account selection are excluded (one account: In scope 7). Resuming a session found through a shell `doan check` association uses the installed, logged-in Claude Code or Codex CLI and its own profile (legacy external path). GitHub authentication for browsing or cloning repositories is deferred; Copilot's GitHub-based agent sign-in is separate. Cloning a GitHub URL uses the user's existing Git credentials and adds no GitHub sign-in, token storage or repository listing.
4. **Autonomous agent wake-up.** Only a human message starts agent work; Doan does not initiate it on its own. Terminal work signals (`doan work`) only show work (a `start` may add another worktree of a registered project to its list, §5 item 1), and a `doan://` link or `doan open` only moves (item 3 'Deep links'); none of them wakes an agent.
5. **Server.** No accounts, sync or hosting. Sharing happens through git, or through an exported file the person sends themselves (In scope 8); Doan uploads and serves nothing, and the web only serves as the download path.
6. **Git operations.** The agent makes commits and branches. Exception: first run and the Add Projects page clone a GitHub repository URL the user entered, with their existing Git credentials, into a destination they confirmed (§5 items 0 and 1). Doan runs no other git command (it reads remotes from `.git/config`) and does not pull, fetch, commit or branch.
7. **Simultaneous human/agent file editing.** A person talks while the agent edits and the app reloads; the person does not draw or directly edit the canvas in Doan. Exception: after a confirmation, Move to Trash moves one canvas file, and its comment file when it goes with it, to the macOS Trash (§5 item 1 'Canvas row menu'). The app writes no canvas content.

### Agent conversation foundation contract

What the conversation runtime promises. The UI is §5 items 1–3; SDK, transport, processes, admission and IPC are [ARCHITECTURE §7 'Agent conversation runtime and IPC'](./ARCHITECTURE.md#agent-conversation-runtime-and-ipc).

- **Transport and evidence boundary.** Claude Code and Codex conversations run on the user's installed CLI; Doan bundles no replacement, and a missing executable is refused. Required CLI versions are verified minimums (Claude Code 2.1.312, Codex 0.164.0), not pins: a newer CLI runs until a new session shows a protocol Doan cannot read. A below-minimum or unreadable version refuses a new session (`runtime_unsupported`) and resume or send (`session_unavailable`). Stored sessions stay resumable from fixed floors that do not follow the minimums, and a conversation's stored session resumes after an app restart.
- **Association recording.** Only a shell `doan check`, passing or failing, records which session changed which canvas. It never changes check output or exit codes, silently skips what it cannot record, and asks agents to manage no session IDs (ARCHITECTURE §4 'Shell check session associations').
- **Session identity and paths.** Every association and app-created conversation records its profile (`configDir`); an unset or empty configuration variable means HOME/.claude or HOME/.codex. Records are untrusted: resume requires the record's profile to match the currently selected one and its cwd to lie inside the same project root. A record never selects an arbitrary profile or copies credentials; a mismatch makes resume unavailable, never a fallback to another profile, cwd or session.
- **Resume and permissions.** Within the verified scope, resume continues the same session and transcript; Doan never forks or silently starts a new session. A turn runs in the permission mode the person picked (item 1 'Permission picker'); Default applies the user's own permission and sandbox settings. Doan picks no mode itself, with one exception: after the person approves a Claude plan, the conversation follows the mode the SDK reports, except Full access, which reads as Default. Doan forwards the runtime's real approval requests and invents none. Denying is not stopping, and a stop the person asked for is not a successful turn. The verified allow/deny cases do not prove every policy/hook combination.
- **Live terminal policy.** Before each resume or send Doan rechecks the session: one open in a terminal is `session_in_use`, one it cannot verify is `session_unavailable`, and a terminal session that cannot be continued is not offered. This is a best-effort check, not a lock. A Codex session counts as open until Codex releases its writer lock, about a minute after the terminal exits. Doan never kills the user's Codex daemon.
- **Launch environment.** Doan behaves the same however it was launched: the environment of a terminal that launched it (another tool's per-terminal agent profiles, session ids, hook variables) never reaches the login-shell probe or the agents, CLIs and git it runs. The profile therefore comes from the person's shell configuration; a `CLAUDE_CONFIG_DIR`/`CODEX_HOME` given only in a launching terminal's environment does not select it.
- **Events and ownership.** Conversation events are stored on this device as they happen; a reload keeps them and the live turn. After a restart, unanswered approvals expire and unfinished turns show as interrupted. Doan runs one turn per session at a time and never forks or takes over a session. Doan-connection conversations (In scope 7) follow the same rules.

## 4. Core loop

### Unit of review: one spec = one canvas

- One spec (one ticket) — user flow, per-state guides for blocks and components, layout and spacing, copy — is reviewed on **a single canvas** holding **multiple frames**; the human zooms and picks a frame.
- **One canvas = one HTML file in the repo.** The agent decides whether to keep shared shells or assets separately.
- **Frames are what the agent marks with `data-doan-frame="id"`**; the agent decides layout and look. The frame list, jumps, anchors and comment targets use this id.
- **Ids do not change**, so anchors, comments and conversations follow a moved file or renamed title. The agent names canvas and frame ids when it creates them, and `doan check` catches duplicates and omissions (ARCHITECTURE §1 'Conventions').
- **A frame can point to its implementation file** (`data-doan-implements`), per frame, since each frame has its own.
- **The agent organizes the inside of a canvas.** Doan fixes no section categories, note format or layout. References only:
  - A Figma design guide (Skillflo B2E, FCLXP-13938 learning dashboard revamp) places `user-journey-map` · `template-guide` · `layout-guide` · `i18n-guide` side by side.
  - Claude Design's canvas guide (`Language Request Todo.dc.html`, Malmoi project): one page per spec, an intro, then numbered frames, each a screen render beside note cards holding design decisions and their rationale.

### Loop

1. **The agent writes the canvas** at `.doan/canvases/<spec>.html` and checks it with `doan check`.
2. **The human views it in the app**, which live-reloads when the file changes.
3. **The human points** with chips (§5 item 6) or a selection. Existing comments in `.doan/comments/` stay readable to the agent; the app has no comment screen.
4. **The human talks to the agent**, in the canvas's conversation panel, where chips arrive as anchors, or to their own agent outside Doan, which finds the target via `active`. Doan does not wake the agent itself.
5. **The agent applies it**: anchors, or `doan active` and `doan comments` → edit → `doan check` → `doan comment resolve` for applied comments. Back to 2.

## 5. MVP

What the human does is **view + point + talk**; approval is deferred until after the MVP. Human-facing text (app screens, onboarding, menus, CLI messages, the guide, the skill stub, docs prose) names the product Doan; only places that already used the full name keep Doan Design (the window title, the `doan skill` guide's heading and the titles of PRODUCT.md and ARCHITECTURE.md), and the full name is not added elsewhere. Commands, paths and identifiers stay lowercase (`doan` and its subcommands, `.doan/`, `data-doan-*`, appId `design.doan.app`, userData `doan`); the app bundle is `Doan.app`. App UI copy is English; a folder is called "Project" on screen, while code names and docs keep "folder".

1. **Home and project workspace**
   - Launch restores the last Home or workspace screen, canvas (by canvas ID, then path), viewport, tree expansion and the last canvas tool (Select or Hand) from device-local state; invalid state, a missing or problem root, or a 10-second loading timeout starts on Home. Selection is never restored.
   - The sidebar lists a Home row (current on Home), then the projects and the selected worktree's canvases; the loaded project's row opens its Overview from a canvas; from anywhere every other project row opens that project's Overview, never its last canvas, and unfolds it. A project row never folds: on hover or keyboard focus a chevron takes its thumbnail's place, and only that chevron (or ←/→) folds or unfolds a project, the loaded one included, without moving; the loaded project's fold lasts only while it stays loaded and is not remembered across relaunch. Registered roots sharing a Git common directory form one project group, named by its main worktree's folder (else its first registered root's); same-named groups are not disambiguated. Only registered worktrees appear, and Doan creates or switches no branches. A `doan work start` from an unregistered worktree of a registered project's Git repository, at the same doan root path, registers that worktree at the end of the group's worktree list; it never adds a project or another doan root of the same checkout, and never changes the screen, the selected worktree or Back/Forward. An auto-registered worktree whose folder is gone leaves the list silently, with no Missing row or toast. One that is still on disk but cannot be listed (not set up, config error, CLI or permission error) stays registered but hidden until it lists again, so it never shows as a problem row. While it is still being read after launch it keeps its remembered canvas and the group's selection. Adding, opening or locating it by hand makes it an ordinary registered worktree. When the auto-registered worktree on screen leaves or hides, Doan goes to the worktree selected before it in that group, else the main worktree, else the first listed one, even when that one has a problem; it opens the same canvas path when that worktree lists it, else its Overview, and shows no toast. A page opened from that worktree's workspace returns to the same destination when left. Remove from Doan removes the group's auto-registered worktrees with the rest; removing one worktree alone is not offered. Canvas labels are file stems, without a frame tree, listed newest-modified first within each group; equal modified times follow natural stem order, then path, and rows without a modified time come last in that order. A row moves as its file changes, and keyboard focus and the current canvas stay on the same canvas. Modified times set by a clone or pull count like any other, because the agent or person runs those Git operations, not Doan (§3 Out of scope 6). A project menu selects a registered worktree (restoring its last canvas and view, or Overview) and offers Overview, Show in Finder, Project Settings and Remove from Doan. Going Home keeps the loaded workspace, selection and draft, including `doan active`.

   - The sidebar can be hidden and shown again from the header's Hide/Show sidebar button (first in the header, before Back and Forward), View > Hide/Show Sidebar or ⌘B, including while the composer has focus. One state covers every screen (Home, workspace, Settings, Add Projects, Project Settings) and is remembered on this device; hidden, the body panels start at the window's 8 px margin. The shortcut is off under a modal or first run and stays on while a page lock is open. Hiding keeps what the sidebar remembers (expanded projects, closed groups, width). When hidden, the Show sidebar button carries the sidebar slot's strongest signal for Home and canvas conversations, in the order permission request, working, then unseen ending, as a dot and in its accessible name ("Show sidebar, needs your answer" / "agent working" / "new activity"); canvas notices add none, and showing the sidebar removes the dot.      - Seen: a project conversation is recorded as seen only while the Overview shows it and the window has focus; opening a workspace or Overview records none.
     - While another conversation shows, a project conversation of the same root that waits for an answer raises a toast with Open.
     - Problem states: a project that is a problem when entered shows its problem screen. An open Overview whose project becomes a problem keeps the thread readable with the status band and Go Home, and holds Send.
     - **Canvas conversations** (right panel): resizable from its start edge like the canvas page's panel (same limits, 280 px default, a double-click restores 280), with its width remembered on this device apart from the canvas panel's; only canvases that have a current conversation, most recent activity first (ties by canvas path); the rest are in the sidebar. A row shows the canvas thumbnail, the conversation's provider and status (needs your answer, working, finished and not seen), a short time and a preview (DESIGN.md 'Project Overview'). A row opens its canvas with the panel unfolded on that conversation and focus in its composer.
       - Special rows: a canvas no longer listed shows only while its conversation has work left; a canvas ID several canvases use says to run `doan check`; neither opens. An unreadable canvas says to run `doan check` and opens.
   - Moved and duplicate canvases: when the open canvas's file moves and exactly one listed canvas has its canvas ID, that canvas stays open with its view, selection, tree state, conversation panel, draft and any pick, and `doan active` returns the new path. With no canvas holding the ID it counts as removed and returns to Overview with a toast; with two or more it returns to Overview with a toast and a notice to run `doan check`. A saved canvas missing at restart returns to Overview with a toast (mechanism: ARCHITECTURE §3 'Moved canvas'). Exception: when the person moved the open canvas to the Trash (item 1 'Canvas row menu'), no other canvas with its ID is followed or counted as a duplicate, and the Trash toast replaces the removal toast.
   - **Export and viewer.** Export (item 1 'Canvas row menu'; the CLI form is item 12) writes one HTML file: the canvas with every repo file it needs copied in as data — token and shared CSS with their `@import`s and `url()`s, images, fonts, local scripts and SVG sprites — inside a light viewer page. It opens in a browser (Chromium and Safari are the targets) without Doan, the repository or a network, at the canvas's `doan:width`. External URLs stay links and load only online.
     - Only what the app would serve is included. A local reference outside the repository or the serving scope (directly or from inside a CSS file), a missing direct reference, a local document in an `iframe`, `frame`, `object` or `embed`, or a canvas without one valid `doan:width` refuses the export, and the refusal lists the references. A missing reference inside a CSS file is left as it is, because it fails in the app too. A relative `url()` held in a custom property is looked up where the app looks it up: from each stylesheet that puts the property into a real property with `var()`. When those name different existing files, the export is refused, because which one shows depends on the element. Local `<a href>` and `<form action>` targets stay as written and are reported as links that won't work in the file. JavaScript is not read, so a file only a script fetches or imports is not included.
     - A result over 50 MiB is refused and names the largest files. An existing output file is replaced only on request, and the output may not sit inside a `.doan` directory, where it would be listed as a canvas.
     - The viewer shows the canvas name, a frame drawer and a zoom control, and nothing else: no selection, tools, conversation, comments or Reload. The drawer lists frames in document order, up to the first 1,000 with a count of the rest, and picking one fits that frame; a canvas with no frames shows a disabled "No frames". Zoom offers Fit, 100%, 50% and 200%, buttons, ⌘/Ctrl-wheel, and ⇧1 (Fit) and ⇧0 (100%) while the viewer has focus. The canvas height follows its content as in the app; if its script never reports a height, the viewer stops at the last one after 5 seconds and fits. Without JavaScript (Quick Look, a mail preview) the canvas shows its top at `doan:width` with a line saying to open the file in a browser.
   - **Row read errors**: a canvas row whose file `ls` could not read (item 9) stays in the tree, says to run `doan check`, and shows the raw error only on request. One unreadable file does not make the project a whole “Config error”.
   - Go > Quick Open… (Cmd+K) searches canvases and frames across all saved healthy projects/worktrees, including from Home. All query tokens must match, case-insensitively; prefix ranks above word start above substring, then the current root, other worktrees of the same repository, other repositories; at most 50 results, grouped per root in order of each root's best match. An empty query shows current-root canvases in a workspace, or all canvases on Home. All / Canvases / Frames tabs reset to All on every open and filter before the cap. A same-canvas result only jumps; other canvases/roots clear selection. Behaviour and copy: [DESIGN.md](./DESIGN.md#quick-open).
   - Overview thumbnails are captured lazily for the listed rows, visible first, with a device-local cache (ARCHITECTURE §3). They are human navigation previews, not the deferred agent screenshot/ref-comparison feature.
4. **Selection and inspector**
   - The human selects an element or frame by an ordinary click in Select; hover only highlights candidates. In Hand clicks neither select nor clear (item 2 'Toolbar'). Ordinary clicks suppress canvas actions; Option-click uses the canvas without changing the selection (ARCHITECTURE §3 'Selection and inspector').
   - The canvas page shows no Inspector, no Canvas info and no panel for the selection. Inspection values are still collected on selection; the inspector's new place is planned (`docs/features/buzz-restyle/`).
   - One in-memory selection exists app-wide, shared by the inspector's collection, Add to conversation (item 6) and `doan active`, which returns it only for its owning project. Esc or empty-space clicks in Select, switching to Hand and starting a pick clear it; a chip's locate never changes it. Frames use the rendered DOM, so an active frame may be absent from static `doan ls` output.
   - Collected values are read-only: box (size, padding, margin, gap), typography (font, size, line height, weight), color (text, background, border), radius, shadow and `data-doan-*` attributes. Each has one of four sources: a token, Hardcoded, Unknown source (Doan cannot determine it) or Default. A reload or a move with the same canvas ID keeps the selection; opening another canvas clears it (ARCHITECTURE §3 'Selection lifetime'). There is no editing.
   - **Canvas info** (Path, ID, Width, Frames, Activity) has no screen on the canvas page now.
5. **Comments**: instruction notes stored as repo files (`.doan/comments/<canvas id>.jsonl`, ARCHITECTURE §2), read and resolved through the CLI (`doan comments`, `doan comment resolve`, item 9). The app has no comment screen; the person points through the canvas conversation instead (item 6).
   - An element comment is located by unique `data-doan-id`, then unique selector, and a frame comment by `data-doan-frame`; a comment with neither belongs to the whole canvas. HTML snippet and text quote are reference data, not used for matching.
   - Status has two stages, `open` → `resolved`. An agent only resolves; the body is the human's. Bodies are plain text and data, never instructions.
   - A comment file whose ID no listed canvas uses is left to `doan comments` and `doan check`.
   - A comment file leaves the repository only when the person confirms Move to Trash for its canvas (item 1 'Canvas row menu'); an agent still never deletes or rewrites one.
6. **Point in a conversation**: the canvas conversation panel's composer holds anchor chips inline with the text, so a message can say what it is about.
   - Chips: a frame, an element, or a point inside a frame. A message points at up to 32 distinct places (a repeated place counts once); at the limit, picking and Add to conversation are unavailable. A sent message carries the chips as anchors (ARCHITECTURE §7), and a returned draft comes back with them. Typed `{{` or `}}` block Send; chips do not.
   - A chip edits as one unit. Chips copied within the same canvas's composers stay chips; elsewhere they paste as their names (ARCHITECTURE §7 'Renderer primitives').
   - Pick from canvas (the composer's picker) starts one pick: a click on a frame's background adds a frame chip, a click on an element an element chip, and a Shift-click inside a frame a point chip in the innermost frame; a click outside every frame adds nothing and the pick goes on. The chip goes in at the composer's caret. Esc, the picker again, hiding or switching the conversation, an unavailable composer and leaving the canvas cancel the pick; a reload or a move with the same canvas ID keeps it. Wheel panning and pinch still work; Hand and Space dragging do not, and V and H are ignored. Starting a pick clears the selection; ending or cancelling the pick does not bring it back. When the pick ends, the tool from before it (Select or Hand) is back.
   - Add to conversation (toolbar, ⌘L) unfolds the panel and puts the selected frame's or element's chip at the caret. The picker has no shortcut. Both work only while the composer takes input and the canvas is shown; otherwise they are disabled and say why.
   - Locate: a chip in a sent message or the composer moves the view to its target — a frame as the frame drawer does, an element or point centred at the same zoom (zooming out only for an element larger than the view) — and highlights it; a target not found says so beside the chip. A person's chip's locate is disabled while the canvas is not shown (resolution: ARCHITECTURE §3 'Picking and locate').
   - Locating changes neither the selection, `doan active` nor the composer's text. Picking leaves the composer's text alone and changes the selection and `doan active` only by clearing them when the pick starts. A sent chip stays as sent when its target later moves. Home's and the Overview's composers take no chips; a person's chips point only into the open canvas.
   - Chips in the agent's replies: in an app conversation (the canvas panel and the Overview) the agent's reply can link a frame or element of a canvas in the conversation's project, and the thread draws it as the person's chip, named from that canvas's frame titles; a chip into another canvas adds ` · <canvas name>`, which is never cut (the label ellipsizes first) and says it will open that canvas. A chip into the canvas on screen locates as a sent chip does (disabled while the canvas is not shown, "No longer in the canvas" under the reply). A chip into another canvas, or any chip on the Overview, opens that canvas as a deep link does — the selection clears, the panel switches to that canvas's conversation, one visit for Back — and moves to the target; a target it does not find leaves just the canvas open. A canvas the project does not have, or has twice, or whose list is still being read or has a problem shows one toast and moves nowhere. A malformed link stays plain text. Terminal sessions and the guide do not learn the form (ARCHITECTURE §7).
7. Tell the CLI the currently selected frame or element (the source of `doan active`).

### CLI `doan`

8. `doan init`: creates `.doan/canvases/` and `.doan/config.json`, sets up `.gitattributes` (union merge for comments, `.doan/` as documentation) and asks for the token CSS path — the terminal form of the app's project setup (Set Up in the sidebar project menu, first run's Set up and continue). It does not install skills: opening the app sets up the skill (item 0 'Agent setup'). It does not add the project to the app either. Agents run it only when the person names `doan init` or when a repository setup request cannot reach the app (item 0 'First run').
9. `doan ls` · `doan comments` · `doan comment resolve` · `doan skill` · `doan config`. They only read and write repo files, so they work without the app. `ls` also reports Git branch/worktrees. One unreadable file does not fail `ls`: it marks the affected rows instead of reporting zero comments, and lists comment files no canvas uses as orphans (ARCHITECTURE §12). `doan comments`, `doan check` and `doan comment resolve` fail as a whole when they cannot read a file they need.
10. `doan active`: returns the frame or element the human selected in the app. Lets the agent find the target from just "fix this". Requires the app to be running. `doan onboarding …` drives first run through the running app; only `onboarding start` and `open` from the bundled CLI may open the app (item 0). `doan open <canvas path> [--frame <id>]` moves the running app to that canvas, and to a frame in it, as a link does (item 3 'Deep links'); it needs the app, and the bundled CLI opens a closed app once and waits for it, as `onboarding start` does, but brings it forward (item 0). An app that is still starting or reading the project is asked again for a few seconds, then reported as busy. `doan work start <canvas>` before editing and `doan work done [<canvas>…]` before ending a reply tell the running app which canvases a terminal agent works on (item 1 sidebar, item 2 'Agent indicator'); they never fail the agent's work when the app is off or unreachable, never open the app, and send nothing from Doan's own conversations. They record no session association (§3 'Association recording'). A `start` from an unregistered worktree of a registered project registers it (item 1); `done` never registers.
11. `doan check` does **static checks only**: what HTML parsing alone can catch — undefined tokens, duplicate or missing ids, missing `doan:width` (an error), comment files with no matching canvas, missing `data-doan-implements` targets, external URLs (a warning, not blocked), viewport height units in the canvas's own CSS (a warning) and, with token CSS, hardcoded colors (a warning). An orphan comment file's warning tells the agent to restore the canvas id or ask the user, never to delete or rewrite the file; only the person's confirmed Move to Trash takes a comment file out of the repository (item 5). Full criteria: ARCHITECTURE §1 'Conventions'. Shell check also records best-effort device-local session associations without changing findings/output (§3, ARCHITECTURE §4).
12. `doan export <canvas path> -o <file> [--force]`: writes one canvas as a single HTML file that opens without Doan, the repository or a network (item 3 'Export and viewer'). It reads only repo files, so it works without the app. The agent runs it only when the person asks to export or share a canvas as a file, writes outside `.doan/`, and says when the result still needs the internet (`external`) or has links that won't work (`links`). An existing output file is replaced only with `--force`, which the agent uses only when the person agreed.

### Skills

13. The `doan` skill reaches the five providers' own sessions through agent setup (item 0) and Doan's provider profiles through agent-auth (ARCHITECTURE §6).
    - Design presets. The CLI bundles 20 presets adapted from Impeccable (catalog: `cli/internal/designskill/catalog.json`), with no aliases for upstream names. `doan design-skill` lists them and returns one body without a project or the running app (ARCHITECTURE §12). The `doan` skill stays the entry point: the agent that already does the work picks a preset from the request. A preset the user names comes first; otherwise one is used only when it clearly fits; a concrete edit needs none; a review ends with a report. There is no classifier model, no rewrite of the user's request and no automatic review.
      - The design-start preset is `context`, separate from CLI `doan init`, which only sets the project up and points agents to `context` without running a model or a preset.
      - `document` writes, only on request, a rules document for agents and design-system canvases in `.doan/ds/` for people. The rules document goes in the project's existing design document or where the user agrees, never under `.doan/`. An existing sufficient system is reused with its organization; a legacy `.doan/canvases/design-system.html` moves only with the user's agreement and keeps its ID. Maintenance changes only what drifted or was requested; a plain setup request is not approval to write a system, and code changes never start maintenance. Procedure: `cli/internal/designskill/presets/document.md`.
      - A `generate` variant draws the target's states or names those it leaves out. When a direction question gets no answer and the agent continues, it states the assumed direction on the canvas and in its answer.
      - The preset picker is on Home (item 1 'Home'); app conversations tell the agent to find presets through the guide. Presets are shown in five groups (start, review, refine, content, explore) without changing the catalog order (ARCHITECTURE §12).

### Dogfooding: Doan's UI drafts live in Doan

- Design drafts for the Doan app UI are kept as canvases in this repo's `.doan/canvases/` (ARCHITECTURE §1 Conventions), and viewed and discussed in the Doan app's canvas conversation panel. Whether the implementation matches the design draft is compared via computed style (`/design-sync`).
- App screens run the design draft → implementation → comparison loop.
- A draft canvas that no screen uses any more is removed only when the user names it; until then it stays unchanged.
- The app's design system lives separately in `.doan/ds/`, one canvas per token group, shared component or shared surface; its rules and canvas index are in [DESIGN.md](./DESIGN.md#design-system).
