# Doan Design — Product plan

> Source of truth for product judgment: problem, users, scope, core loop and MVP. It describes the product as it is now; history lives in git.
> Structure, formats and conventions live in [ARCHITECTURE.md](./ARCHITECTURE.md); measured UI values live in [DESIGN.md](./DESIGN.md). [README.md](../README.md) is the public introduction and is not a decision source.

## 1. Problem

Doan is a design app for coding with agents. When the screens are settled on a canvas before the code, the agent implements a design the person already agreed on: its result is predictable, and fewer revision rounds spend fewer tokens on rework.

The design drafts that coding agents make live outside the code, in external design services. This causes the first five problems below; the sixth comes from running agents inside Doan. The arrow after each names the §3 'In scope' item that addresses it.

1. **Conversations split.** Design-draft and implementation conversations pile up separately in two tools, and some runtimes cannot reach the draft at all (Codex could not use Claude Design or DesignSync). → Deliver
2. **Agents cannot read design drafts properly.** Large files get truncated (DesignSync `get_file` caps at 256 KiB), and the agent does not know where the human pointed. → Show · Let humans point
3. **Design drafts do not know the code.** They do not know the real tokens or implementation, so they drift from it. → Tie to code · Check
4. **Records are locked into an external service.** A service shutdown can separate drafts from their feedback: standalone Claude Design closes on 2026-12-14, and projects can move to Claude, but chats and comments cannot move and are deleted later ([migration notice](https://support.claude.com/en/articles/17440474-move-from-standalone-claude-design-to-claude)). → Show (the canvas is a file in the repo; in a project whose Doan files are kept out of Git it is on this Mac only, outside the repository's history, and can be lost with the checkout) · Conversation (kept on this device)
5. **A draft cannot be shown to someone outside the repo.** A canvas reads the repo's token CSS, shared CSS and assets by relative paths, so sending the HTML file alone does not open it, and a reviewer without the repo or Doan cannot see it. → Export
6. **Agents in Doan cannot read the spec.** A canvas follows one spec or ticket (§4 'Unit of review'), and specs and tickets often live in Notion or Jira. A Doan conversation runs on Doan's own agent profile, which does not see the MCP servers the person set up for a terminal, so the person has to paste the spec into the message. → MCP connectors

Source: the Malmoi case. These problems were hit while running a Claude Design handoff → `/design-sync` loop during malmoi development (2026-09 to 10). Beyond the evidence above: a modal pinned to the pixel diverged in 29 places with all tests green, and drafts showed commands and images that did not exist; an old canvas was lost, the rule for when the draft stops being the source of truth was revised three times, and which board had been approved was recorded nowhere on the draft side; access to drafts differed per machine, session and runtime, and in orchestrations only some workers could read them.

## 2. Users

The primary users are external users in general; installation, onboarding and documentation are in product scope.

Doan is downloaded from the repository's GitHub Releases as a notarized arm64 (Apple silicon) dmg.

Doan's own agent connections cover five providers — Claude Code, Codex, Cursor, Antigravity and GitHub Copilot — with one account each (§3 In scope 7); first run chooses a buddy, signs in to them and selects a project. Opening the packaged app from Applications also sets up the `doan` command and skill, with no setup screen, for the same five agents' sessions outside Doan (§5 item 0 'Agent setup'). A user who has only the app can ask their own agent to run first run, or to set up a repository for Doan, through `doan onboarding` (§5 item 0).

A canvas can also reach people who use neither Doan nor the repo, such as a reviewer or a stakeholder: they receive an exported file and open it in a browser to look at it, play its prototypes or, with its inspector, check the values a developer needs (§3 In scope 8).

## 3. Scope

### In scope

1. **Show.** The app shows the canvas the agent wrote into the repo, with zoom, frame jumps and, while the person holds Option over a selection, the distances to the element under the pointer (§5 item 4 'Measuring'), an inspector beside the board with the values the canvas sets on the selection (§5 item 4 'Inspector'), and plays a frame the agent marked as a prototype alone in its own window, from the main window or when the person asks an agent (`doan open --prototype`, §5 item 2 'Prototype window').
2. **Let humans point.** The human selects an element or frame, and puts frames, elements and spots inside frames into a message as chips (§5 item 6), or puts an image of an area of the board into the canvas composer with Capture area (§5 item 2 'Toolbar'). The agent points back the same way: a frame or element its reply names in the app shows as a chip that moves to it.
3. **Deliver.** The agent receives the person's message with its anchors, or reads the selection (`active`) through the CLI and skills, and applies them. The app sets up the CLI and skill for the five providers' own sessions.
4. **Check.** `doan check` statically checks the canvas's conventions, tokens and external resources.
5. **Tie to code.** The canvas uses the repo's real token CSS, and frames point to implementation files (`data-doan-implements`).
6. **Conversation.** A human message starts a live conversation on a connected Claude Code, Codex, Cursor, Antigravity or GitHub Copilot account (In scope 7), or resumes a recorded Claude Code or Codex drawing session through the installed, logged-in CLI without forking. A canvas can hold several conversations, and all of them can run at once: starting or sending in one never stops or holds another, and Doan sets no limit on how many run (the provider account's own limits apply). A project also holds conversations bound to no canvas (project conversations), which run at once in the same way; queueing and the anchor limit are §5 items 1 and 6. A queued message is still the person's message, not Doan waking the agent (Out of scope 4). The agent of a canvas or project conversation can also hand its work on to a new conversation on each new canvas its turn created (§5 item 2 'Handoff', an exception in Out of scope 4). Session associations and conversation events stay on this device, outside the repo. A person can delete a conversation from this device; the agent's own session files stay. The composer also passes a project skill (a skill in the opened repository) to a Claude Code or Codex conversation by name (§5 item 1 'Project skills'); Doan does not read, run, change or install it. It sends the provider built-in commands Doan confirmed run in a conversation, such as `/compact`, as messages of their own, and shows a card instead of sending the built-ins that do not (§5 item 1 'Built-in commands').
7. **Agent authentication.** Users sign in from Doan and keep a Doan-specific connection, independent of Orca's or a terminal's login, with at most one account per platform. All five providers use their official login in a Doan-owned profile, keep credentials on this device, sign out locally and run new and canvas conversations on the connected account ([ARCHITECTURE §7 'Agent authentication'](./ARCHITECTURE.md#agent-authentication)).
   - Sign-in, check and sign-out happen in first run (buddy → agent sign-in → local folder or GitHub repository URL → Home) and, since first run cannot be reopened, afterwards in Settings > Agents (§5 item 0). Home's agent picker sends the person there (§5 item 1); conversations offer no sign-in.
   - A replacement sign-in that does not finish keeps the stored connection and its verified state unless the attempt has touched that connection's live login (ARCHITECTURE §7 'Sign-out and replacement').
   - Independent credentials do not establish external-session portability.
   - The app shows each connected account's remaining usage (the share of each rate-limit window used and when it resets) for Claude Code, Codex, Cursor and GitHub Copilot, read from the Doan connection only, never from a terminal's or Orca's login (§5 item 0 'Agent usage'). Antigravity's usage is not shown.
8. **Export.** The person saves a canvas as one HTML file that opens in a browser without Doan, the repository or a network, and sends it themselves. The app offers it from the sidebar's canvas row menu and the canvas toolbar, and the CLI as `doan export` (§5 item 1 'Canvas row menu', item 2 'Toolbar', item 3 'Export and viewer', item 12). The file has the canvas page's read-only inspector, so the recipient can check a frame's or element's values without Doan, and plays the frames marked as prototypes in a browser tab or window of its own. A marked frame can also be saved as a prototype file that plays it and the frames linked with it: from the prototype window's header, from the exported file's player, which downloads the frame playing, and as `doan export --frame <id> --prototype` (§5 item 2 'Prototype window', item 3 'Export and viewer').
9. **MCP connectors.** Claude Code and Codex conversations on a Doan connection can use the tools of remote MCP servers: the Notion, Atlassian and Figma presets, or any HTTPS server the person adds by URL. The person connects each agent to each server in Settings > MCP Connectors (§5 item 0) with that provider's own MCP sign-in; Doan keeps only the server list, and the provider CLI keeps the registrations in Doan's profile and the tokens in the OS keychain ([ARCHITECTURE §7 'MCP connectors'](./ARCHITECTURE.md#mcp-connectors)).
   - Conversations offer no MCP sign-in, as for agent sign-in (In scope 7).
   - Doan's servers never share a registration or token with the person's terminal setup: connecting, disconnecting, removing and signing out of Doan leave the terminal's MCP servers and tokens as they are.
   - Only remote servers with the provider's OAuth sign-in: no local (stdio) servers, typed headers or API keys, project-scope registration (`.mcp.json`), or MCP servers for terminal sessions (the legacy external path). Cursor, Antigravity and GitHub Copilot cannot use the servers.
   - Claude Code also loads the connectors of the person's claude.ai account. Doan neither shows nor manages them, so a service connected both ways can give Claude two sets of the same tools.

Doan handles installation and onboarding for these capabilities. Where conversations show is §5 items 0–3. The person also chooses one of five buddies, which shows on Home, on the docked composer of the Overview, the canvas conversation panel and the prototype window's conversation panel and in the canvas working notice, and sets the app's accent colour (§5 item 0 'First run' and 'General', item 1 'Buddy').

### Out of scope

1. **Drawing.** The agent draws the design draft. Doan is not a vector tool (Figma) where humans draw shapes.
2. **Enforcing a canvas format.** The agent decides sections, notes and layout. Doan's conventions are only the minimal attributes Doan reads (canvas, frame and element ids, frame title, implementation path, board width). Two optional attributes add a contract only where the agent puts them: the prototype mark makes a frame playable in its own window, from the CLI too, and in an exported file's player, and exportable as a prototype file (§5 item 2 'Prototype window', item 3 'Export and viewer'), and `data-doan-goto` names the frame an element links to, which a click follows in the prototype window and the exported file's player and `doan check` checks (ARCHITECTURE §1 convention 15); a marked frame also gets `--doan-viewport-height` while playing (convention 14); a canvas without them loses nothing.
3. **Multiple accounts per agent platform.** Account pools and multiple-account selection are excluded (one account: In scope 7). Resuming a session found through a shell `doan check` association uses the installed, logged-in Claude Code or Codex CLI and its own profile (legacy external path). GitHub authentication for browsing or cloning repositories is deferred; Copilot's GitHub-based agent sign-in is separate. Cloning a GitHub URL uses the user's existing Git credentials and adds no GitHub sign-in, token storage or repository listing.
4. **Autonomous agent wake-up.** Only a human message starts agent work; Doan does not initiate it on its own. Work signals (`doan work`, including the `doan work update` of an app conversation) only show work, tell the agents on the same canvas file about each other (§5 item 10), and, while the person rests, move the view within the canvas already open (§5 item 2 'Following'); a terminal `start` or `update` may add another worktree of a registered project to its list (§5 item 1). A `doan://` link or `doan open` only moves, or with `--prototype` plays a marked frame in the prototype window (item 3 'Deep links'); none of them wakes an agent. One narrow exception is the handoff (§5 item 2 'Handoff'): a canvas or project conversation turn started by a person's message may, through its permission mode, start a new conversation on each new canvas that turn created and its agent asked for; Doan writes no handoff message of its own and starts nothing on a new canvas the agent did not ask for, and a turn started by a handoff cannot hand off again. A second narrow exception is the usage limit (§5 item 3 'Usage limit'): a message the person sent while their Doan connection's usage limit is in force, or one whose turn the limit stopped before the agent did anything, waits and goes out when the limit resets; a turn the limit stops the same way again waits for a later reset. Doan writes nothing of its own and sends nothing while it is not running. Claude Code's next-message suggestion (§5 item 3 'Project Overview') is generated by the provider CLI itself at the end of the person's turn, so it is not work Doan starts; it adds one short request per turn on the person's account.
5. **Server.** No accounts, sync or hosting. Sharing happens through git, or through an exported file the person sends themselves (In scope 8); Doan uploads and serves nothing, and the web only serves as the download path: an eligible release copy checks GitHub Releases at launch and every 6 hours while automatic checks are on. The person can also check manually. Doan downloads an available update in the background and can open its release page in the browser (§5 item 0 'About'). These requests send nothing about the person or their projects. Links Doan opens in the browser (the release page, the repository page) are the person's own visits; Doan sends nothing with them.
6. **Git operations.** The agent makes commits and branches. Exception: first run and the Add Projects page clone a GitHub repository URL the user entered, with their existing Git credentials, into a destination they confirmed (§5 items 0 and 1). Second exception: `git init`, only when a folder in no Git repository (HOME and the folders above it excluded) is set up or switched to Keep out of Git, and only after the person agreed: in the app, by setting up with the shown change list or confirming the Project Settings page's Create a Git repository dialog; from the CLI, by passing `--git-init`, which an agent adds only when the person agreed (§5 item 0 'Doan files'). Doan runs no other git command (it reads remotes from `.git/config`) and does not pull, fetch, commit, branch or add a remote. Keeping a project's Doan files out of Git adds one marked pattern pair to the repository's `.git/info/exclude`; that pair, its `.gitattributes` line and the new repository's own files from `git init` are the only Git settings Doan writes (§5 item 0 'Doan files'); Doan never runs `git rm --cached` or reads `.git/index`.
7. **Simultaneous human/agent file editing.** A person talks while the agent edits and the app reloads; the person does not draw or directly edit the canvas in Doan. Exception: after a confirmation, Move to Trash moves one canvas file to the macOS Trash (§5 item 1 'Canvas row menu'). The app writes no canvas content. Agents editing the same canvas at once (several app conversations of one canvas, or terminal sessions) are not locked, and the app shows no warning; the replies to `doan work start` and `update` tell each agent which other sessions work on the same file, and the agent asks the person once before its first edit (§5 item 10). Running them that way is the person's choice.

### Agent conversation foundation contract

What the conversation runtime promises. The UI is §5 items 1–3; SDK, transport, processes, admission and IPC are [ARCHITECTURE §7 'Agent conversation runtime and IPC'](./ARCHITECTURE.md#agent-conversation-runtime-and-ipc).

- **Transport and evidence boundary.** Claude Code and Codex conversations run on the user's installed CLI; Doan bundles no replacement, and a missing executable is refused. Required CLI versions are verified minimums (Claude Code 2.1.284, Codex 0.158.0), not pins: a newer CLI runs until a new session shows a protocol Doan cannot read. A below-minimum or unreadable version refuses a new session (`runtime_unsupported`) and resume or send (`session_unavailable`). Stored sessions stay resumable from floors that never sit above the minimums: lowering a minimum lowers a floor with it, and a raised minimum leaves the floors where they are. A conversation's stored session resumes after an app restart.
- **Association recording.** Only a shell `doan check`, passing or failing, records which session changed which canvas. It never changes check output or exit codes, silently skips what it cannot record, and asks agents to manage no session IDs (ARCHITECTURE §4 'Shell check session associations').
- **Session identity and paths.** Every association and app-created conversation records its profile (`configDir`); an unset or empty configuration variable means HOME/.claude or HOME/.codex. Records are untrusted: resume requires the record's profile to match the currently selected one and its cwd to lie inside the same project root. A record never selects an arbitrary profile or copies credentials; a mismatch makes resume unavailable, never a fallback to another profile, cwd or session. A conversation moves its record to another session only after the person's Claude Code `/clear` ('Resume and permissions' below), and only when the new session's transcript is in the same profile's project folder as the old one's, every cwd it records is the conversation's, and no other conversation holds that session; otherwise the turn fails (`session_unavailable`, or `session_in_use` for a held session) and the record stays.
- **Resume and permissions.** Within the verified scope, resume continues the same session and transcript; Doan never forks or silently starts a new session. One exception: Claude Code's `/clear` (or `/reset`, `/new`) that the person sends moves the run to a new session, and the conversation follows it after the checks in 'Session identity and paths' (§5 item 1 'Built-in commands'). Every other change of session id during a Claude Code turn, a plan approval's clear context included, ends the turn as `session_unavailable`, and the conversation stays on its session. A turn runs in the permission mode the person picked (item 1 'Permission picker'); Ask first applies the user's own permission and sandbox settings, narrowed only by the userData limit below; on a Doan connection, Claude Code's and Codex's profiles also carry the `doan` allowances agent setup gives terminal sessions (item 0 'Agent setup'), so `doan work` and `doan open` do not ask there. Doan picks no mode itself, with one exception: after the person approves a Claude plan, the conversation follows the mode the SDK reports, except Full access, which reads as Ask first. Codex's `/review` request carries no permission mode, so the review runs in the mode the thread was last told; Doan sends it only while that mode is known and is the picker's (§5 item 1 'Built-in commands'). A handoff (`doan handoff`, §5 item 2 'Handoff') takes the same path as the agent's other shell commands in that mode, with no approval card of Doan's own; Plan refuses it. Codex, whose profile lets the same read and signal `doan` commands through unasked as a terminal Codex, still asks before `doan handoff`, and the person approves once; every other `doan` command, `doan export` and `doan config` included, goes through the mode like any shell command: Full access runs it without asking; Accept edits runs one that writes only inside the workspace (a `doan export` there, `doan config`) without asking, like the agent's own edits, and asks before a write outside it; Ask first asks before it leaves its read-only sandbox; and Plan refuses what that sandbox does not allow (ARCHITECTURE §7 'Agent authentication'). An agent in a Doan-connected conversation cannot use Doan's onboarding or remove projects (`doan onboarding`, `doan remove`), whatever it is approved to run; those stay with the person's terminal agents and Doan's own screens. In any Doan app conversation the CLI refuses both at once, telling the agent they cannot run from an app conversation and to ask the person to run them in a terminal. An agent in a Doan-connected conversation cannot read or write Doan's userData outside its own profile (other providers' profiles and sign-ins, Doan's conversations, other conversations' pasted images and text) in any permission mode, Full access included, nor write its profile beyond what its own CLI writes there (sessions, logs, caches, its sign-in); a blocked access shows as the agent's tool failure, with no screen of Doan's own. It can still read Doan's conversation runtime file (the app socket's address and a credential that cannot use onboarding or remove projects), this turn's pasted images and text (in Codex every paste) and its own profile, but cannot change its provider's instructions, rules, settings, skills, subagents, commands, hooks or plugins there; a Copilot, Cursor or Antigravity agent also cannot write other agents' skill and settings folders in its own home folder (`.agents`, `.claude`, `.codex`, `.grok`). That limit narrows the provider's own settings in three ways: a Claude Code turn runs with Claude's own sandbox off, whatever the settings say, because the limit holds the whole Claude process instead, so in Ask first a Bash command that sandbox would have let through asks; Codex's Ask first sandbox is Doan's read-only profile; and sandboxed commands in Codex's Ask first, Accept edits and Plan reach the network without asking, so `doan` reaches the app. Claude Code conversations on a Doan connection neither save nor load Claude Code's auto memory, and environment variables a Claude Code hook sets for the session (`CLAUDE_ENV_FILE`) do not reach the turn's commands; the person's terminal Claude Code is unaffected. Doan forwards the runtime's real approval requests and questions and invents none; it never asks a question or picks an answer itself. Denying is not stopping, and a stop the person asked for is not a successful turn. The verified allow/deny cases do not prove every policy/hook combination.
  - Questions: when Claude Code calls its question tool (`AskUserQuestion`) or Antigravity asks, the turn waits for the person's answer in the answer popover (§5 item 3 'Answer popover') as it waits for an approval, and the agent goes on in the same turn with the answer as the tool's result. Skip lets it go on without an answer. A question the popover cannot show whole (malformed, past the limits of 4 questions, 8 choices each, 512 code units for a header, choice or description and 4,096 for a question or a typed answer, or repeating a question) and one that comes after Stop or the turn's end never show and do not fail the turn: Claude Code is refused and told to ask in its reply instead.
  - Codex never sends its blocking question (`item/tool/requestUserInput`) in Doan's permission modes (observed: the Default collaboration mode Doan uses disables that tool; ARCHITECTURE §7 'Agent conversation runtime and IPC'). One that does arrive gets an empty answer and never shows, and the turn goes on. Codex's asynchronous questions show as the agent's text and are answered by the next message.
  - Antigravity asks through a permission request whose two or more options are all one-time allows with no reject; Doan shows it as one single-choice question without Other, never as Allow. Cursor's questions are skipped as before, and Copilot has no question tool.
  - Limit: a question the provider marks secret masks its field, and Doan writes its answer to none of its own records (history, notifications, the thread); the provider's own records (for a Doan connection, its profile under Doan's userData) and the agent repeating the answer may still hold it. No provider sends one in Doan's modes now.
- **Turn stages.** During a turn Doan reads what the provider already sends and names the stage for the turn indicator (§5 item 3 'Project Overview'); it sends no request for it and invents none. Claude Code tells thinking (its thinking blocks); Codex tells a single file read, listing or search (its command's actions; its reasoning arrives at once, so Codex never shows thinking); Claude Code and Codex tell when every tool running in the turn has ended; Copilot tells thinking (thought chunks); ACP providers that report a tool call while it runs (Copilot, Antigravity, Cursor) tell that tool. Every other moment is "working". Stages are live only: never written to the conversation history, the list, unseen or notifications.
- **MCP tools.** A Doan-connection Claude Code or Codex conversation sees the MCP servers connected to that agent (In scope 9) from its first turn, and a running conversation picks up a Connect, Disconnect or Remove from its next turn; the running turn keeps its tools.
  - Before each Codex turn Doan waits for the servers to start. Past 1 second the thread shows "Waiting for <Notion>"; after 10 seconds the turn starts without the servers still starting, and the line becomes "<Notion> wasn’t ready, so this turn started without it."
  - A Codex MCP tool approval shows as a permission request "Run <tool> on <Notion>" with Allow and Deny, plus Allow for this session when Codex offers it; Doan never offers a lasting approval. Deny fails that call and the turn goes on. An approval that arrives after Stop is declined. Other Codex elicitations (forms) are declined, so that tool call fails and the turn goes on.
  - Claude Code's MCP permission requests read "Run <tool> on <Notion>" as well. No MCP tool input is copied into the summary or the history.
  - Permission modes apply as to other tools: Plan fails a Codex MCP tool that needs approval, and Full access runs it without asking.
- **Live terminal policy.** Before each resume or send Doan rechecks the session: one open elsewhere (in a terminal, or in another Claude process such as a Claude desktop app Code session) is `session_in_use` (“Couldn’t continue the terminal session: <Provider> is still using it.”; a send reads “<Provider> is still using this session. Try again when it finishes.”, which never says where, because the holder can also be a Doan conversation's background work), one it cannot verify is `session_unavailable`, and a terminal session that cannot be continued is not offered. When the only doubt is a live Claude Code session record Doan cannot read (an older Claude Code version or an unknown shape), the canvas panel's new conversation state says so in place of the choice (“Can’t continue the Claude Code session from your terminal: Doan couldn’t check whether it’s still in use. Sending starts a new conversation.”) and does not check that link again until the canvas is visited again. A session a Doan conversation already holds is refused the same way and not offered until that conversation is deleted: one session is one conversation, because two conversations sending to one session would mix their histories. This is a best-effort check, not a lock. A Codex session counts as open until Codex releases its writer lock, about a minute after the terminal exits. Doan never kills the user's Codex daemon.
- **Launch environment.** Doan behaves the same however it was launched: the environment of a terminal that launched it (another tool's per-terminal agent profiles, session ids, hook variables) never reaches the login-shell probe or the agents, CLIs and git it runs. The profile therefore comes from the person's shell configuration; a `CLAUDE_CONFIG_DIR`/`CODEX_HOME` given only in a launching terminal's environment does not select it. The same applies to `CLAUDE_CODE_ENABLE_PROMPT_SUGGESTION`: Doan reads it from the login shell and otherwise sets it to `true` for Claude Code runs (item 3 'Project Overview').
- **Events and ownership.** Conversation events are stored on this device as they happen; a reload keeps them and the live turn. After a restart, unanswered approvals and questions expire and unfinished turns show as interrupted. Doan runs one turn per session at a time and never forks or takes over a session. Doan-connection conversations (In scope 7) follow the same rules.

## 4. Core loop

### Unit of review: one spec = one canvas

- One spec (one ticket) — user flow, per-state guides for blocks and components, layout and spacing, copy — is reviewed on **a single canvas** holding **multiple frames**; the human zooms and picks a frame.
- **One canvas = one HTML file in the repo**, named with a lower-case `.html`. The agent decides whether to keep shared shells or assets separately.
- **Frames are what the agent marks with `data-doan-frame="id"`**; the agent decides layout and look. The frame list, jumps and anchors use this id.
- **Ids do not change**, so anchors and conversations follow a moved file or renamed title. The agent names canvas and frame ids when it creates them, and `doan check` catches duplicates and omissions (ARCHITECTURE §1 'Conventions').
- **A frame can point to its implementation file** (`data-doan-implements`), per frame, since each frame has its own.
- **The agent organizes the inside of a canvas.** Doan fixes no section categories, note format or layout. References only:
  - A Figma design guide (Skillflo B2E, FCLXP-13938 learning dashboard revamp) places `user-journey-map` · `template-guide` · `layout-guide` · `i18n-guide` side by side.
  - Claude Design's canvas guide (Malmoi `Language Request Todo.dc.html`): one page per spec, an intro, then numbered frames, each a screen render beside note cards with design decisions and rationale.

### Loop

1. **The agent writes the canvas** at `.doan/canvases/<spec>.html` and checks it with `doan check`.
2. **The human views it in the app**, which live-reloads when the file changes.
3. **The human points** with chips (§5 item 6) or a selection.
4. **The human talks to the agent**, in the canvas's conversation panel, where chips arrive as anchors, or to their own agent outside Doan, which finds the target via `active`. Doan does not wake the agent itself, apart from a handoff and a message waiting out a usage limit (Out of scope 4).
5. **The agent applies it**: anchors or `doan active` → edit → `doan check`. Back to 2.

## 5. MVP

What the human does is **view + point + talk**; approval is deferred until after the MVP. Human-facing text (app screens, onboarding, menus, CLI messages, the guide, the skill stub, docs prose) names the product Doan; only places that already used the full name keep Doan Design (the window title, the `doan skill` guide's heading and the titles of PRODUCT.md and ARCHITECTURE.md), and the full name is not added elsewhere. Commands, paths and identifiers stay lowercase (`doan` and its subcommands, `.doan/`, `data-doan-*`, appId `design.doan.app`, userData `doan`); the app bundle is `Doan.app`. App UI copy is English; a folder is called "Project" on screen, while code names and docs keep "folder".

### App (Mac)

- **Text edit menu (app-wide).** Right-click or Control-click in a text field opens the macOS menu: [spelling suggestions · separator] · [Look Up “…” · separator] · Cut · Copy · Paste · separator · Select All, with shortcut hints and no icons. Suggestions appear only for a word the spellchecker marked and only when it has suggestions (no "No Guesses Found"); choosing one replaces the word. Look Up opens the macOS dictionary panel for the selection; its name quotes only the selection's visible text, so a chip reads as its name. Cut and Copy are off without a selection. A password field offers no Look Up or suggestions and keeps Cut and Copy off. A read-only, disabled or unavailable field (an unavailable composer) opens Look Up and Copy only when it has a selection, and nothing otherwise. URL fields (MCP server URL, GitHub repository URL, the Antigravity callback address) and Quick Open have no spellcheck. Menu Cut, Copy and Paste give the same result as ⌘X, ⌘C and ⌘V: in a composer, chips copy as chips within one canvas and as their names elsewhere, Paste attaches Finder files, path-less images and long text as ⌘V does, and ⌘Z undoes. If the field the menu was opened on disappears or loses focus while the menu is open, the chosen edit item or suggestion does nothing; Look Up and a non-editable field's Copy write nothing and still run. It puts `doan` on `PATH` (`~/.local/bin/doan`), links the `doan` skill where each agent reads skills, writes a Codex rule that lets Codex run the read and signal commands (`doan ls`, `check`, `active`, `work`, `open`, `skill`, `design-skill` and `help`) outside its sandbox without asking, because the sandbox blocks the app socket, while every other `doan` command follows the person's own Codex settings, and adds four rules to Claude Code's `permissions.allow` in `~/.claude/settings.json` so Claude Code runs `doan work start`, `doan work update`, `doan work done` and `doan open` without asking (layout in ARCHITECTURE §7 'Agent setup'). Cursor, Antigravity and Copilot may still ask, depending on the person's own permission settings. A replaced bundle needs nothing rewritten and a moved app is set up again on its next launch; of copies in both locations, the one launched last wins. Development builds and every other copy write nothing.
      - Doan never creates a provider folder (`~/.claude`, `~/.codex`, `~/.gemini`); that provider's link or rule appears on the first launch after the folder exists. Cursor and Copilot read `~/.agents/skills`, so they get no second link that would list the skill twice.
      - When the login shell's `PATH` lacks `~/.local/bin`, Doan also creates `/usr/local/bin/doan`, through the macOS administrator dialog when needed. A cancelled dialog is never asked again, and About gives the `PATH` line for the rc file instead.
      - Doan replaces without asking only what it created; anything else at a target is left alone and shown in About, and items that depend on it are skipped.
      - Claude Code's settings file is the person's: Doan only adds the missing rules, keeps every other byte, and writes nothing when every rule is already there, so repeated launches change nothing. A file Doan cannot merge safely (a link, not UTF-8, not valid JSON or wrongly shaped; ARCHITECTURE §7 'Agent setup') is left alone, and About says which rules to add where unless it already has them all.
      - Agent sessions read skills and the Codex rule when they start, so a session started before Doan's first launch must be restarted; this is not announced. An app-conversation Codex lists two `doan` skills from the same source (accepted). An old stub folder in `~/.agents/skills/doan` is foreign and stays until the person removes it.
   2. Project setup: Set up on a "Not set up" project (sidebar project menu) shows a form with token CSS (None by default, or Choose…) and the list of changes; Set up project runs the bundled `doan init`. A folder inside a set-up repository registers that repository instead, so the app never creates a nested repo (ARCHITECTURE §13 'The app's folders'), and the notice names that project's mode.
      - **Doan files.** Every setup path (the Set up form, first run's and Add Projects' setup panel, the clone screen, `doan onboarding project select`/`clone`, `doan init --storage`) chooses where a Doan root's files are kept, with two radios: Include in Git (the default, committed with the repository) or Keep out of Git (this Mac only). Kept out of Git, `.doan/` stays in the checkout but Git ignores it, through a marked pair in `.git/info/exclude`, and setup writes no `.gitattributes`; the change list shows `.git/info/exclude` instead. The mode belongs to the Doan root and is shared by every worktree of that repository at the same root path; another Doan root of the same repository chooses its own. Projects set up before this choice existed read as Include in Git. When the root is already kept out of Git (another worktree was set up), setup shows that fact with "Change it in Project Settings." instead of the choice. In a folder that is in no Git repository, Keep out of Git creates one: the Set up form's change list adds `.git/ — a new Git repository` above the exclude line, and first run's and Add Projects' setup panel adds one line under the storage card, "Doan will run `git init` here to create a Git repository."; screen readers get that line or list as the consent button's description (on the Add Projects page, its Add project). Setting up then runs `git init` (no commit, branch or remote; ARCHITECTURE §12 'Storage') before every other write. A folder below a repository uses that repository's exclude, and a folder under a dotfiles repository in HOME gets its own nested repository. In HOME or a folder above it nothing offers a repository and Keep out of Git is refused: "Doan doesn’t create a Git repository in your home folder. Choose Include in Git, or choose a folder inside it." Without Git (the same lookup as cloning, never opening the Command Line Tools installer) it is refused with `xcode-select --install` as the fix; a failed `git init` is refused with "Couldn’t create a Git repository here, so nothing was set up." When a later step fails, Doan removes the `.git/` this run made and only that; if it cannot, the error names the leftover `<path>/.git` and says to remove it or keep it, then try again. After a failure the folder is read again, so a leftover `.git` reads as a repository and the `.git/` line goes. An exclude write that fails writes nothing. The CLI creates the repository only with `--git-init` (`doan init --storage local --git-init`, `doan config --storage local --git-init`); without it `local_not_git` says to ask the person first, and an agent passes the flag only when the person agreed to a Git repository in that folder. Include in Git never creates a repository, and a repository Doan created stays when the project switches back. Cloning with Keep out of Git into a repository whose Doan files are already committed applies the mode after the clone. The choice is disabled while a clone runs and keeps its value after a cancel or failure.
      - Kept out of Git, `.doan/` does not follow worktrees or other Macs: each checkout has its own, a new worktree starts without Doan files (and is not auto-registered, item 1), and removing a worktree or `git clean -x` deletes them. Export shares a canvas. Doan does not stop a person from writing their own `.gitignore` rule or committing `.doan/` anyway, and does not read such rules as the mode.

Home has no connection chips, attention banner or setup checklist: a missing project shows in Home's project picker and a missing ready agent in its agent picker.

There is no timer, and nothing else is read while the window is hidden. A connection that cannot be used is not read; an unchecked one is checked first, as for a conversation (Copilot is read without a check). Until the first tool check after launch finishes, rows read "Reading usage" rather than a cause.

       - Queue: messages the person queued while the handoffs wait are handled once, after every request is resolved. With one request they follow a started handoff to the new conversation and go out after its first turn; if that turn has already ended, they follow its end as any queue does (sent after done, its draft otherwise). Work content lasts the work turn: a terminal session's from its first `start` or `update` until `done` or expiry, a conversation's for its turn; only the last update counts. It slides to the next frame an update names and otherwise sits on its frame at once (pan, zoom, reload, window resize). It never blocks selecting, hovering, picking, panning or zooming and never changes the selection. An id the document does not have shows no highlight; only the words change.
     - Following: when an update names a frame not yet followed in this work turn and the document has it (also once a reload creates it), the person has not moved for 5 seconds, and following has not stopped in this turn, the view jumps to it once without selecting it or adding another highlight: at the same zoom, centred, when it fits the area left by the notice and tool row, else as the frame drawer jumps. A frame already wholly in that area is left where it is; a taller one counts when its top edge is in it, a wider one when it spans the area's width. A frame named less than 5 seconds after a move is judged again when they pass. A person's move of the view (wheel, pinch, Hand or Space drag, zoom controls and shortcuts, the frame drawer, Quick Open, Locate, `doan open --frame`, a link's frame) or a change of selection during the work turn stops following for every work turn on the canvas until each ends; nothing shows that it stopped. Pointer moves over the board and typing only restart the rest. It does not follow during a pick, a capture, a drag (a canvas text drag included) or Space, with the page's menus or a dialog open, or off the canvas page; a frame named then is judged again only at the next update or document layout, not when that ends. Opening or returning to the canvas mid-turn counts the frame worked on then as followed and starts the 5-second rest again, and an update from another work source than the last one shown moves only the highlight and the words. It never moves to another canvas.

A project conversation or a conversation bound to another canvas whose `update` names this canvas shows the same variant.    - **Deep links.** `doan work done` returns a `doan://open?root=…&canvas=…` link for each edited canvas (an agent may append `&frame=<id>`), but agents do not print them: Orca's terminal (1.4.243), the Claude desktop app (4.4212.0) and the Codex app (26.1027) do not open links with a scheme other than http(s) when clicked, so a printed link does nothing there. The guide has the agent end its answer with one line, in the answer's language, offering to open the edited canvas in Doan by the name Doan shows (a frame by its title), and give the links only when the person asks for them. With several edited canvases the offer names them all, and a bare “open” opens the first. It does not ask while stopping to ask something else, and does not ask again about a canvas already opened or declined in the conversation. The agent runs `doan open` (item 10) only when the person asks and reports the result in one line. Conversations inside the app do not offer, because the person is already in Doan; a person's own request to open still works there. Only the packaged app registers the `doan` scheme; development runs do not. Opening a link launches the app if needed, shows the window, and after launch restore and the first project read opens that canvas the way Quick Open does; a frame moves the view and highlights it as Quick Open's frame jumps do, and a missing frame opens just the canvas. A link opened while a dialog is open dismisses it as its Cancel would, then moves; a dialog that refuses its cancel (a busy one, or first run) and a locked page drop the link and show a toast, “Couldn’t open the link.” plus what blocks: “The Add Projects page is in the middle of a task. Finish or cancel it, then try again.”, “Settings is in the middle of a change. Finish or cancel it, then try again.”, “Project Settings is in the middle of a change. Finish or cancel it, then try again.”, “Finish Doan’s first run, then try again.” or “A dialog is busy and did not close. Finish it, then try again.”. While a modal dialog is open (a running Set up, first run) that toast shows inside it and its timer runs. A malformed link, a root not registered in Doan (compared literally) or a canvas not in that project's list moves nowhere and shows a toast: “Couldn’t open the link.” plus why. `doan open` moves the same way and under the same rules, except that a refusal shows no toast and brings no window forward: the app answers the command with what blocks, and the agent tells the person. `doan open --prototype` moves nothing in the main window: it plays the frame in the prototype window ('Prototype window'), so only first run and the buddy screen refuse it (“Finish Doan’s first run, then try again.”), and the main window's locked pages and dialogs do not. There is no `doan://` form for it. A link or `doan open` only moves or shows: it never writes, sends, starts a conversation, adds a project or changes a setting, because any web page can open a link.

     - **Context window ring** (the canvas panel follows the same rules).        - Reveal: a streamed reply appears word by word, each new run of words fading in over 400 ms, instead of whole chunks at once; inside a code block it reveals line by line, and text without spaces (Chinese, Japanese) by word. The shown text is never more than 400 ms behind the received text, and a small chunk shows as it arrives. While the reply streams, a link (a `doan:` chip link included) or table still incomplete at the end of the received text is held until it completes, so it never shows as text and then changes; after `message.done` nothing is held. A reply already streaming when the thread mounts (reopening a conversation, unfolding the panel, switching back) starts at its current text and is not typed again.

A window that was hidden shows what arrived meanwhile at once. Selecting text inside a revealing reply shows it whole and stops the follow; a code block's Copy copies the whole received block. Screen readers do not read the revealed words; only the thread's status line speaks.

Opening a conversation puts it at the bottom at once. The person's wheel, pointer on the scroller (the scrollbar included) or scroll keys in the thread (Page Up/Down, Home, End, arrows, Space) stop the follow at once; typing in the composer does not. It resumes only when the person is back at the bottom, and not within 100 ms of the last wheel event, so trackpad momentum does not pull the thread back. While the answer popover or its bar shows, the thread's end leaves room of its height, so the popover never covers the last item: at the bottom the thread stays on the bottom at once when that room changes, and a change of the room alone is not new content (no `behind`, no Jump to latest), while the folded line and turn indicator that come back when a request ends are. Jump to latest sits above the popover. Jump to latest eases to the bottom with the same follow; `behind` and Jump to latest otherwise keep their rules, shown when the content grows while the person is away from the bottom.

     - **Edit line counts** (the canvas panel and the prototype window follow the same rules). An edit step in an expanded activity row shows, after its path, the lines that edit added and removed as `+12 −3`: a true minus sign, thousands grouped, and both sides even at zero (`+12 −0`, `+0 −0`), so a known zero differs from an unknown count, which shows nothing. Canvas HTML under `.doan/canvases/` follows the same rule as any other file, and a step with no path ("Edited a file") shows its counts too. A changed line counts as one added and one removed; each edit of the same file counts on its own.

While the head spins with the turn indicator's words it shows no total. The total grows as the turn runs; a count that arrives later is not announced, and a step or head stays one line, so the thread's height does not change.
       - Counts come only from an applied edit's result the provider reports: Claude Code (the edit's patch; a new file counts its content), Codex (each completed file change) and Copilot (the completed call's diff, for the file on the step's own path only: one call that patches several files is a single step named by one of them). There is no count for history written before counts, a denied or failed edit, an edit still running when Stop was pressed, a Copilot edit whose two texts together pass 20,000 lines or whose added and removed lines together pass 1,000, Cursor (unconfirmed) or Antigravity (it reports no applied diff). Only the counts show; the diff itself is not shown or stored.

4. **Selection**
   - The human selects by ordinary clicks in Select, a frame first: the first click inside a frame selects that frame, and the next click inside the selected frame goes one level in, to a nested frame or, at the innermost frame, the element clicked. Nested frames are entered one level per click from the outside, never skipping to the inside of a frame not yet entered, and no double-click is needed. A click inside another frame keeps the frames already entered that contain both and selects the new frame below them; another top-level frame starts at that frame. A click on a frame's own background selects that frame; an empty div or other element inside a frame is an element. A click outside every frame selects that element at once as a note, unless it holds frames (a row or grid laying frames out), which counts as empty space; empty space clears the selection. Which frames are entered comes from the selected node's current ancestors, so nothing remembers a path the selection has left.
   - ⌘-click in Select skips the frame steps and selects the selectable node under the pointer; later clicks and Esc go on from its current frame. Option with ⌘ keeps Option's canvas use. ⌘ changes nothing in the Picker, Hand, Capture area or a Space drag.
   - Esc steps back one level per press: an element to its frame, a frame to its outer frame, a top-level frame or a note to no selection; holding Esc takes one step, not one per key repeat. While a reload is still finding the selected node again, Esc clears the selection.
   - Hover highlights what the next click would select, ⌘ included, and is recomputed at once after a selection, an Esc, ⌘ or Option pressed or released, a pick starting or ending, or a text drag ending, with the pointer still; with the pointer resting on the canvas it also comes back after a reload's first layout, a problem overlay leaving the canvas, or a dialog closing back to the canvas page. In Hand clicks neither select nor clear (item 2 'Toolbar'). Ordinary clicks suppress canvas actions; Option-click uses the canvas without changing the selection (ARCHITECTURE §3 'Selection').
   - The marks show only what the canvas shows: the selection and hover outlines, the size bubble's size and Measuring use the node's box cut, on both axes, to each ancestor that clips it (a box whose `overflow` is not `visible` and applies to it; an absolutely positioned node escapes the static boxes below its containing block, a fixed one every box). A strip wider than the window it slides in is marked at the window.
   - Canvas text: in Select and Hand, pressing canvas text (a glyph, or the padding of the element holding the text) with the primary button and no modifier and moving 4 screen px, at any zoom, drags a text range from the press to the pointer. The press still never reaches the canvas: no pointer-down, mouse or click events and no focus. The range stays inside the innermost frame where it started, or, outside every frame, inside the element a click there selects as a note; it includes `user-select: none` text, and no drag starts in a field, editable text, a nested iframe or Shadow DOM. The app paints the range over the board in the person's accent at 30% with no ring (design/canvas.md 'Canvas text range'); the canvas's own selection and styles stay untouched. During the drag the cursor is the text cursor, hover hides while the selection mark stays, V, H and Space are ignored, Esc ends the drag and clears the range, and wheel panning and pinch move the board and carry the range's end to the pointer's new place. Releasing keeps the range, brings hover back and moves keyboard focus to the canvas area as a click does. A text drag never changes the selection or `doan active`; a press that moved less than 4 px is a click, and a drag that returns to its start selects nothing. ⌘C and Edit > Copy copy the selection made last, as plain text: dragging canvas text collapses an app text selection, and selecting app text clears the range, so one selection shows at a time; with a modal or menu over the page nothing of the canvas is copied. Past 100,000 characters only the start is copied, without a notice. The range clears on the next primary press in the canvas (a margin click and a press into a nested iframe included; in Hand any primary press without Ctrl or Space, a pan's included), Esc (the first Esc clears only the range and keeps the selection, item 2 'Notices and states'), starting a pick or Capture area, a reload, switching or closing the canvas, the board no longer drawn and leaving the canvas page; Space, switching between Select and Hand, wheel panning, pinch, zoom and right or Control presses keep it. There is no double-click word selection (a double-click stays two clicks), no Shift or keyboard extension, no ⌘A over the canvas, no edge auto-scroll and no dragging text out.
   - Measuring: in Select, with a selection, holding Option (⌥) shows the distances in canvas px between the selection and the hover target, the node the next click would select (⌘⌥ measures what a ⌘-click would select). Because the target follows the click rule, a selected frame with Option over an element inside it measures between the two, where Figma shows nothing. Option pressed or released redraws at once with the pointer still. There is no measurement without a selection, over the selection itself, or over empty space a click would clear; there Option hides the hover, since Option-click does not select.
     - Geometry, from the clipped boxes the marks use: apart on an axis, a solid line from the selection's near edge to the target's near edge on the selection's centre line, with a dashed extension to the target's edge when that centre line is outside the target's range, both axes when diagonal. One inside the other or overlapping: each same-side edge distance that is not 0, on the overlap's centre line. Apart on one axis and overlapping on the other: the gap plus, per side, the same-side edge difference when it is not 0 and either the selection's edge lies strictly inside the target's range or the target's range lies strictly inside the selection's, with a dashed line along the target's edge from its near edge to the selection's far edge. Touching (an edge on the other's opposite edge) on one axis and overlapping or touching on the other draws no lines; touching on one axis and apart on the other measures the gap and treats the touching coordinate as inside the target's range. These match Figma's observed Option-hover measurement.
     - Look: one fixed red (not the buddy accent), 1 screen px solid and dashed lines and labels of the same screen size at any zoom; a label sits 6 px below a horizontal line or right of a vertical one, centred, and never moves, even over a narrow gap, another label or the size bubble (labels draw above it). While measuring, the selection and the target get a 1 px red line inside their accent outline, the one place a mark covers element pixels, and the target's dashed hover outline turns solid (design/canvas.md 'Canvas distance measurement'). Numbers round like the size bubble, after subtracting the raw values. The cursor does not change.
     - Measuring is not drawn during the Picker, Hand, Capture area, a text drag, a Space drag, a modal or menu over the canvas, or while a reload is finding the selection again; when that ends it comes back with the pointer still. Releasing Option, in the app or in the canvas after an Option-click moved focus there, the app losing focus (⌘Tab) or the pointer leaving the canvas ends it. Option with the wheel or a pinch keeps the target, and the lines follow the board through zoom, pan, Fit, ⌘0, following and panel resizes. Measuring never changes the selection, the size bubble's text or `doan active`, and Option-click still uses the canvas. The prototype window and the export viewer's player have no selection; the export viewer's board measures as the canvas page does (item 3 'Export and viewer'). Capture and Export carry no app marks. The lines are display only: the overlay is hidden from assistive technology and there is no keyboard way to measure; white label text on the red is about 3.9:1, below the small-text 4.5:1, and the lines can be hard to see on red canvases. Under forced colours the lines and labels keep their colours.
   - Inspector: a column between the board and the conversation panel shows the values the canvas sets on the selected frame or element, so the person can check a size, a gap or a color, and its token, before asking an agent to change it. It is read-only, on the canvas page and in the export viewer (item 3 'Export and viewer'), not the Overview or the prototype window.
     - Opening: only the person opens it, with Show inspector in the canvas header (item 2 'Canvas header') or in the selection's size bubble (item 2 'Size bubble'), and folds it with Hide inspector at the end of its head; no agent, menu item or shortcut does. The bubble's Show inspector is a `sliders-horizontal` icon button with the header button's name and tooltip, after Add to message, shown only while the column is not; pressing it does what the header button does, and neither Play nor Add to message runs. A pointer press on it does not take focus. Open/folded and width are one setting on this device for every canvas; with nothing saved it is folded. It folds and unfolds with the conversation panel's motion. Folding moves focus to Show inspector and unfolding to Hide inspector.
     - Width: resizable from its start edge, by dragging or ←/→ on the handle, between 280 px, also its default, which a double-click restores, and the width that leaves the board 360 px beside the conversation. A saved width above the widest shows at the widest without being rewritten.
     - Narrow window: the conversation is sized first. When the window, at the conversation's width, leaves less than 280 px for the inspector beside a 360 px board, the inspector yields: its column is not shown, its saved open flag stays, and Show inspector, in the header and in the size bubble, is unavailable with its reason (item 2 'Canvas header'). Widening the window brings it back. Focus inside the column moves to Show inspector, and from there, or from the bubble's Show inspector, to Hide inspector when the column returns. While folded or yielding it reads no styles.
     - Head: “Inspector” while nothing is selected; with a selection, the selection's name as the element menu's trigger. Hide inspector ends it.
     - States: with no selection (also while no board is rendered), “Select a frame or element on the canvas to see its styles.” A new selection clears the rows and shows “Reading styles” after 300 ms, so a quick read does not flash it. The same selection read again (found again by a reload, a move with the same canvas ID, Retry) keeps its rows, scroll and focus until the new values replace them. A failed read shows “Couldn’t read the styles.” with Retry. A selected node the read cannot find, and a selection a reload loses (the canvas's toast above tells it), show the empty state. With values, the rows; when the canvas sets none of them, “The canvas sets no styles here.”
     - Values: only what the canvas sets; browser defaults and `data-doan-*` attributes are not shown. A value set through a token shows only the token's name, as a chip; any other value shows as it is, colors in hex where they convert, with a swatch (inside the chip for a color token). There are no source captions (such as Hardcoded or Default) and no switch between tokens and values. A row split by side or corner (padding, margin, radius) is a token chip only when every side uses the same token, else its value, because a chip standing for a partly tokenized padding would answer “what is the padding?” wrongly. A split value set on one side only reads by that side (“Top 8px”, “Top left 8px”); other shorthands stay as written.
     - Tooltip: one per row, on hover or focus, with these lines in order: the full name or value when it is cut, the computed value of a token, the alias chain (`--a → --b`), each side's value with its token (opposite sides paired, as in “Top and bottom 20px, left and right 24px”), and “Inherited from <element>” for an inherited value, with a token or not.
     - Groups and order: Box (Padding, Gap, Margin, Width, Height), Typography (Size, Weight, Line height, Family), Colors (Text, Background, Border), Radius, Shadow, Layout (Display, Direction, Columns, Wrap, Justify, Align). Layout rows show only for a flex or grid element; Direction and Wrap only for flex, Columns only for grid. A group with no row is not shown.
     - Copy: pressing a row, or Enter, Space or ⌘C on a focused row, copies what it shows, the token's name or else the value, and the shared toast says “Copied <text>”, or “Couldn’t copy the value. Try again.” when copying fails; the row keeps showing its value. The row list is one Tab stop; ↑/↓, Home and End move between rows.
     - Element menu: the head's trigger opens the tree of the innermost frame holding the selection: the frame, then its elements in document order, each indented under its parent with a guide line per ancestor and a kind icon (frame, flex row, flex column, grid, input, button, text, other box), and named by the frame's title, else its `data-doan-id`, else its tag and up to 24 characters of its own text. The selection is the pressed row. Elements that draw no box (inside `display: none`, a hidden input) are left out. Over 200 rows the menu keeps the path to the selection, then its children, then its siblings. Names are never cut or wrapped: when a deep row is wider than the menu, the menu scrolls sideways, and opening it or moving with ↑/↓, Home and End brings the row's icon and name into view. Hovering or focusing a row marks that node on the board; choosing one (a press, Enter or Space) selects it as a ⌘-click does and closes the menu. ↑/↓, Home and End move between rows, and Esc closes only the menu.
     - Esc: with focus in the inspector, an open tooltip included, Esc steps the selection back one level as on the board; only an open element menu takes Esc first. After a step from inside the inspector focus goes to the head's trigger, or to the board area when the selection cleared.
     - Not offered: editing values or tokens, putting a row into a conversation as a chip (the copied text is pasted instead), canvas information while nothing is selected, the values of several elements at once or of the hovered element, and style values in `doan active` or any other CLI output.
   - One in-memory selection exists app-wide, read by `doan active`, which returns it only for its owning project. Esc steps it back and empty-space clicks in Select clear it, as above; switching to Hand, starting a pick and opening another canvas clear it, and ending the pick does not bring it back; a chip's locate and Quick Open's jump never change it. Frames use the rendered DOM, so an active frame may be absent from static `doan ls` output.
   - A reload or a move with the same canvas ID keeps the selection, unless the selected element or frame is no longer found, which clears it with the toast “The selection is no longer in the canvas.”; opening another canvas clears it (ARCHITECTURE §3 'Selection lifetime').
5. **No comments.** Doan has no comment feature; the person points through the canvas conversation (item 6) or a selection (`doan active`). A `.doan/comments/` directory in a repository is not Doan's: Doan does not read it, warn about it, move it or delete it, and never serves or exports it, as with other `.doan/` metadata.
6. **Point in a conversation**: the canvas conversation panel's composer holds anchor chips inline with the text, so a message can say what it is about.
   - Besides chips, a message can carry an image of an area of the board (Capture area, item 2 'Toolbar'). It is an ordinary attachment: the agent gets its path, with no frame id or position.
   - Chips: a frame, an element, or a point inside a frame. A message points at up to 32 distinct places (a repeated place counts once); at the limit, picking is unavailable. A sent message carries the chips as anchors (ARCHITECTURE §7), and a returned draft comes back with them. Typed `{{` or `}}` block Send; chips do not.
   - A chip edits as one unit. Chips copied within the same canvas's composers stay chips unless the paste would point at more than 32 places; elsewhere, and past that limit, they paste as their names (ARCHITECTURE §7 'Renderer primitives').
   - Pick from canvas (the composer's picker), the toolbar Picker and ⌘L (Edit > Pick from Canvas) start the same one pick; a folded panel unfolds first: a click on a frame's background adds a frame chip, a click on an element an element chip, and a Shift-click inside a frame a point chip in the innermost frame; a click outside every frame adds nothing and the pick goes on. The chip goes in at the composer's caret and focus goes to the composer. Esc, any of the three again, hiding or switching the conversation, an unavailable composer and leaving the canvas cancel the pick; a reload or a move with the same canvas ID keeps it. Wheel panning and pinch still work; Hand and Space dragging do not, and V and H are ignored. Starting a pick clears the selection; ending or cancelling the pick does not bring it back. When the pick ends, the tool from before it (Select or Hand) is back. A pick cancelled by the picker or the toolbar Picker leaves focus on that button; one cancelled by Esc returns focus to where it was before the pick, unless the person moved it meanwhile; focus never falls to the page body.
   - The pick works only while the composer takes input and the canvas is shown; otherwise the three are disabled and say why (⌘L is enabled only on the canvas page).
   - Add to message: the size bubble's Add to message (crosshair, tooltip “Add to message”) puts the selected frame or element in as a chip, the same chip a pick of it makes, at the composer's caret; a folded panel unfolds first and focus goes to the composer. The selection, the size bubble and `doan active` stay. It is unavailable, with its reason as tooltip and accessible description, in capture mode (“Finish or cancel the capture first.”), for a selection outside every frame (“Only frames and what’s in them can go in a message.”), and whenever the pick is unavailable: the composer's reasons as the pick says them, an unlisted canvas's notice, otherwise “Add to message isn’t available while the canvas can’t be shown.”
   - A pick started (⌘L) while a size bubble button had focus clears the selection and so hides that button; cancelling it with Esc puts focus in the composer field while the person has not moved focus meanwhile.
   - Locate: a chip in a sent message or the composer moves the view to its target — a frame as the frame drawer does, an element or point centred at the same zoom (zooming out only for an element larger than the view) — and highlights it; a target not found says so beside the chip. A person's chip's locate is disabled while the canvas is not shown (resolution: ARCHITECTURE §3 'Picking and locate').
   - Locating changes neither the selection, `doan active` nor the composer's text. Picking leaves the composer's text alone and changes the selection and `doan active` only by clearing them when the pick starts. Add to message changes neither. A sent chip stays as sent when its target later moves. Home's and the Overview's composers take no chips; a person's chips point only into the open canvas.
   - Chips in the agent's replies: in an app conversation (the canvas panel and the Overview) the agent's reply can link a frame or element of a canvas in the conversation's project, and the thread draws it as the person's chip, named from that canvas's frame titles; a chip into another canvas adds ` · <canvas name>`, which is never cut (the label ellipsizes first) and says it will open that canvas. A chip into the canvas on screen locates as a sent chip does (disabled while the canvas is not shown, "No longer in the canvas" under the reply). A chip into another canvas, or any chip on the Overview, opens that canvas as a deep link does — the selection clears, the panel switches to that canvas's conversation, one visit for Back — and moves to the target; a target it does not find leaves just the canvas open. A canvas the project does not have, or has twice, or whose list is still being read or has a problem shows one toast and moves nowhere. A malformed link stays plain text. Terminal sessions and the guide do not learn the form (ARCHITECTURE §7).

### CLI `doan`

8. `doan init`: creates `.doan/canvases/` and `.doan/config.json`, sets up `.gitattributes` (`.doan/` as documentation), or with `--storage local` the `.git/info/exclude` pair instead (item 0 'Doan files'; a plain `init` follows a root already kept out of Git; in a folder in no Git repository it also needs `--git-init`, which an agent passes only after the person agreed to a new repository there), and prompts for an optional token CSS path during new setup in an interactive terminal when neither `--token-css` nor `--json` was supplied. This is the terminal form of the app's project setup (Set up in the sidebar project menu, first run's Set up and continue). It does not install skills: opening the app sets up the skill (item 0 'Agent setup'). It does not add the project to the app either. Agents run it only when the person names `doan init` or when a repository setup request cannot reach the app (item 0 'First run').
9. `doan ls` · `doan skill` · `doan config`. All three work without the app. The CLI includes the skill guide, so `doan skill` also works outside a project. `ls` also reports Git branch/worktrees. One unreadable file or folder does not fail `ls`: it marks the affected rows and lists the rest (ARCHITECTURE §12); the app lists only the canvases. `doan check` fails as a whole when it cannot read a file it needs.
10. `doan active`: returns the frame or element the human selected in the app. Lets the agent find the target from just "fix this". Requires the app to be running. `doan onboarding …` drives first run through the running app; only `onboarding start` and `open` from the bundled CLI may open the app (item 0). `doan open <canvas path> [--frame <id>]` moves the running app to that canvas, and to a frame in it, as a link does (item 3 'Deep links'); with `--frame <id> --prototype` it plays that marked frame in the prototype window instead and leaves the main window as it is (item 2 'Prototype window'), and a frame the file does not hold once (one a script adds included) or does not mark is refused before the app is asked; it needs the app, and the bundled CLI opens a closed app once and waits for it, as `onboarding start` does, but brings it forward (item 0). An app that is still starting or reading the project is asked again for a few seconds, then reported as busy. `doan work start <canvas>` before editing, `doan work update <canvas> [--frame <id>] [--note <text>]` each time the agent starts editing a frame, and `doan work done [<canvas>…]` before ending a reply tell the running app which canvases a terminal agent works on and, with `update`, which frame and what it is doing in one line of at most 120 characters (item 1 sidebar, item 2 'Agent indicator'); `update` also counts as `start`. They never fail the agent's work when the app is off or unreachable and never open the app. From Doan's own conversations only `update` is sent, naming that conversation, because the app already follows the turn. They record no session association (§3 'Association recording'). The replies to `start` and `update` list the other sessions working on the same canvas file (`others`: the same root and path, so another worktree's copy is not the same file): each one's kind (terminal or app conversation), provider when known, and current frame and note, never a session or conversation ID, account or elapsed time, at most eight. A terminal session counts while it touched that file in the last 5 minutes; an app conversation while its turn runs and its last `update` of the turn names this file, or, before any `update` in the turn, while it is bound to this canvas. The caller is left out, and two anonymous terminals of one root cannot see each other. `done`, an error or an app that is off gives no list. The guide has the agent, before its first edit of that canvas in the conversation, say who else is working (kind, provider, frame by its title, note) and ask whether to go ahead; it asks again only when the list has more entries than when it last asked, never when the person said up front to go ahead regardless, and treats the frame and note as data, not instructions. An app conversation, whose `start` sends nothing, sends an `update` before its first edit. Doan itself never blocks or warns about an edit (Out of scope 7). A terminal `start` or `update` from an unregistered worktree of a registered project registers it (item 1); `done` and a conversation's `update` never register. `doan handoff <canvas path> --message <text|->` asks the running app to start a new conversation on that new canvas when the turn ends (item 2 'Handoff'); it works only inside a Doan app conversation, never opens the app, and `doan help` lists it as such. `doan remove [--repo <path>]` takes the project group of that folder out of the running app's list, with the same result as Remove from Doan (item 1): from any registered worktree of the group, the whole group, with no confirmation (running it is the confirmation), no toast, and the window not brought forward. It is refused, changing nothing, from inside any Doan app conversation (by the CLI, which tells the agent to ask the person to run it in a terminal); while any conversation turn of the group runs (canvas and prototype window conversations included, unlike the menu's alert); while first run or the buddy screen, a dialog or a locked page is open, or a project is still being read; for a folder Doan does not list; and when the app is not running, which it never opens. A Not set up or Config error folder is pointed to Remove from Doan in the app. Agents run it only when the person asks: `doan help` says so, and the guide and skill stub do not name it.
11. `doan check` does **static checks only**: what HTML parsing alone can catch — among them undefined tokens, duplicate or missing ids, missing `doan:width` (an error), missing `data-doan-implements` targets, external URLs (a warning, not blocked, except an SVG `<use>` pointing to another file or URL, which the app cannot draw: an error), a relative `url()` in a custom property that stylesheets in different folders resolve to different files (a warning), viewport height units in the canvas's own CSS (a warning) and, with token CSS, hardcoded colors (a warning). Full criteria: ARCHITECTURE §1 'Conventions'. Shell check also records best-effort device-local session associations without changing findings/output (§3, ARCHITECTURE §4).
12. `doan export <canvas path> [--frame <id> --prototype] -o <file> [--force]`: writes one canvas as a single HTML file that opens without Doan, the repository or a network (item 3 'Export and viewer'); with `--frame <id> --prototype` the file plays that marked frame and the frames linked with it (`linkedFrames` counts the others), and the agent tells the person it still holds the whole canvas. It reads only repo files, so it works without the app. The agent runs it only when the person asks to export or share a canvas as a file, writes outside `.doan/`, and says when the result still needs the internet (`external`) or has links that won't work (`links`). An existing output file is replaced only with `--force`, which the agent uses only when the person agreed.

### Skills

13. The `doan` skill reaches the five providers' own sessions through agent setup (item 0) and Doan's provider profiles through agent-auth (ARCHITECTURE §6).
    - Design presets. The CLI bundles 20 presets adapted from Impeccable (catalog: `cli/internal/designskill/catalog.json`), with no aliases for upstream names. `doan design-skill` lists them and returns one body without a project or the running app (ARCHITECTURE §12). The `doan` skill stays the entry point: the agent that already does the work picks a preset from the request. A preset the user names comes first; otherwise one is used only when it clearly fits; a concrete edit needs none; a review ends with a report. There is no classifier model, no rewrite of the user's request and no automatic review.
      - The design-start preset is `context`, separate from CLI `doan init`, which only sets the project up and points agents to `context` without running a model or a preset.
      - `document` writes, only on request, a rules document for agents and design-system canvases in `.doan/ds/` for people. The rules document goes in the project's existing design document or where the user agrees, never under `.doan/`. An existing sufficient system is reused with its organization; a legacy `.doan/canvases/design-system.html` moves only with the user's agreement and keeps its ID. Maintenance changes only what drifted or was requested; a plain setup request is not approval to write a system, and code changes never start maintenance. Procedure: `cli/internal/designskill/presets/document.md`.
      - A `generate` variant draws the target's states or names those it leaves out. When a direction question gets no answer and the agent continues, it states the assumed direction on the canvas and in its answer.
      - The preset picker is in Home's and the docked composers (item 1 'Home'); app conversations tell the agent to find presets through the guide. Presets are shown in five groups (start, review, refine, content, explore) without changing the catalog order (ARCHITECTURE §12).

### Dogfooding: Doan's UI drafts live in Doan

- Design drafts for the Doan app UI are kept as canvases in this repo's `.doan/canvases/` (ARCHITECTURE §1 Conventions), and viewed and discussed in the Doan app's canvas conversation panel. Whether the implementation matches the design draft is compared via computed style (`/design-sync`).
- App screens run the design draft → implementation → comparison loop.
- A draft canvas that no screen uses any more is removed only when the user names it; until then it stays unchanged.
- The app's design system lives separately in `.doan/ds/`, one canvas per token group, shared component or shared surface; its rules and canvas index are in [DESIGN.md](./DESIGN.md#design-system).
