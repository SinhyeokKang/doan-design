# Doan Design — Product plan

> Source of truth for product judgment: problem, users, scope, core loop and MVP. It describes the product as it is now; history lives in git.
> Structure, formats and conventions live in [ARCHITECTURE.md](./ARCHITECTURE.md); measured UI values live in [DESIGN.md](./DESIGN.md). [README.md](../README.md) is the public introduction and is not a decision source.

## 1. Problem

The design drafts that coding agents make live outside the code, in external design services. This causes four problems; the arrow after each names the §3 'In scope' item that addresses it.

1. **Conversations split.** Design-draft and implementation conversations pile up separately in two tools, and some runtimes cannot reach the draft at all (Codex could not use Claude Design or DesignSync). → Deliver
2. **Agents cannot read design drafts properly.** Large files get truncated (DesignSync `get_file` caps at 256 KiB), and the agent does not know where the human pointed. → Show · Let humans point
3. **Design drafts do not know the code.** They do not know the real tokens or implementation, so they drift from it. → Tie to code · Check
4. **Records are locked into an external service.** When the service shuts down, the drafts and their feedback disappear: standalone Claude Design shuts down on 2026-12-14 without migrating chats and comments (support.claude.com/en/articles/17440474). → Show (the canvas is a file in the repo) · Conversation (kept on this device)

Source: the Malmoi case in the README background.

## 2. Users

The primary users are external users in general; installation, onboarding and documentation are in product scope.

Doan's own agent connections cover five providers — Claude Code, Codex, Cursor, Antigravity and GitHub Copilot — with one account each (§3 In scope 7); first run signs in to them and selects a project. Opening the packaged app from Applications also sets up the `doan` command and skill, with no setup screen, for the same five agents' sessions outside Doan (§5 item 0 'Agent setup'). A user who has only the app can ask their own agent to run first run through `doan onboarding`.

## 3. Scope

### In scope

1. **Show.** The app shows the canvas the agent wrote into the repo, with zoom and frame jumps. The canvas page has no inspector screen; a selection's styles and tokens are still collected for its planned new place (§5 item 4).
2. **Let humans point.** The human selects an element or frame, and puts frames, elements and spots inside frames into a message as chips (§5 item 6). Comments in repo files have no app screen; the CLI still reads and resolves them (§5 item 5).
3. **Deliver.** The agent receives the person's message with its anchors, or reads the selection (`active`) and existing comments through the CLI and skills, applies them and resolves the comments it applied. The app sets up the CLI and skill for the five providers' own sessions.
4. **Check.** `doan check` statically checks the canvas's conventions, tokens and external resources.
5. **Tie to code.** The canvas uses the repo's real token CSS, and frames point to implementation files (`data-doan-implements`).
6. **Conversation.** A human message starts a live conversation with the installed, logged-in Claude Code or Codex, either resuming the drawing session without forking or explicitly starting a new one. Each canvas has one current conversation; starting another archives the previous one. A project also holds conversations bound to no canvas (project conversations); promotion, restore, queueing and the anchor limit are §5 items 1 and 6. A queued message is still the person's message, not Doan waking the agent (Out of scope 4). Session associations and conversation events stay on this device, outside the repo.
7. **Agent authentication.** Users sign in from Doan and keep a Doan-specific connection, independent of Orca's or a terminal's login, with at most one account per platform. All five providers use their official login in a Doan-owned profile, keep credentials on this device, sign out locally and run new and canvas conversations on the connected account ([ARCHITECTURE §7 'Agent authentication'](./ARCHITECTURE.md#agent-authentication)).
   - Sign-in, check and sign-out happen in first run (agent sign-in → local folder or GitHub repository URL → Home) and, since first run cannot be reopened, afterwards in Settings > Agents (§5 item 0). Home's agent picker sends the person there (§5 item 1); conversations offer no sign-in.
   - A replacement sign-in that does not finish keeps the stored connection and its verified state.
   - Independent credentials do not establish external-session portability.

Doan handles installation and onboarding for these capabilities. Where conversations show is §5 items 0–3.

### Out of scope

1. **Drawing.** The agent draws the design draft. Doan is not a vector tool (Figma) where humans draw shapes.
2. **Enforcing a canvas format.** The agent decides sections, notes and layout. Doan's conventions are only the minimal attributes Doan reads (canvas, frame and element ids, frame title, implementation path, board width).
3. **Multiple accounts per agent platform.** Account pools and multiple-account selection are excluded (one account: In scope 7). Resuming a session found through a shell `doan check` association uses the installed, logged-in Claude Code or Codex CLI and its own profile (legacy external path). GitHub authentication for browsing or cloning repositories is deferred; Copilot's GitHub-based agent sign-in is separate. Cloning a GitHub URL uses the user's existing Git credentials and adds no GitHub sign-in, token storage or repository listing.
4. **Autonomous agent wake-up.** Only a human message starts agent work; Doan does not initiate it on its own.
5. **Server.** No accounts, sync or hosting. Sharing happens through git, and the web only serves as the download path.
6. **Git operations.** The agent makes commits and branches. Exception: first run and the Add Projects page clone a GitHub repository URL the user entered, with their existing Git credentials, into a destination they confirmed (§5 items 0 and 1). Doan runs no other git command (it reads remotes from `.git/config`) and does not pull, fetch, commit or branch.
7. **Simultaneous human/agent file editing.** A person talks while the agent edits and the app reloads; the person does not draw or directly edit the canvas in Doan.

### Agent conversation foundation contract

What the conversation runtime promises. The UI is §5 items 1–3; SDK, transport, processes, admission and IPC are [ARCHITECTURE §7 'Agent conversation runtime and IPC'](./ARCHITECTURE.md#agent-conversation-runtime-and-ipc).

- **Transport and evidence boundary.** Claude Code and Codex conversations run on the user's installed CLI; Doan bundles no replacement, and a missing executable is refused. Required CLI versions are verified minimums (Claude Code 2.1.312, Codex 0.164.0), not pins: a newer CLI runs until a new session shows a protocol Doan cannot read. A below-minimum or unreadable version refuses a new session (`runtime_unsupported`) and resume or send (`session_unavailable`). Stored sessions stay resumable from fixed floors that do not follow the minimums, and a conversation's stored session resumes after an app restart.
- **Association recording.** Only a shell `doan check`, passing or failing, records which session changed which canvas. It never changes check output or exit codes, silently skips what it cannot record, and asks agents to manage no session IDs (ARCHITECTURE §4 'Shell check session associations').
- **Session identity and paths.** Every association and app-created conversation records its profile (`configDir`); an unset or empty configuration variable means HOME/.claude or HOME/.codex. Records are untrusted: resume requires the record's profile to match the currently selected one and its cwd to lie inside the same project root. A record never selects an arbitrary profile or copies credentials; a mismatch makes resume unavailable, never a fallback to another profile, cwd or session.
- **Resume and permissions.** Within the verified scope, resume continues the same session and transcript; Doan never forks or silently starts a new session. A turn runs in the permission mode the person picked (item 1 'Permission picker'); Default applies the user's own permission and sandbox settings. Doan picks no mode itself, with one exception: after the person approves a Claude plan, the conversation follows the mode the SDK reports, except Full access, which reads as Default. Doan forwards the runtime's real approval requests and invents none. Denying is not stopping, and a stop the person asked for is not a successful turn. The verified allow/deny cases do not prove every policy/hook combination.
- **Live terminal policy.** Before each resume or send Doan rechecks the session: one open in a terminal is `session_in_use`, one it cannot verify is `session_unavailable`. This is a best-effort check, not a lock. Doan never kills the user's Codex daemon.
- **Events and ownership.** Conversation events are stored on this device as they happen; a reload keeps them and the live turn. After a restart, unanswered approvals expire and unfinished turns show as interrupted. Doan runs one turn per session at a time and never forks or takes over a session. Doan-connection conversations (In scope 7) follow the same rules.

## 4. Core loop

### Unit of review: one spec = one canvas

- One spec (one ticket) — user flow, per-state guides for blocks and components, layout and spacing, copy — is reviewed on **a single canvas** holding **multiple frames**; the human zooms and picks a frame.
- **One canvas = one HTML file in the repo.** The agent decides whether to keep shared shells or assets separately.
- **Frames are what the agent marks with `data-doan-frame="id"`**; the agent decides layout and look. The frame list, jumps, anchors and comment targets use this id.
- **Ids do not change**, so anchors, comments and conversations follow a moved file or renamed title. The agent names canvas and frame ids when it creates them, and `doan check` catches duplicates and omissions (ARCHITECTURE §1 'Conventions').
- **A frame can point to its implementation file** (`data-doan-implements`), per frame, since each frame has its own.
- **The agent organizes the inside of a canvas.** Doan fixes no section categories, note format or layout. References only:
  - A Figma design guide (Skillflo B2E, FCLXP-13938 learning dashboard revamp) places `user-journey-map` · `template-guide` · `layout-guide` · `i18n-guide` side by side.
  - Claude Design's canvas guide (`Language Request Todo.dc.html`, Malmoi project): one page per spec, an intro, then numbered frames, each a screen render beside note cards holding design decisions and their rationale.

### Loop

1. **The agent writes the canvas** at `.doan/canvases/<spec>.html` and checks it with `doan check`.
2. **The human views it in the app**, which live-reloads when the file changes.
3. **The human points** with chips (§5 item 6) or a selection. Existing comments in `.doan/comments/` stay readable to the agent; the app has no comment screen.
4. **The human talks to the agent**, in the canvas's conversation panel, where chips arrive as anchors, or to their own agent outside Doan, which finds the target via `active`. Doan does not wake the agent itself.
5. **The agent applies it**: anchors, or `doan active` and `doan comments` → edit → `doan check` → `doan comment resolve` for applied comments. Back to 2.

## 5. MVP

What the human does is **view + point + talk**; approval is deferred until after the MVP. Human-facing text (app screens, onboarding, menus, CLI messages, the guide, the skill stub, docs prose) names the product Doan; only places that already used the full name keep Doan Design (the window title, the `doan skill` guide's heading and the titles of PRODUCT.md and ARCHITECTURE.md), and the full name is not added elsewhere. Commands, paths and identifiers stay lowercase (`doan` and its subcommands, `.doan/`, `data-doan-*`, appId `design.doan.app`, userData `doan`); the app bundle is `Doan.app`. App UI copy is English; a folder is called "Project" on screen, while code names and docs keep "folder".

   - Strip, slots, the reason line, the removal question and Edit on Home come from main's conversation list, so they survive a reload and a restart; after either, the strip shows only Home conversations with work left (running, waiting, or an unseen ending; a turn cut off by the restart is an unseen stop), so a failed or stopped conversation already seen is no longer reachable from the strip or Edit on Home (ARCHITECTURE §7 'Home, workspace and project IPC' 'Home conversations'). Within a run a strip stays until Dismiss. A start has no cancel while the provider opens.
   - **Project conversations.** A conversation bound to no canvas (every Home conversation until promoted) is a project conversation. While one works in a root (preparing, running, waiting, ended under 10 seconds ago and not yet judged, or about to send its queue), no other project conversation can start or send there; canvas conversations and other roots are not limited.
     - Promotion is judged once per turn, at the first folder refresh after it ends or 10 seconds after: exactly one canvas new since the turn was accepted wins; with none new, exactly one existing canvas qualifies when the turn's own edit activity names it and the file changed during the turn. Several candidates, a refused edit, or a target whose current conversation is working leave it a project conversation. A promotion archives the canvas's previous current conversation and moves no screen; Home's guidance to the agent stops then. A send to the same conversation waits until the previous turn is judged.
     - Edit evidence is confirmed only for Claude Code and Codex (ARCHITECTURE §7 'Project conversations and promotion'); other providers only miss edit promotions, and new canvases bind for every provider.
     - Limit: within one turn, a refused edit and someone else's change to the same canvas file cannot be told apart, so that turn is promoted.
     - A message queued while its conversation works goes out after a done turn; after a failed or stopped turn, an archive, a sign-out or a refused send, the queue comes back as the draft. Queued messages survive a reload; after a restart they come back as a draft, never sent by themselves.
     - A send to an archived conversation restores it, unless the canvas's current conversation works or the canvas left the project or its ID is listed twice; a refusal changes nothing.
     - The project Overview hosts thread, composer, queue, restore and switching for project conversations (item 3); the canvas page's conversation panel does the same for its canvas (item 2 'Conversation panel').
   - Measured appearance, draft deviations and unreached states are in [DESIGN.md](./DESIGN.md#home) ('Home', 'Add Projects page', 'Projects home'). First run and the Add Projects page share the Project step and one addition decision (ARCHITECTURE §7 'Settings IPC' 'Project addition').

   - **Layout.** A canvas header above the board, a toolbar floating on the board, and the conversation panel (below) in the right column; measured layout in [DESIGN.md](./DESIGN.md#canvas-area-and-right-panel).
   - **Canvas header.** The canvas name, the frame drawer (item 3), the zoom controller and Reload canvas; Show conversation ends it while the panel is folded. A page that is not a listed canvas, and a project problem, show no canvas name and a disabled frame drawer.
   - **Zoom controller.** A whole percent with a menu of Fit (⌘1), 100% (⌘0), 50% and 200%. It is disabled while no board is rendered (loading, failed, no width, not a listed canvas, a project problem); a canvas with no frames zooms normally. Reload canvas (like ⌘R) stays enabled whenever a canvas is open, also while it loads, failed or has no width.
   - **Toolbar.** Select, always pressed, and Add to conversation (item 6). A click in the canvas always selects; Option-click passes through.
   - **Fit and frame moves** keep the frame clear of the header and the toolbar, also for the first Fit of a canvas opened from the Overview (ARCHITECTURE §3 'Canvas view').
   - **Notices and states.** Canvas notices and status messages float at the board's top centre, under the agent notice; toasts sit at the window's bottom right. Esc closes an open menu or popover first, then the `/` list, then cancels a pick, and only then clears the selection.
   - **Conversation panel.** The right column shows this canvas's conversations — title menu, a New conversation button, thread and docked composer — with the Overview's parts and rules (item 3 'Project Overview'). Hide conversation folds it and the canvas takes the width. Project conversations and other canvases' conversations never show here; the sidebar slots and the permission toast tell about them.
     - Title menu: New conversation, then this canvas's conversations, the current one first and the rest by most recent activity. A failed list read offers Retry and leaves the composer usable as a new conversation.
     - Which conversation shows: a requested one, else the canvas's current conversation, else the new conversation state. An archived conversation shows only when chosen from the menu, and a send restores it. While the canvas's current conversation works, a restore and a new-conversation send are held.
     - New conversation (the menu, ⌘N): suggested prompts by Home's rules. The first send starts a conversation bound to this canvas with the composer's provider, model, effort, permission mode and attachments, and archives the previous current one. Each canvas keeps its own new-conversation draft, shown nowhere else.
     - Terminal session: when a shell `doan check` recorded a resumable session association for this canvas (§3 'Association recording'), the new conversation state offers continuing that session (the default choice) or a new conversation. Continuing resumes it with the installed CLI (§3 Out of scope 3) and takes no model, effort, permission mode or attachments. The association is asked for once per visit and Send waits for it; a refused continue offers a new conversation and keeps the draft.
     - Drawing and promotion: while a project conversation is drawing this canvas (its turn created it and promotion is not judged yet), the new conversation state says a send here starts a separate conversation; sending is not held. When that conversation is promoted while the panel is open, the panel keeps what it shows and adds a notice with Open.
     - Opening: every entry that names a canvas conversation (the Overview's row, toast and notification Open, the agent notice, a sidebar canvas slot, Add to conversation, ⌘N) unfolds a folded panel on it; a permission entry focuses the request's first choice, the others the composer. An agent starting, asking or ending never unfolds the panel; while folded, Show conversation carries a dot while this canvas's current conversation waits for an answer or has an unseen ending.

     - Refusals keep the composer's text, chips, attachments and preset. On a page that is not a listed canvas, or a canvas whose ID another canvas shares, the composer keeps its draft but takes no input and says why.
     - Width: resizable from its left edge, within limits that follow the window and leave the canvas room (DESIGN.md 'Panel width'); a saved width above the widest shows at the widest without being rewritten. Open/folded and width are remembered on this device for every canvas.
   - **Agent indicator.** While the canvas's current conversation works or waits for an answer, the board shows a glow, a dot field and a notice: “Agent is working” with Stop, or “Agent needs your answer” with Open and no Stop (the request has its own). It follows only the current conversation of this canvas in this project root: another canvas's conversation, a project conversation or a twin canvas (same id or path) in another worktree never shows or stops it. It shows while the canvas loads, failed or has no width, not on an unlisted page or a project problem, and disappears when the turn ends. Stop ends the turn without asking; a failed stop returns Stop with a toast. It never blocks selecting, panning or zooming.
3. **Design navigation**
   - The project/canvas shell tree is described in item 1. Arrow keys, Home/End and typeahead move through visible rows and open and close groups (`ShellSidebar.tsx`). Current projects remain expanded; other project expansion persists.
   - **Frame drawer.** The header's drawer shows the frame being viewed (nearest the view's centre) by number and title or id. It lists frames in document order without search, up to the first 1,000, then points to Quick Open. Picking a row moves the view to that frame and selects it, so `doan active` returns it; the pick resolves by frame id, so reordered frames still give the picked one and a gone frame does nothing. It is disabled where the zoom controller is.
   - Quick Open's frame jumps move the viewport and highlight the frame without changing selection, the panel, drafts or `doan active`. Reopening the same canvas does nothing; Reload remains available. The sidebar has no frame rows or frame selection controls.
   - **Project Overview.** With no canvas open, a workspace shows the project Overview, the project's conversation screen: a header, the shown project conversation's thread and docked composer, and the Canvas conversations list in the right panel. It is reachable from each project menu, the sidebar project row, Home's Send, the permission toast, notifications and “Open the running conversation”. It shows no Doany, greeting, gradient or conversation strip.
     - Header: project, branch chip and conversation title. With two or more registered worktrees the chip switches worktree as the project menu does; with one it is read-only. The composer has no worktree choice, because a conversation stays with the worktree it started in.
     - Conversation menu: New conversation, then the project conversations (bound to no canvas), most recent activity first. New conversation and ⌘N (enabled on an Overview or canvas page) go to the new conversation state, keeping its draft. Switching conversations adds no Back/Forward visit.
     - The new conversation state shows suggested prompts by Home's rules and conditions (item 1); a suggestion fills the composer and never sends. A failed list read offers Retry, and the composer stays usable.
     - Which conversation shows: a requested one (Home's Send, a toast's or notification's Open, “Open the running conversation”, the sidebar slot) — a canvas conversation instead opens its canvas with the panel unfolded (item 2). Otherwise, once the list is read: the project conversation this device last showed for that root unless it was promoted since, else the most recently active readable one, else the new conversation state. An unreadable requested or remembered conversation still shows, with its read failure. Details: ARCHITECTURE §7 'Project Overview conversations'.
     - Promotion: when the shown conversation is promoted (item 1 'Project conversations'), the main column resets to the new conversation state, the draft moves with it and focus stays in the composer. A line saying it moved to that canvas, with Open, stays until the next send or choice. If the person had seen that turn's end, the conversation is seen through its promotion.
     - Seen: a project conversation is recorded as seen only while the Overview shows it and the window has focus; opening a workspace or Overview records none.
     - While another conversation shows, a project conversation of the same root that waits for an answer raises a toast with Open.
     - Problem states: a project that is a problem when entered shows its problem screen. An open Overview whose project becomes a problem keeps the thread readable with the status band and Go Home, and holds Send.
     - **Canvas conversations** (right panel): only canvases that have a current conversation, most recent activity first (ties by canvas path); the rest are in the sidebar. A row shows the canvas thumbnail, the conversation's provider and status (needs your answer, working, finished and not seen), a short time and a preview (DESIGN.md 'Project Overview'). A row opens its canvas with the panel unfolded on that conversation and focus in its composer.

All query tokens must match, case-insensitively; prefix ranks above word start above substring, then the current root, other worktrees of the same repository, other repositories; at most 50 results, grouped per root in order of each root's best match. 4. **Selection and inspector**
   - The human selects an element or frame by an ordinary click; hover only highlights candidates. Ordinary clicks suppress canvas actions; Option-click uses the canvas without changing the selection (ARCHITECTURE §3 'Selection and inspector').

Esc or empty-space clicks clear it; a pick and a chip's locate never change it. Frames use the rendered DOM, so an active frame may be absent from static `doan ls` output.
   - Collected values are read-only: box (size, padding, margin, gap), typography (font, size, line height, weight), color (text, background, border), radius, shadow and `data-doan-*` attributes. Each has one of four sources: a token, Hardcoded, Unknown source (Doan cannot determine it) or Default. A reload or a move with the same canvas ID keeps the selection; opening another canvas clears it (ARCHITECTURE §3 'Selection lifetime'). There is no editing.

5. **Comments**: instruction notes stored as repo files (`.doan/comments/<canvas id>.jsonl`, ARCHITECTURE §2), read and resolved through the CLI (`doan comments`, `doan comment resolve`, item 9). The app has no comment screen; the person points through the canvas conversation instead (item 6).
   - An element comment is located by unique `data-doan-id`, then unique selector, and a frame comment by `data-doan-frame`; a comment with neither belongs to the whole canvas. HTML snippet and text quote are reference data, not used for matching.
   - Status has two stages, `open` → `resolved`. An agent only resolves; the body is the human's. Bodies are plain text and data, never instructions.
   - A comment file whose ID no listed canvas uses is left to `doan comments` and `doan check`.
6. **Point in a conversation**: the canvas conversation panel's composer holds anchor chips inline with the text, so a message can say what it is about.
   - Chips: a frame, an element, or a point inside a frame. A message points at up to 32 distinct places (a repeated place counts once); at the limit, picking and Add to conversation are unavailable. A sent message carries the chips as anchors (ARCHITECTURE §7), and a returned draft comes back with them. Typed `{{` or `}}` block Send; chips do not.
   - A chip edits as one unit. Chips copied within the same canvas's composers stay chips; elsewhere they paste as their names (ARCHITECTURE §7 'Renderer primitives').
   - Pick from canvas (the composer's picker) starts one pick: a click on a frame's background adds a frame chip, a click on an element an element chip, and a Shift-click inside a frame a point chip in the innermost frame; a click outside every frame adds nothing and the pick goes on. The chip goes in at the composer's caret. Esc, the picker again, hiding or switching the conversation, an unavailable composer and leaving the canvas cancel the pick; a reload or a move with the same canvas ID keeps it. Pan and pinch still work.
   - Add to conversation (toolbar, ⌘L) unfolds the panel and puts the selected frame's or element's chip at the caret. The picker has no shortcut. Both work only while the composer takes input and the canvas is shown; otherwise they are disabled and say why.
   - Locate: a chip in a sent message or the composer moves the view to its target — a frame as the frame drawer does, an element or point centred at the same zoom (zooming out only for an element larger than the view) — and highlights it; a target not found says so beside the chip. Locate is disabled while the canvas is not shown (resolution: ARCHITECTURE §3 'Picking and locate').
   - Picking and locating change neither the selection, `doan active` nor the composer's text. A sent chip stays as sent when its target later moves. Home's and the Overview's composers take no chips; chips point only into the open canvas.

### CLI `doan`

8. `doan init`: creates `.doan/canvases/` and `.doan/config.json`, sets up `.gitattributes` (union merge for comments, `.doan/` as documentation) and asks for the token CSS path — the terminal form of the app's project setup (Set Up… in the sidebar project menu, first run's Set up and continue). It does not install skills: opening the app sets up the skill (item 0 'Agent setup').
9. `doan ls` · `doan comments` · `doan comment resolve` · `doan skill` · `doan config`. They only read and write repo files, so they work without the app. `ls` also reports Git branch/worktrees. One unreadable file does not fail `ls`: it marks the affected rows instead of reporting zero comments, and lists comment files no canvas uses as orphans (ARCHITECTURE §12). `doan comments`, `doan check` and `doan comment resolve` fail as a whole when they cannot read a file they need.
10. `doan active`: returns the frame or element the human selected in the app. Lets the agent find the target from just "fix this". Requires the app to be running. `doan onboarding …` drives first run through the running app; only `onboarding start` from the bundled CLI may open the app (item 0).
11. `doan check` does **static checks only**: what HTML parsing alone can catch — undefined tokens, duplicate or missing ids, missing `doan:width` (an error), comment files with no matching canvas, missing `data-doan-implements` targets, external URLs (a warning, not blocked) and, with token CSS, hardcoded colors (a warning). An orphan comment file's warning tells the agent to restore the canvas id or ask the user, never to delete or rewrite the file. Full criteria: ARCHITECTURE §1 'Conventions'. Shell check also records best-effort device-local session associations without changing findings/output (§3, ARCHITECTURE §4).

### Skills

13. The `doan` skill reaches the five providers' own sessions through agent setup (item 0) and Doan's provider profiles through agent-auth (ARCHITECTURE §6).
    - Design presets. The CLI bundles 20 presets adapted from Impeccable (catalog: `cli/internal/designskill/catalog.json`), with no aliases for upstream names. `doan design-skill` lists them and returns one body without a project or the running app (ARCHITECTURE §12). The `doan` skill stays the entry point: the agent that already does the work picks a preset from the request. A preset the user names comes first; otherwise one is used only when it clearly fits; a concrete edit needs none; a review ends with a report. There is no classifier model, no rewrite of the user's request and no automatic review.
      - The design-start preset is `context`, separate from CLI `doan init`, which only sets the project up and points agents to `context` without running a model or a preset.
      - `document` writes, only on request, a rules document for agents and design-system canvases in `.doan/ds/` for people. The rules document goes in the project's existing design document or where the user agrees, never under `.doan/`. An existing sufficient system is reused with its organization; a legacy `.doan/canvases/design-system.html` moves only with the user's agreement and keeps its ID. Maintenance changes only what drifted or was requested; a plain setup request is not approval to write a system, and code changes never start maintenance. Procedure: `cli/internal/designskill/presets/document.md`.
      - A `generate` variant draws the target's states or names those it leaves out. When a direction question gets no answer and the agent continues, it states the assumed direction on the canvas and in its answer.
      - The preset picker is on Home (item 1 'Home'); app conversations tell the agent to find presets through the guide. Presets are shown in five groups (start, review, refine, content, explore) without changing the catalog order (ARCHITECTURE §12).

### Dogfooding: Doan's UI drafts live in Doan

- Design drafts for the Doan app UI are kept as canvases in this repo's `.doan/canvases/` (ARCHITECTURE §1 Conventions), and viewed and discussed in the Doan app's canvas conversation panel. Whether the implementation matches the design draft is compared via computed style (`/design-sync`).
- App screens run the design draft → implementation → comparison loop.
- A draft canvas that no screen uses any more is removed only when the user names it; until then it stays unchanged.
- The app's design system lives separately in `.doan/ds/`, one canvas per token group, shared component or shared surface; its rules and canvas index are in [DESIGN.md](./DESIGN.md#design-system).
