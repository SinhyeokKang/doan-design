# Doan Design — Product plan

> Source of truth for product judgment: problem, users, scope, core loop and MVP. It describes the product as it is now; history lives in git.
> Structure, formats and conventions live in [ARCHITECTURE.md](./ARCHITECTURE.md); measured UI values live in [DESIGN.md](./DESIGN.md). [README.md](../README.md) is the public introduction and is not a decision source.

## 1. Problem

The design drafts that coding agents make live outside the code (in external design services). This causes four problems. The arrow at the end of each problem points to the §3 'In scope' item that addresses it.

1. **Conversations split.** Design-draft conversations and implementation conversations pile up separately in two tools. Depending on the runtime, the agent cannot even reach the design draft (Codex could not use Claude Design or DesignSync). → Deliver
2. **Agents cannot read design drafts properly.** Large files get truncated (DesignSync `get_file` caps at 256 KiB), and the agent does not know where the human pointed. → Show · Let humans point
3. **Design drafts do not know the code.** They do not know the real tokens or implementation, so they drift from the implementation. → Tie to code · Check
4. **Records are locked into an external service.** When the service shuts down, the drafts and the feedback on them disappear. Standalone Claude Design shuts down on 2026-12-14, and chats and comments are not migrated (support.claude.com/en/articles/17440474). → Show (the canvas is a file in the repo) · Conversation (kept on this device)

Source: the Malmoi case in the README background.

## 2. Users

The primary users are external users in general. Installation, onboarding and documentation are within product scope.

Doan's own agent connections cover five providers — Claude Code, Codex, Cursor, Antigravity and GitHub Copilot — with one account each (§3 In scope 7). First run signs in to these connections and selects a project. Separately, opening the packaged app from Applications sets up the `doan` command and the `doan` skill for the sessions of the same five agents that the user runs outside Doan, in a terminal or another app, with no setup screen (§5 item 0 'Agent setup'). A user who has only the app can also ask their own agent to run first run through the bundled `doan onboarding` commands.

## 3. Scope

### In scope

1. **Show.** The app shows the canvas the agent wrote into the repo, with zoom in/out and frame jumps. The canvas page has no inspector screen: the styles and tokens of a selected element are still collected, and the inspector's new place is planned (`docs/features/buzz-restyle/`).
2. **Let humans point.** The human selects an element or frame in the canvas, and puts frames, elements and spots inside frames into a conversation message as chips (§5 item 6). Instruction notes (comments) stored as repo files have no app screen; the CLI still reads and resolves the ones that exist (§5 item 5).
3. **Deliver.** The agent receives the person's message with its anchors in the conversation, or reads the target the human selected (`active`) and any existing comments through the CLI and skills; it applies them and resolves the comments it applied. The app sets up the CLI and the skill for the five providers' own sessions.
4. **Check.** `doan check` statically checks the canvas's conventions, tokens and external resources.
5. **Tie to code.** The canvas uses the repo's real token CSS, and frames point to implementation files (`data-doan-implements`).
6. **Conversation.** A human message starts a live conversation with the installed, logged-in Claude Code or Codex, either resuming the drawing session without forking or explicitly starting a new session. There is one current conversation per canvas; starting another archives the previous one. A project also holds conversations bound to no canvas (project conversations), any number of them, of which only one works at a time. A project conversation whose turn creates or edits a canvas is promoted: it becomes that canvas's current conversation and the canvas's previous current conversation is archived (§5 item 1 'Project conversations'). An archived conversation stays readable, and a message sent to it makes it current again, archiving the one it replaces. A message sent while its conversation works waits in a queue and goes out, joined with the others, as one message after the turn ends; it is still the person's message, not Doan waking the agent (Out of scope 4). A message may point at up to 32 distinct frames, elements and spots inside frames (anchors), which the person adds from the open canvas as chips (§5 item 6). Session associations and conversation events stay on this device, outside the repo.
7. **Agent authentication.** Users sign in from Doan and retain a Doan-specific agent connection independently of Orca or a terminal's login. At most one connected account per platform; multiple accounts per platform are excluded. All five providers are implemented — Claude Code, Codex, Cursor, Antigravity and GitHub Copilot: the official login of each provider in a Doan-owned profile, credentials in the OS keychain (Claude Code, Codex) or an OS-encrypted vault (Cursor, Antigravity, Copilot), local sign-out, and new and Canvas conversations on the connected account ([ARCHITECTURE §7 'Agent authentication'](./ARCHITECTURE.md#agent-authentication)). The backend covers OAuth, encrypted credential persistence, refresh, local logout and shared authenticated execution for new and Canvas conversations; UI stays with the consuming screens.
   - First run (agent sign-in → local folder or GitHub repository URL → Home) and Settings > Agents sign in, check and sign out, both through the shared provider view-model (§5 item 0); first run cannot be reopened, so Settings > Agents is where sign-in happens after it. Home holds the single conversation composer and project picker; it reads readiness for its agent picker, whose actions open Settings > Agents (§5 item 1). Conversations themselves offer no sign-in.
   - A replacement sign-in that does not finish keeps the stored connection verified, and a Codex replacement signs in to a staging profile first.
   - Real token expiry and refresh have not been observed. Independent credentials do not establish external-session portability. Repository authentication, listing and cloning are outside agent authentication.

Doan handles installation and onboarding for these capabilities. Conversations show on Home's composer, the project Overview (the thread, the docked composer and the canvas conversations list, §5 item 3), the canvas page's conversation panel (§5 item 2 'Conversation panel'), the temporary conversation strip on a problem workspace, the sidebar status slots, the permission toast (§5 item 1) and macOS notifications (§5 item 0 'Notifications'). A canvas page also shows when its canvas's current conversation works (§5 item 2 'Agent indicator'); it shows no Inspector, Canvas info or comment screen. The planned inspector is in `docs/features/buzz-restyle/`.

### Out of scope

1. **Drawing.** The agent draws the design draft. Doan is not a vector tool (Figma) where humans draw shapes.
2. **Enforcing a canvas format.** The agent decides sections, notes and layout. Doan's conventions are only the minimal attributes Doan reads (canvas, frame and element ids, frame title, implementation path, board width).
3. **Multiple accounts per agent platform.** Single-account agent authentication is in scope (In scope 7); account pools and multiple-account selection are excluded. Resuming a session found through a shell `doan check` association still uses the installed, logged-in Claude Code or Codex CLI and its own profile (legacy external path). GitHub authentication for repository browsing or cloning is deferred; Copilot's own GitHub-based agent authentication is a separate concern. First run's clone of a GitHub URL uses the user's existing Git credentials (credential helper or SSH) and adds no GitHub sign-in, token storage or repository listing.
4. **Autonomous agent wake-up.** Only a human message starts agent work; Doan does not initiate it on its own.
5. **Server.** No accounts, sync or hosting. Sharing happens through git, and the web only serves as the download path.
6. **Git operations.** The agent makes commits and branches. Exception: first run and the Add Projects page clone a GitHub repository URL the user entered, with the user's existing Git credentials, into a destination they confirmed, through the same clone code and cleanup rules (§5 items 0 and 1). Neither runs any other git command (remotes are read from `.git/config`), and Doan does not pull, fetch, commit or branch.
7. **Simultaneous human/agent file editing.** A person talks while the agent edits and the app reloads; the person does not draw or directly edit the canvas in Doan.

### Agent conversation foundation contract

This section is the backend and preload contract; the conversation UI is §5 items 1–3. [ARCHITECTURE §7](./ARCHITECTURE.md#agent-conversation-runtime-and-ipc) records the implemented interfaces and limits.

- **Transport and evidence boundary.** Use the official Claude Agent SDK, bundled at exactly 0.3.312, with the installed Claude Code executable (`pathToClaudeCodeExecutable`, user/project/local setting sources), and the installed Codex direct app-server. A fresh Claude SDK/CLI runs per turn and one persistent Codex app-server per conversation, matching the measured execution paths; owned processes close on archive/quit and the stored identity resumes after restart. No ACP adapter or separate agent CLI is bundled for Claude Code or Codex; Cursor, Antigravity and Copilot run through ACP runners on Doan connections, and only the sha-pinned Antigravity server is downloaded (ARCHITECTURE §7). Provider CLI versions are verified minimums (Claude Code 2.1.312, Codex 0.164.0), not exact pins: a newer installed CLI runs until a new-session handshake shows a protocol shape Doan cannot read (ARCHITECTURE §7). The package excludes SDK platform CLI packages; a missing installed executable is refused without SDK binary fallback. The managed Codex daemon (observed on 0.164.0) is a competing writer, not a verified replacement app-server. Below-minimum or unreadable versions refuse resume/send with `session_unavailable` and new-session startup with `runtime_unsupported`; stored sessions are accepted from fixed floors (Codex rollout header 0.163.0, Claude registry 2.1.312).
- **Association recording.** Only shell `doan check` records changed canvas hashes, on either success or failure, in existing userData's `sessions.jsonl`. Claude uses `CLAUDE_CODE_SESSION_ID`; Codex uses `CODEX_THREAD_ID` (or `CODEX_SESSION_ID` when the former is absent); conflicting Codex IDs or both runtimes' IDs skip recording. Missing/invalid identity or paths and write failures silently skip the side effect, preserving all check output and exit codes. `DOAN_RUNTIME` selects the record's directory without a socket; invalid overrides skip recording rather than break check. Agents are not asked to switch tools or manage session IDs.
- **Session identity and paths.** Records include required `configDir` as well as runtime, session ID, root, canvas, hash, cwd and time. Normalize unset/empty configuration variables to HOME/.claude or HOME/.codex, and resolve existing directories to canonical absolute paths. A nonempty relative/invalid configuration path is not a default. Treat every record as untrusted: validate before lookup/spawn, require configDir to match the currently selected shell-probed runtime configuration, and require canonical cwd to exist inside the same stored root. Config paths may legitimately be outside the repo; they never authorize selecting an arbitrary profile or copying credentials. A profile mismatch or missing directory makes resume unavailable, never a fallback to another profile/cwd/session. Persist this identity for app-created conversations too; `new`/`newDesign` use the selected configuration and project root.
- **Resume and permissions.** Both runtimes have shell IDs and support same-ID, same-transcript resume within the verified scope; never fork or silently create a new session on failure. Inherit effective user/project permissions and sandbox settings without forcing bypass, auto-review or an ACP preset. Forward actual approval requests and their supported choices; deny is not interrupt, and an explicit user stop is not a successful turn. No prompt is fabricated when the user's policy already allows or denies an operation. The verified allow/deny cases do not prove every policy/hook combination.
- **Live terminal policy.** Provide Claude resume despite the residual check-to-use/later-attachment race. Immediately before each resume/send, recheck the verified version, registry and OS PID/start identity. An already-open matching terminal is `session_in_use`; an unverifiable version/registry/PID is `session_unavailable` (fail closed). This accepts only the race after a successful check, not unknown detection, atomic exclusivity or live terminal synchronization. Codex active-writer rejection is `session_in_use`, including a daemon retaining ownership after terminal exit; never kill the user daemon.
- **Events and ownership.** Store ordered events immediately and expose the same events through main-window-only IPC. Normalize Claude aborted-tools and Codex interrupted completion after a requested stop to interruption (otherwise a failed turn), actual denial to permission resolution (the turn may continue), and active-writer refusal to `session_in_use`. Unknown/missing session or unverifiable identity is `session_unavailable`; unsupported runtime version is `runtime_unsupported` for a new session and `session_unavailable` for resume/send. No automatic fork, takeover or user-daemon termination. A renderer reload reads persisted events and continues the live subscription; after app restart, unresolved approvals expire and unfinished turns fold to crashed interruptions. Main reserves each runtime/configDir/sessionId before accepting work and releases it only after the owned process group is confirmed gone; an idle Codex server retains ownership. This is app-local reservation, not an external lock. Doan-connection conversations (In scope 7) use the same events, permissions and IPC. Detailed admission, persistence and permission contracts are in ARCHITECTURE §7.

## 4. Core loop

### Unit of review: one spec = one canvas

- The whole design spec of one spec (one ticket) is reviewed on **a single canvas**. The design spec contains the user flow, per-state guides for blocks and components, layout and spacing guides, and copy guides.
- **One canvas holds multiple frames.** Canvas and frame are not 1:1.
- The human zooms the canvas in and out and picks a specific frame to review.
- **One canvas = one HTML file in the repo.** The agent decides whether to keep a shared shell or assets separately and reference them.
- **Doan recognizes frames by the `data-doan-frame="id"` attribute.** The agent attaches this attribute to the elements it wants treated as frames and freely decides layout and look. The frame list, jumps, anchors and comment targets use this id.
- **Ids do not change**, so anchors, comments and a canvas's conversations follow even when a file moves or a title changes.
  - Canvas id: `<meta name="doan:canvas" content="id">` inside `<head>`.
  - Frame id: the `data-doan-frame` value. The visible name is kept separately in `data-doan-title` (optional).
  - The agent names the id when it first creates it. `doan check` catches duplicates and omissions.
- **A frame can point to an implementation file**: `data-doan-implements="app/projects/new/page.tsx"`. Since one canvas has multiple frames and each frame has a different implementation file, this is set per frame, not per canvas.
- **The agent decides how to organize the inside of a canvas.** Doan does not fix the shape of the guide (section categories, note format, layout). The cases below are references only, not a format to follow.
  - A Figma design guide (Skillflo B2E, FCLXP-13938 learning dashboard revamp). One section places `user-journey-map` · `template-guide` (per-block structure diagram, states, branches, layout) · `layout-guide` · `i18n-guide` side by side.
  - The way Claude Design spreads a design guide over a canvas (`Language Request Todo.dc.html`, about 30 KB, from the Malmoi project):
    - One HTML page with `<meta name="design_doc_mode" content="canvas">` is one spec.
    - Header: a one-line spec title and an intro paragraph. The intro paragraph gives the brief path, the implementation components touched, the source of the dimensions, and notation rules.
    - The body stacks numbered frames (1–8, 5b) vertically. Each frame consists of a header (number badge · title · implementation file path), a screen render on the left (fixed width · theme · locale), and a 400px column of note cards on the right. Note cards hold design decisions and their rationale, with tags like "not in code · i18n key".
    - Screens are drawn with templates (`sc-for`·`sc-if`) and data inside a script (`renderVals`). Fonts and icons are loaded from a CDN.

### Loop

1. **The agent writes the canvas.** It writes `.doan/canvases/<spec>.html` and verifies it itself with `doan check` (static).
2. **The human views it in the app.** They view with zoom in/out and frame jumps, and the view live-reloads when the file changes.
3. **The human points.** They put frames, elements and spots of the canvas into a message as chips (§5 item 6), or select an element or frame in the canvas. The app has no comment screen (§5 item 5); the comments already in `.doan/comments/` stay readable to the agent.
4. **The human talks to the agent.** In the canvas's conversation panel they say "fix this" with the chips, which reach the agent as anchors; or they tell their own agent outside Doan, which finds the target via `active`. Doan does not wake the agent by itself.
5. **The agent applies it.** It reads the anchors in the message, or `doan active` and `doan comments` → edits the canvas → `doan check` → `doan comment resolve` for any comment it applied. Then back to 2. The human checks the canvas in the app.

## 5. MVP

What the human does is **view + point + talk**; approval is deferred until after the MVP. Human-facing text (app screens, onboarding including the Welcome wordmark, menus, CLI messages, the guide, the skill stub, docs prose) names the product Doan; only places that already used the full name keep Doan Design (today the window title, the `doan skill` guide's heading and the titles of PRODUCT.md and ARCHITECTURE.md), and the full name is not added elsewhere. Commands, paths and identifiers stay lowercase (`doan` and its subcommands, `.doan/`, `doan:` meta keys, `data-doan-*`, `window.doan`, appId `design.doan.app`, userData `doan`); the app bundle is `Doan.app`. App UI copy is English; a folder is called "Project" on screen, while code names and docs keep "folder".

   - The human selects an element or frame by an ordinary click; hover only highlights candidates. Ordinary clicks suppress canvas actions. Option-click uses the canvas without changing the selection; links navigate through the existing same-folder-key gate.

   - One in-memory selection exists app-wide, shared by the inspector's collection, Add to conversation (item 6) and `doan active`. `active` returns it only for its owning project; another open project has no selection. Esc or empty-space clicks clear it; with nothing selected and no reanchor pending, Esc's default action is not prevented. A pick (item 6) and a chip's locate never change it. Frames use the rendered DOM, so an active frame may be absent from static `doan ls` output.
   - The collected values are read-only:
     - Box: size · padding · margin · gap
     - Typography: font · size · line height · weight
     - Color (text · background · border) · radius · shadow
     - `data-doan-*` attributes (id · implements)
   - Values are collected once on selection by main through CDP. Each value has one of four sources: a token (name and value, e.g. `--foreground` → `#0a0a0a`), Hardcoded, Unknown source or Default. Unknown means Doan cannot determine the source; CDP can read no-CORS sheets, so it does not mean an unreadable CDN. Reload reanchors the same canvas by unique `data-doan-id`, then selector (frames also keep their id); failure clears it with a notice. A move of the open canvas with its canvas ID (item 3) is a reload of the same canvas; a reload whose canvas ID changed at the same path is another canvas and clears selection. Opening another canvas clears selection; choosing the already open canvas preserves it. There is no editing (details and limits in ARCHITECTURE §3).

5. **Comments**: instruction notes stored as repo files (`.doan/comments/<canvas id>.jsonl`, ARCHITECTURE §2), read and resolved through the CLI (`doan comments`, `doan comment resolve`, item 9). The app has no comment screen; the person points through the canvas conversation instead (item 6).

6. **Point in a conversation**: the canvas conversation panel's composer holds anchor chips inline with the text, so a message can say what it is about.
   - Chips: a frame (its title, else its id), an element (“<name> <doan-id>”, or `<name> “<text>”` cut at 40 characters, where the name comes from the tag: heading, link, image, field, button, else the tag) and a point inside a frame (“Point in <frame>”). A message points at up to 32 distinct places, and a repeated place counts once; at the limit the composer says “A message can point at up to 32 places. Remove one to add another.” and the picker and Add to conversation are unavailable. A sent message carries the chips as anchors (ARCHITECTURE §7); one-line places (titles, previews, the queue line) show chip names in their place, and a returned draft comes back with its chips. Typed `{{` or `}}` still block Send; chips do not.
   - Editing: the caret stands before or after a chip, never inside. Backspace, Delete and Option-Backspace take a chip whole; Cmd-Backspace and Cmd-Delete take chips and text to the line's start or end; Shift-arrows select a chip as one unit; Cmd-Z and Shift-Cmd-Z (also Edit > Undo and Redo) undo a chip insert or delete as one step. Text pastes as plain text and images or files become attachments. Chips copied between composers of the same canvas stay chips; pasted anywhere else (another canvas, Home, the Overview, other apps) they become their names. During an IME composition a chip waits and goes in when the composition ends.
   - Pick from canvas (the composer's picker, first in its model row): starts one pick. The canvas shows a crosshair and “Click a frame or an element, or Shift-click a spot” with Esc. A click on a frame's background adds a frame chip, a click on an element adds an element chip, and a Shift-click inside a frame adds a point chip for that spot in the innermost frame; a click outside every frame adds nothing and the pick goes on. The chip goes in at the caret the composer had, and focus returns after it, unless focus moved elsewhere meanwhile or a composition is running. Esc (wherever focus is), the picker again, Hide conversation, another conversation from the menu, the composer becoming unavailable and leaving the canvas cancel the pick; a reload or a move with the same canvas ID keeps it. Pan and pinch still work while picking.
   - Add to conversation (toolbar) and Edit > Add Selection to Conversation (⌘L): with a frame or element selected, unfold the panel and put the selection's chip at the caret, or at the end when the composer had no focus, then focus the composer. The picker has no shortcut.
   - Availability: the picker, Add to conversation and ⌘L work only while the composer takes input and the canvas is shown; otherwise they are disabled with the tooltip “Pick from canvas isn’t available while the canvas can’t be shown.” or the composer's reason.
   - Locate: a chip in a sent message (a button named “Show <label> on canvas”) or in the composer moves the view to its target. A frame chip moves as picking the frame in the frame drawer does; an element or point chip keeps the zoom and centres the target, zooming out only for an element larger than the view. The target is highlighted for 1.2 seconds, a point with a 12 px ring. Elements are found by unique `data-doan-id`, then selector; frames and points by frame id. A target that is not found shows “No longer in the canvas” beside the chip until the next action or 4 seconds. Locate is disabled while the canvas is not shown.
   - Picking and locating change neither the selection, `doan active` nor the composer's text. A sent chip stays as it was sent when its target later moves. Home's and the Overview's composers take no chips; chips point only into the open canvas, and a point outside every frame is not offered.

### CLI `doan`

8. `doan init`: creates `.doan/canvases/` and `.doan/config.json` in the repo, adds union merge for comments and marks `.doan/` as documentation for GitHub's language stats in `.gitattributes`, and asks for the token CSS path. Does the same as the app's project setup (Set Up… in the sidebar project menu, first run's Set up and continue) from the terminal. It does not install skills: opening the app sets up the skill (item 0 'Agent setup').
9. `doan ls` · `doan comments` · `doan comment resolve` · `doan skill` · `doan config`. They only read and write repo files, so they work without the app. `ls` also returns optional `git` (branch/worktrees) when the repo is in a Git worktree. One unreadable file does not fail `ls`: an unreadable canvas file gives its row `error`, an unreadable comment file gives the rows of that ID `commentsError`, and both omit `comments` rather than report zero. The top-level `orphans` lists the comment files no canvas uses, each with `uncertain` while any canvas could not be read or parsed (ARCHITECTURE §12). `doan comments`, `doan check` and `doan comment resolve` still fail as a whole when they cannot read a file they need.
10. `doan active`: returns the frame or element the human selected in the app. Lets the agent find the target from just "fix this". Requires the app to be running. `doan onboarding …` drives first run through the running app; only `onboarding start` from the bundled CLI may open the app (item 0).
11. `doan check` does **static checks only**. It looks at what HTML parsing alone can catch: undefined `var(--*)`, duplicate `data-doan-id`, missing or duplicate canvas ids and frame ids, missing `doan:width` (error), comment files with no matching canvas, and whether `data-doan-implements` target files exist. External URLs (CDN scripts and fonts) are not blocked but shown as a warning list. If token CSS exists and hex or rgb colors are used directly, it warns. Comment files with no matching canvas are a warning, not an error; its message says what to do: “No canvas uses this comment file's id. Restore the canvas id, or ask the user. Do not delete or rewrite the comment file.” Full criteria: ARCHITECTURE §1 'Conventions'. Shell check also records best-effort device-local session associations without changing findings/output (§3, ARCHITECTURE §4).

### Skills

13. The `doan` skill reaches the five providers' own sessions through agent setup (item 0) and Doan's provider profiles through agent-auth (ARCHITECTURE §6).
    - Design presets. The CLI bundles 20 presets adapted from Impeccable, in this catalog order: `context`, `shape`, `document`, `extract`, `critique`, `audit`, `polish`, `distill`, `bolder`, `quieter`, `layout`, `typeset`, `colorize`, `clarify`, `harden`, `onboard`, `adapt`, `animate`, `delight`, `generate`. Upstream `craft`, `live`, `overdrive` and `optimize` are merged into these or left out, with no aliases. `doan design-skill` lists them, `doan design-skill <id>` returns one body; neither needs a project or the running app (ARCHITECTURE §12). The existing `doan` skill stays the entry point: the stub and the `doan skill` guide name the presets and the mapping rules, and the agent that already does the work picks a preset from the request. A preset the user names comes first; otherwise one is used only when it clearly fits; a concrete edit needs none; a review ends with a report. There is no classifier model, no rewrite of the user's request and no automatic review.
      - The design-start preset's id is `context` (upstream `init`). It is separate from CLI `doan init`, which only sets the project up; the success `result.nextSteps` of `doan init` points agents to `context` without the CLI running a model or a preset.
      - `document` ("Document the design system") creates and maintains a rules document for agents and design-system canvases in `.doan/ds/` for people, only when requested. It reads `context` first unless this conversation already read it or a product context document exists. The rules document updates the project's existing design document; without one, the agent asks where to put it and, with no answer, proposes a root `DESIGN.md` and waits for agreement. It never goes under `.doan/`.
      - For a new system, `document` proposes one canvas per token group, shared component or shared surface, keeping a unit's variants, states and steps together. Shared means people see it on two or more screens, including a dialog mounted once and opened from several screens. Each visual shared component keeps its own canvas; parts of one screen and nonvisual infrastructure wrappers may be skipped, with reasons reported. File names are canvas IDs; an existing ID collision needs another ID and disclosure. Frames point to existing implementation files, colors and type use token variables, components use their own markup and CSS, and icons come from the project's icon source. CSS outside the serving scope is disclosed; a workaround restates only needed rules, never a whole stylesheet copied into assets. Each canvas is checked rendered before finishing; anything not checked is reported.
      - An existing system that is sufficient is reused, not regenerated, and keeps its organization, including a legacy `design-system.html` under `.doan/canvases/`. Moving that file requires the user's request or agreement and preserves its ID. Maintenance changes only canvases and frames that drifted or were requested, keeps other IDs and content, and adds a new shared component as a new canvas. The rules document names the canvas for each token group and component and is the only place that lists open decisions; canvases disclose only what they draw that is not in code. A plain setup request is not approval to write a system, and code changes never start maintenance automatically. A rule is only as wide as its evidence and names the tokens, components or files it covers; instructions for new work stay open unless the user or a project document states them; no interim rule presupposes an open item; Verify rereads every rule for scope words ("every", "all", "new", "until" and similar).
      - A `generate` variant draws the target's states (hover, focus, disabled, loading, error and validation, empty) or names on the canvas the ones it leaves out. When a direction question gets no answer and the agent continues, it states the assumed direction on the canvas and in its answer.
      - The app has a main/preload read API for the list and bodies (ARCHITECTURE §7), and app conversations tell the agent to find presets through the guide. The picker, search, selection and send UI is on Home (item 1 'Home'). The catalog gives each preset one lowercase `group` (`start`, `review`, `refine`, `content`, `explore`; ARCHITECTURE §12), in this catalog order: Start `context`, `shape`, `document`, `extract`; Review `critique`, `audit`; Refine `polish`, `bolder`, `quieter`, `layout`, `typeset`, `colorize`; Content `distill`, `clarify`, `harden`, `onboard`; Explore `adapt`, `animate`, `delight`, `generate`. A group need not be contiguous in the catalog (`distill` sits between `polish` and `bolder`); group order is first appearance and the catalog order is unchanged.
