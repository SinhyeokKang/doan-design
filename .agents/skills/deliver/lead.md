# Lead (develop checkout)

> Part of the `/deliver` skill ([SKILL.md](SKILL.md)); the scope guard (§0) below is SKILL.md '0. Intake'.

**Messages between lead and conductor** use Orca mail. Both agents can receive mail at their Orca terminal handles.

- Use the handle returned by the conductor launch. Find the lead’s handle with `orca terminal list --worktree path:<develop checkout> --json`. Send with `orca orchestration send --to <handle> --subject "<topic>" --body "<message>" --json`.
- Start the message with `[lead]` or `[conductor <slug>]` and include the decision, reason and requested change. Say which earlier decision a new message replaces.
- A message ID confirms storage. The receiver reads the message with `orca orchestration check --terminal <own handle>` when notified. If delivery is refused, follow the reported recovery or tell the user. If the terminal is waiting for user approval, report what it asks and leave the decision to the user.

1. **Start the conductor.** Apply the scope guard (§0) first. Load the version-matched `orca-cli` guide, `git fetch origin`, then create the worktree, name its branch and start the conductor (`orca worktree create` names the branch `<git user>/<name>` unless `--branch` is given, and `--branch` silently adds a numeric suffix to a taken name, so rename instead: a taken name then fails):
   `orca worktree create --name <slug> --no-parent --base-branch origin/develop --repo path:<develop checkout> --json`, then `git -C <worktree> branch -m <type>/<slug>`, then `orca agent launch --agent <runtime> --worktree path:<worktree> --surface terminal --prompt "<brief>" --json`. `worktree create` without `--agent` opens an empty shell ("Terminal 1"); once the agent's terminal has started, close that shell with `orca terminal close --terminal <handle> --json` after checking it holds only a prompt.
   (`feat/<slug>` for `/orchestrate`; `<runtime>` is this session's model family unless the user allowed another.) The brief names the skill to run (`/deliver <change>` or `/orchestrate <plan>`), says the branch is already checked out (do not create or switch branches), that it ends with a PR against develop and does not merge, that it asks the user directly for decisions, that a small extra change the user gives it goes on the same branch and PR, and that it messages the lead as 'Messages between lead and conductor' above says. Name any running conductor whose files overlap. Confirm the session started on the brief (the receipt's outcome, then its first output) before reporting.
2. **Watch.** A background loop wakes the lead when the conductor's PR opens or its terminal goes idle with no busy indicator; read the terminal then. Conductors' questions go to the user in their own sessions; the lead answers only what concerns its own decisions or other conductors.
3. **Review the PR.** It comes from the branch the lead created and targets develop. Wait for `gh pr checks <n> --watch`, then `gh pr checks <n> --required` until it lists `gate` as passed (`gate` appears only after the shards finish). A shard cancelled with no steps run (`gh run view <run id> --json jobs`) never got a macOS runner within its timeout: rerun it with `gh run rerun <run id> --failed` instead of reading its log or sending it to the conductor. Read the body and diff: scope matches the brief, no decision in PRODUCT or ARCHITECTURE changed without the user, unverified items are listed, the `/agent-eval` requirement (AGENTS.md 'Workflow') is met or its absence explained, and a finished feature is promoted with its directory deleted. Send findings to the conductor by Orca mail and re-review its push; the lead does not edit a conductor's branch.
4. **Resolve contention.** Merge PRs as they pass review, in the order the user or a chain file gives, otherwise in arrival order. After each merge, check the other open conductor PRs: one that now conflicts, or that changes the same files as what just merged, goes back to its conductor to merge `origin/develop` into its branch (no rebase or force push), resolve, rerun its gate and push; a shared-document conflict keeps develop's text and adds the branch's own. A PR whose files do not overlap merges as it is; the push gate on develop checks the result.
5. **Merge and clean up.** `gh pr merge <n> --merge`, then `git pull --ff-only` on develop. In the conductor's worktree, `git status --porcelain` must be empty and `git cherry origin/develop` must have no `+`; ask before discarding anything. Note the branch tip, remove the worktree with `orca worktree rm --worktree id:<repo-id>::<path> --json` (never `--delete-branch`; recreate the branch at its tip if the receipt shows it deleted), and confirm no child worktree of that conductor remains in `orca worktree list`. Report the merge commit and anything left.
6. **Verify what the conductors left unverified.** Once every conductor PR the lead started has merged, collect the unverified items their PR bodies and reports list, and verify them in the develop checkout at the merged HEAD: real-app probes through `/runtime-test` with `app/runtime/` isolation, PoCs against the real binaries in `.scratch/`, and checks a conductor skipped. The lead runs these itself rather than starting conductors for them. Computer use (`orca computer`, for a window Playwright cannot drive) is a standing permission for the lead here; do not ask the user before using it, and keep the same isolation as other runtime checks. A defect found goes back to the user as a fix candidate (`/deliver` through step 1); an item that cannot be verified here (another machine, OS or agent version, a real account) goes to BACKLOG 'Not verified in the real app' with what was and was not seen. Report each item as verified, failed or still unverified, with its evidence.
